# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). This project does not yet follow Semantic Versioning releases (see `README.md` status) — entries accumulate under `[Unreleased]` until the first tagged release.

## [Unreleased]

### Changed

- **README refreshed with current screenshots and up-to-date counts.** Added the Imaging tab's portrait-layout screenshot (`assets/screenshots/imaging portrait.png`, showing the layout described in the `IMG-120`/`IMG-130` changelog entry) to the Screenshots section, and corrected the test-count badge and the Status section's test and requirement counts, all of which had drifted behind the codebase: `pytest -m "not soak and not hardware and not integration"` now passes 639 of 646 collected tests (1 skipped, 6 deselected), up from the previously shown 244/488, and `docs/SRS.md` now carries 272 numbered requirements, up from 235.

### Removed

- **The Library's statistics dashboard is gone, and the Library no longer has tabs.** The Statistics tab on Images and the whole `StatsWidget` (`galileo/ui/library/stats_widget.py`, ported from AstroFiler) are removed, along with `test_tc_lib_080_*`. Requirement `LIB-080` (a repository statistics dashboard) is therefore not met; it and `TC-LIB-080` are still in the SRS/RTM, and `TODO.md` notes that they need reinstating or retiring. Images and Dedup are now single screens, and **Merge Objects** is its own item in the Library menu, after Dedup, with its own icon. The **Siril CLI** path is removed from Options > Library > General (nothing reads it any more; the `siril_cli_path` key is no longer written, and any existing value in `library.ini` is ignored). The separate PySiril timeout and logging settings on the Calibration tab were left as they were.

- **The placeholder library code that stood in for AstroFiler is gone.** `galileo.library.repository` (`Repository`, an in-memory scanner), `galileo.library.calibration` (`LibraryCalibrationService`, also exported as `LibraryService`), `galileo.library.cloud` (`CloudSyncService`), the three matching stub commands (`calibrate`, and the old `load_repo` / `cloud_sync`), and the stub tables `fits_files`, `path_mappings` and `master_frames` were a small stand-in written before the real AstroFiler code was brought over; each is replaced by the real thing (below). Nothing outside the tests used them except the sequencer's optional `_repository` hook, which now takes `LibraryRegistrar`. A `galileo.db` created before this change keeps its old, never-filled stub tables; they are harmless and no longer read. AstroFiler's own Log and About views, its update checker and its start-up registration ping were not brought over (Galileo has its own log, About box and release process), and the **Display Settings** group (theme, font size, grid icon size) was dropped from the configuration screen — Galileo has one global theme, and nothing in the library read the other two.

- **Reference screenshots (`assets/samples/`) are no longer part of the repository.** They are screenshots of a third-party application used only as a reference layout to which controls each screen needs, and shipping them would redistribute someone else's copyrighted artwork. The files are untracked and the folder is listed in `.gitignore`, so a local copy can stay in place for reference without being committed by accident. The Mount and Filter Wheel changelog entries and the matching docstrings in `galileo/ui/app_window.py` now say "reference layout" instead of naming the other application's screens. The "N.I.N.A.-style" / "sampled from N.I.N.A.'s theme" wording in the README, changelog, and the comments in `galileo/ui/app_window.py`, `theme.py` and `icons.py` was reworded too; the colours themselves are unchanged. `docs/PSD.md`, `SRS.md` and `SECURITY.md` still name NINA where they record it as a behavioral reference and state the clean-room constraint (PSD C1). Comments and changelog entries that mention `assets/samples/...` still name them as the layout reference; the images just won't be in a fresh clone. They remain in earlier commits already pushed to GitHub — see the maintainer for whether history should be rewritten.

### Fixed

- **Plate solving still failed with "Error reading the image file" after the BITPIX-64 fix below, on a file confirmed as BITPIX 16 and openable in Tenmon — because the two fixes are for different bugs.** The BITPIX-64 fix stopped Galileo writing a 64-bit sample format; it did not fix everything ASTAP is strict about. Constructing a FITS HDU as `fits.PrimaryHDU(pixel_data, header=some_pre_built_header)` — which every writer in `galileo/metadata.py` and `galileo/platesolve.py` did — is completely standard, astropy-valid FITS, and astropy (so Tenmon, and anything else built on a general-purpose FITS library) reads it back without a murmur. But for unsigned pixel data (8- or 16-bit), astropy needs to add `BSCALE`/`BZERO` cards for the unsigned-integer convention, and when a header is merged in at construction it appends those two cards *after* everything already in that header — landing them at the very end of the file, behind every custom keyword (`TELESCOP`, `OBJCTRA`, a previous solution's WCS, …), instead of immediately after `NAXIS2` where a real camera's own FITS writer puts them and where ASTAP's own minimal parser expects to find them. ASTAP refused the file outright rather than reading past them in the wrong place. Every write path now builds the HDU from the pixel data alone first — letting astropy place `BSCALE`/`BZERO` on its own, immediately after `NAXIS2` — and only then appends the metadata cards, via a new shared `galileo.metadata.build_primary_hdu` (`FitsMetadataWriter.write`'s compressed and uncompressed branches, `galileo/platesolve.py`'s `_write_frame` and `_normalise_fits`) rather than passing a header into the HDU constructor. Verified by disassembling the raw header bytes of a file matching the report (a 1920×1080 Alpaca-sourced frame with typical telescope/instrument metadata) before and after the fix, and by reproducing the ordering defect standalone to confirm the new tests fail against it. Tests: `test_tc_meta_010_bscale_bzero_land_right_after_naxis_not_after_custom_keywords` and `test_tc_meta_010_build_primary_hdu_round_trips_and_keeps_extra_cards` in `tests/test_meta.py`; `test_tc_plt_070_solve_frame_puts_bzero_bscale_ahead_of_the_header_not_after_it` and `test_tc_plt_070_a_rewritten_file_also_puts_bzero_bscale_ahead_of_the_kept_header` in `tests/test_plt.py`. Not done: several other FITS writers elsewhere in the codebase (`galileo/calibration.py`, `galileo/sequencer/basic.py`, the vendored AstroFiler calibration/master-frame code, `galileo/vstarget/analysis/stack.py`) build their HDUs the same header-merged-at-construction way and likely have the identical ASTAP-compatibility defect; none of them write frames that currently pass through a solver, so they were left as they were rather than changed on spec.

- **Autofocus reported "Stars: 0, HFR: 0.03"-style nonsense on real frames, misjudged HFR even when star detection worked, and never left the focuser at the computed best-focus position.** Three compounding bugs in `galileo/autofocus.py`:
  - `_measure_stars` handed the raw frame straight to SEP, which requires a 2-D array. A colour camera's frame (Alpaca hands back `(height, width, 3)`) made `sep.Background`/`sep.extract` raise, which a bare `except Exception:` swallowed *silently* — no log line — and fell back to a crude `std/mean` contrast ratio with `star_count` hardcoded to 0. That fallback is what "Stars: 0, HFR: 0.03" actually was. Colour frames are now collapsed to one plane before detection (`_to_2d`, the same averaging `galileo.platesolve.frame_for_solver` already does for the same reason — colour carries no astrometric/photometric information), and the fallback now logs the exception instead of hiding it.
  - Even when SEP succeeded, HFR was approximated as `sep.extract`'s `a`/`b` shape-fit axes (`(a+b)/2`, itself halved again) — those describe an object's isophotal footprint, not where half its flux falls, and are only ~1–2px even for a well-defocused star, so a real detection still reported HFR under 1 when values like 4.3px were expected. It now calls `sep.flux_radius(..., frac=0.5)` per detected star and reports the median — an actual half-flux radius.
  - `AutofocusService.run()` computed `best_position` from the fitted curve but never moved there: `apply_and_confirm` (FOC-020's "move to best position and confirm with an exposure") existed and was unit-tested in isolation, but nothing called it — not `run()` itself, not the Focus screen's worker thread, not the sequencer's `run_triggered`. A successful run now ends by calling `apply_and_confirm(best)` internally, so the focuser is actually left at the computed position regardless of caller. The confirmation exposure is tagged `confirm=True` on its `FocusFrameEvent` so the Focus screen can show it — image and stats update, letting a user visually check focus at the position actually used — without folding a non-sweep sample into the V-curve plot.

  Code: `_to_2d`, `_measure_stars`, `AutofocusService._sweep`/`_measure_hfr` in `galileo/autofocus.py`; `FocusFrameEvent`'s new `confirm` field in `galileo/bus.py`; `FocusPage._on_frame`/`_on_frame_event` in `galileo/ui/focus.py`. Tests: `test_tc_foc_090_run_publishes_start_each_frame_and_completion` in `tests/test_foc.py` and `test_tc_foc_090_auto_focus_button_runs_a_sweep_and_shows_it` in `tests/test_focus_page.py`, both updated for the extra confirmation frame/exposure and the focuser's final `move_to`.

- **Every FITS file Galileo wrote used a 64-bit sample format, which most other astronomy software — ASTAP, Tenmon, and presumably others — refuses to open as "unsupported sample format".** The previous entry in this section fixed this for the frames written for plate solving only; it turned out to be the same root cause everywhere else Galileo writes a FITS file, not a solver-specific problem. A camera reached over Alpaca hands its image back built from JSON numbers, which numpy turns into 64-bit integers, and every writer — the imaging tab's Save Frame, its Auto-Save to Library, the live stack, `galileo.metadata.FitsMetadataWriter` generally — wrote that straight out as `BITPIX` 64. astropy reads a 64-bit FITS without complaint, which is why this went unnoticed until it was opened in something else. `galileo.metadata.normalise_pixels`, previously private to the solver's own frame-writing helper, is now this module's general pixel-format layer: `FitsMetadataWriter.write` (and so every save path built on it) converts through it before writing, picking the smallest of a fixed portable set (`uint8`/`uint16`/`int32`/`float32`) that holds the data — the same choice `frame_for_solver` already made, which now shares this one implementation instead of its own copy. Tests: `test_tc_meta_010_written_frames_use_a_pixel_format_other_software_reads` and `test_tc_meta_010_normalising_pixels_keeps_the_image` in `tests/test_meta.py`.

- **Load & Slew now rewrites the file it is given instead of copying it, so the FITS files that exist in the wild actually solve.** It copied the chosen file byte for byte and handed that to ASTAP, so anything ASTAP cannot read failed instantly with “Error reading the image file” — a tile-compressed FITS (whose image lives in a later HDU, not the primary one), a three-plane colour FITS, or one with 64-bit pixels. The file is now read with astropy, which handles all of those, and rewritten as a single plane at a bit depth solvers accept; solving a copy is still the point, since ASTAP writes its solution into the file it is given. The source header is carried over apart from the keywords describing the old layout, so the focal length, pixel size and any existing WCS survive.

- **A solver that rejects a frame now says what it was handed.** “Error reading the image file” on its own gives nothing to act on, so when ASTAP exits with that code the frame’s real dimensions, bit depth and size are reported with it — and the full command line is written to the log. A wrong bit depth or an unexpected plane count is then visible in the message rather than needing a round of guesswork.

- **Fixed: the solver was told every camera has a colour mosaic.** The Bayer pattern is saved for every camera and defaults to RGGB, so it says nothing about whether a sensor is actually colour; writing `BAYERPAT` into the solve frame regardless would have told the solver a mono camera had a mosaic. It is left out until Galileo has a real colour/mono setting to go on. (Introduced in the header change below, and fixed before release.)

### Fixed

- **Fixed: plate solving failed immediately with “Error reading the image file” on a perfectly good frame.** The frame written for the solver was whatever array the camera handed back, and two things about that are outside what ASTAP (and most solvers) will open. The Alpaca adapter builds its image from JSON numbers, so the array arrives as 64-bit integers and was written as a 64-bit FITS (`BITPIX` 64, or -64 for a float) — a legal FITS, but not one ASTAP reads. A colour camera compounds it: its frame arrives as three planes and was written as a three-dimensional FITS, which solvers handle inconsistently at best. Either way ASTAP rejected the file on open, which is why it failed in a fraction of a second rather than after searching. Solver frames are now always written as a single plane — the colour planes averaged, since colour carries no astrometric information — in unsigned 16-bit where the data fits (what astronomy cameras actually produce) and 32-bit float otherwise. The colour axis is found at whichever end the source puts it, so both Alpaca’s (height, width, 3) and a plane-first FITS cube are handled. This also answers whether a one-shot-colour image has to be debayered before solving: it does not — ASTAP solves a raw Bayer mosaic, and what it needs is a readable single-plane file, which is what it now gets. Code: `frame_for_solver` in `galileo/platesolve.py`. Tests: two cases in `tests/test_plt.py`.

- **Frames captured for plate solving carried no FITS header at all, which can stop a good image solving.** `_write_frame` wrote a bare image array, so the solver was told nothing about the instrument — no pixel size, no focal length, and for a one-shot-colour camera no `BAYERPAT` to say the frame is a Bayer mosaic. A solver that cannot derive the image scale has to search a wide range of scales instead, which is a common reason a perfectly good frame fails. Captured solve frames now carry `XPIXSZ`/`YPIXSZ`, `FOCALLEN`, `APTDIA`, `TELESCOP`, `INSTRUME` and `BAYERPAT`, taken from the selected optical tube and the camera’s saved configuration — so the values depend on the focal length being set on Equipment > Optics and the pixel size on Equipment > Camera (use its Download Info button). Anything not configured is left out rather than guessed at, and the frame is still written and still solvable, just without the help. The header is built by a new `galileo.metadata.build_header`, shared with the imaging tab’s saved frames so both describe the instrument identically. Tests: two cases in `tests/test_plt.py`.

### Added

- **An Options > Imaging screen offers a "Desired BITPIX" setting for frames the imaging tab saves** (`IMG-170`, new in the SRS/RTM — counts now 256/270), following on from the BITPIX-64 fix above. Left on the default **Auto**, a saved frame is written in the smallest of a fixed portable format set — 8-, 16- or 32-bit integer, or 32-bit float — that holds its values without loss, which is what Galileo has always done once the fix above landed. Choosing a fixed value (8/16/32/-32) instead writes *every* frame Save Frame, Auto-Save to Library and Save Stack produce in that one format, for a downstream tool that expects one consistent format rather than whatever best fits each frame; a value outside the chosen format's range is clipped rather than wrapped, and a float destined for an integer format is rounded to the nearest whole number. A change takes effect on the Imaging tab already open, not only after a restart. Frames captured for plate solving are not affected by this setting and always use Auto — what a solver can read is a correctness question, not a preference. Code: `normalise_pixels`'s new *bitpix* parameter and `BITPIX_CHOICES` in `galileo/metadata.py`, the new `galileo/imaging_settings.py`, `AppWindow._build_imaging_settings_page` in `galileo/ui/app_window.py`. Tests: the `TC-IMG-170` group in `tests/test_img.py`.

- **A finished slew now leaves the mount tracking, at the rate the target actually needs** (`EQP-MNT-050`, new in the SRS/RTM — counts now 255/269). Nothing turned tracking on after a slew before, so a mount that arrived parked-but-idle simply let the sky drift past. Now, once a slew reports itself finished, the mount is put on the right rate and tracking is switched on: **lunar** for the Moon, **solar** for the Sun, **sidereal** for everything else — stars, deep-sky objects and the planets, whose departure from sidereal is smaller than a night's guiding error. The rate is selected *before* tracking is enabled, so the mount never tracks at the wrong one even briefly. This covers the Star Atlas **Goto** (which knows the object it was sent to), the Mount page's RA/Dec and Alt/Az **Slew** buttons (which name nothing, so the Pier's current object stands in), and the plate-solve **Slew to Target** workflow, which already waited for its slews. **Sync** does not start tracking — nothing moved. Waiting for a slew takes as long as the slew does, so on the UI it runs on a worker thread and the status bar reports "Slew finished — tracking at the Lunar rate" when it is done. A mount that never stops reporting itself slewing (3 minutes) is left alone rather than having tracking commands piled on top of a movement still in progress; a mount that cannot select a rate, or refuses to, is still left tracking, since sidereal is what such a mount does anyway and not tracking at all would be worse; and a mount that does not report its slewing state at all is taken as arrived rather than never tracked. Code: the new `galileo/tracking.py` (`tracking_rate_for`, `wait_for_slew`, `resume_tracking`), `SolveWorkflow._resume_tracking` in `galileo/platesolve.py`, `AppWindow._track_when_slew_finishes` and `_ResumeTrackingThread` in `galileo/ui/app_window.py`. Tests: the `TC-EQP-MNT-050` group in `tests/test_eqp.py`. Not done: the sequencer's and meridian-flip's own slews do not yet resume tracking — both call the mount port directly and are outside this change; and comets, asteroids and satellites still track sidereal rather than at a custom rate, which is `EQP-MNT-040` and remains unbuilt.

- **Live stacking: a run of frames now builds one image as it is taken** (`IMG-160`, new in the SRS/RTM — counts now 254/268). A **Live Stack** checkbox sits under Gain in Capture Settings, off by default. With it ticked and a Quantity of three or more, each captured frame is registered against the first of the run and added to a running mean which becomes the displayed frame — so the preview, statistics and histogram improve as the run goes on, instead of each exposure discarding the one before. Runs of one or two frames are unaffected. Registration uses `astroalign`, which solves a full affine transform and so corrects field rotation as well as drift; where astroalign is not installed, or cannot find a transform for a particular frame, the stacker falls back to whole-pixel translation measured by FFT phase correlation, and the status line says which was used rather than leaving it to be guessed. The mean is taken per pixel over the frames that actually cover it, so the partly-covered edges a drifting run leaves keep their brightness instead of fading out. A frame whose shape doesn't match the stack — binning or the region of interest changed mid-run — is refused rather than stacked into nonsense, and counted in the summary. A new **Save Stack…** button beside Save Frame offers **Save to Library** (written to the scratch folder and registered, so it lands in the repository beside the subs) and **Save to File…** (a path of your choosing); it stays disabled until there is a stack. The saved stack records what it is made of: `NCOMBINE` frames and `EXPTOTAL` seconds of integration, with `EXPTIME` left as the single-sub exposure since that is what the Library files by, and `DATE-OBS`/`DATE-END` spanning the first sub to the last. Auto-Save to Library is unchanged and still catalogues the individual subs — the stack is saved only when asked for. Code: the new `galileo/livestack.py` (`LiveStacker`, `register`, `translation_offset`), `capture_series`/`save_stack`/`save_stack_to_library` in `galileo/ui/imaging.py`. Tests: the `TC-IMG-160` group in `tests/test_img.py`. Not done: stacking a one-shot-colour frame works on the raw mosaic, so an odd-pixel alignment shift will scramble the Bayer grid if Debayer is then switched on — debayer before stacking is not yet possible; and the stack is held in memory only, so it is lost when a new run starts or the application closes unless it has been saved.

- **The Camera selector now appears on every screen that selects the optics, and says whether the camera is connected** (`PROF-120`, new in the SRS/RTM — counts now 253/267). The top-bar Camera selector was shown only on Imaging and Solve, and only when a Pier had more than one camera configured — so on a normal one-camera setup it was invisible everywhere, and Solve refusing to capture with "Connect a camera on the Camera equipment page first" gave no way to see which camera it meant or whether it was connected. The selector now appears wherever the Optics selector does (Framing, Imaging and Solve — an optical train is the tube *and* the camera that feeds it), whatever the number of cameras, and each entry is marked **(not connected)** until that camera answers, e.g. `Primary Camera — ASI2600MM (not connected)`. With no camera configured it stays visible but disabled, reading `None configured — see Equipment > Camera`. Refusing to capture now names the selected camera and says whether it is unconfigured or merely unconnected, on both Imaging and Solve. Framing gains the selector for consistency but does not use either selection yet — its field-of-view calculation is still a stub on an empty profile.

- **Fixed: the Camera selector could list, and default to, the wrong camera.** `list_device_config_slots` returned slots in whatever order the database produced them, which with the unique index on (pier, category, slot) is alphabetical — putting `camera_2` ahead of `primary`. The selector therefore listed "Camera 2" first on a Pier with two cameras, and any caller taking the first slot as a default got the second camera. Slots now come back in slot order: `primary`, then the numbered slots by number, then anything else alphabetically. The Camera and Focuser pages were already order-independent (they load each panel by slot id and size themselves from the highest number), so only the selector's order and default changed. Requirement `PROF-110`'s screen list in the SRS was also stale — it said Framing and Imaging, while Solve has shown the Optics selector since it gained one — and now names all three.

- **The Star Atlas shows where each Pier's telescope is pointing, and the reticle travels across the sky as the mount slews** (`SKYMAP-090`, new in the SRS/RTM — counts now 252/266). Every Pier in the current Observatory gets a labelled reticle — a circle with four ticks and a gap in the middle, so whatever it sits on stays visible — captioned with the Pier's name and its current object, e.g. **Pier A → M 31**. A Pier whose mount Galileo can read is drawn where the mount says it is actually pointing, so during a slew the reticle can be watched crossing the sky: it turns amber, the label gains **(slewing)**, and a dotted line runs to a fainter reticle on the target it is heading for. The mount is re-read every 3 seconds while the page is on screen, and every second while a slew is running, always on a worker thread — a slow or unreachable mount can never stall the sky view. A Pier whose mount can't be read (including every Pier that isn't the selected one, since only the selected Pier's devices are connected) falls back to a reticle on its current object; a mount that stops answering reverts to that rather than leaving a stale reticle frozen where it last reported. Mounts reporting coordinates of date are converted to J2000, which is what the map draws in. A new **Telescope markers** checkbox in the Star Atlas panel turns the reticles off, and is remembered between runs like the other display options. This also delivers the "mount's current pointing position live on the sky map" half of `SKYMAP-050`; that requirement's field-of-view rectangle is still not drawn. Code: `set_pier_markers` and `_draw_pier_markers` in `galileo/ui/star_atlas.py`, `AppWindow.pier_markers` / `_poll_pier_pointing` and `_MountPositionThread` in `galileo/ui/app_window.py`. Tests: the `TC-SKYMAP-090` group in `tests/test_star_atlas.py`. Not done: a reticle for a Pier other than the selected one never moves, because Galileo connects one Pier's devices at a time — showing live positions for several mounts at once needs per-Pier device connections, which the Equipment pages don't yet keep.

- **Capture now takes a run of frames, at a gain you set, and files each one into the Library** (`IMG-150`, new in the SRS/RTM — counts now 251/265). **Quantity** (default 1) and **Gain** (default 110) sit under Exposure in Capture Settings. Capture takes Quantity frames one after another with the screen's settings, showing each one — preview, statistics, histogram — as it arrives rather than only the last; the progress bar spans the whole run and the status line reads "Frame 2 of 5 — Exposing… 3.4s left". A new **Stop** button beside Capture abandons the exposure in progress and takes no more. Gain 0 means "leave the camera as its driver has it"; any other value is sent with the exposure (`CCD_GAIN`/`CCD_CONTROLS` on INDI, `gain` on Alpaca). **Auto-Save to Library**, a checkbox under Save Frame and on by default, writes each frame as it is taken to a scratch folder and registers it with the Library, which moves it into the repository under its own naming scheme — so it appears on Library > Images (refreshed automatically if that screen is open) without a later scan. It needs the repository folder set in Options > Library; without one nothing is written and the log says so. A frame the Library refuses is left in the scratch folder and the status line says where it is. A light frame with no current object is filed under `Unknown`, with a note pointing at the Star Atlas. **Save Frame…** is unchanged: it still prompts for a path and writes a FITS file there. *Headers:* frames the Imaging tab writes now carry every card Galileo can fill in, where before they carried only `OBJECT` — `IMAGETYP`, `EXPTIME`/`EXPOSURE`, `FILTER`, `GAIN`, `XBINNING`/`YBINNING`, `CCD-TEMP`, `DATE-OBS`/`DATE-END`/`DATE`, `TELESCOP`, `INSTRUME`, `FOCALLEN`, `APTDIA`, `XPIXSZ`/`YPIXSZ`, `OBJCTRA`/`OBJCTDEC`, `RA`/`DEC`, `SITENAME`/`SITELAT`/`SITELONG`, `OBSERVER`, `BAYERPAT`, `PIERSIDE`, `FOCUSPOS` and `SWCREATE`. That covers every card the Library builds file and folder names from, which is what lets a captured frame be filed correctly. Values come from the selected optics, the camera's saved configuration, the Observatory, the connected mount and focuser, and the current object; anything unknown is left out, and reading the mount can never fail a capture. A dark or bias carries no `OBJECT` or `FILTER` so the Library files it as calibration. Two fixes fell out of this: the Alpaca camera adapter ignored gain entirely and always exposed with the shutter open (a dark was taken as a light), and its `get_temperature` reported a hard-coded −10 °C when it had never read one — it now reports NaN, so an unknown temperature is no longer written to headers as a real reading. Code: `capture_series`, `frame_metadata` and `_auto_save_to_library` in `galileo/ui/imaging.py`, `LibraryRegistrar.register_capture`, an extended `_KEYWORD_MAP` in `galileo/metadata.py`, `AppWindow._imaging_frame_context` and a series-aware `_CaptureThread` in `galileo/ui/app_window.py`. Tests: the `TC-IMG-150` group in `tests/test_img.py`. Not done: binning is recorded as 1×1 because the tab has no binning control yet, and the sequencer's own capture path is untouched.

- **Each Pier now has a "current object": pick something in the Star Atlas and frames are named after it and Solve slews to it** (`IMG-140`, new in the SRS/RTM — counts now 250/264). Selecting an item in the Star Atlas (clicking it, or finding it by name) makes it the selected Pier's current object, and the top bar shows **Current object: M 31** at its right-hand end on every screen ("none" until one is picked). It is kept per Pier — two Piers can be working on different targets, and switching Pier switches the note — for the running session only; it isn't saved to the database, so it is empty again after a restart. *File names:* the Imaging tab's saved frames are now `M_31_<time>.fits` instead of `frame_<time>.fits`, the Save Frame dialog suggests `M_31_<date>T<time>.fits`, and the FITS `OBJECT` keyword is written to match (previously these files carried no `OBJECT`); the frames captured for plate solving are `solve_M_31_<timestamp>_<n>.fits`. With no current object the names are as before. Unsafe characters in the name become `_`. *Solve:* **Capture & Solve with the Solver Action set to Slew to Target** now takes the current object's J2000 coordinates as its target instead of wherever the mount happened to be pointing. It slews there first (if the mount is more than the Accuracy away), then captures, solves, syncs and re-slews as before until the solution is within the Accuracy of the object. It now uses `math.isfinite`, and a lookup that fails is logged at debug level instead of vanishing silently (the object is still returned with an unknown magnitude, as before). This function had no test; nine `TC-SKY-100` cases in `tests/test_sky.py` cover a real value, a negative magnitude, NaN, ±inf, a masked cell, no rows, no table and a network error, using a fake Simbad client so they run offline. The two infinity cases fail on the old code.

- **Advanced-sequencer templates now keep their instruction parameters, and no longer depend on the module importing itself** (`SEQ-ADV-060`, `galileo/sequencer/advanced.py`). Ruff flagged `_find_instruction_class` for doing `import galileo.sequencer.advanced` from inside that module and looking classes up with `getattr`; following that up showed the template feature didn't actually round-trip. `save_template` wrote only each instruction's type and label, and `load_template` rebuilt instructions with `cls.__new__(cls)` — no constructor, no saved values — so a saved *Capture Ha × 10 @ 300 s* came back as the class defaults (*L × 1 @ 60 s*), silently; the only test checked the template's name and instruction count, so it passed. Now: instructions are looked up in `InstructionRegistry` (new `find(name)`, first registration wins so a plugin can't shadow a built-in), which also makes templates work for plugin-registered instruction types, something the module `getattr` could never do; `to_dict` stores every dataclass field under `params` and `BaseInstruction.from_dict` restores them (unknown parameters are ignored with a warning; plugin classes that aren't dataclasses can override it); a template naming an unregistered type — or any other name in the module, which the old lookup would have accepted — now raises `ValueError` instead of quietly dropping the step and running a shorter sequence. Templates saved by earlier versions (type and label only) still load, with defaults. Not changed: templates still save only a group's instructions, not its nested groups, conditions or triggers (see `CODE_REVIEW.md`). Tests: four new `TC-SEQ-ADV-060` cases in `tests/test_seq_adv.py`; seven of them fail on the old code.

- **A failed session auto-regeneration no longer starts a second, partial regeneration.** After files are imported (Images > Download / Load New) `SessionsWidget.auto_regenerate_sessions` rebuilds sessions for the new files. Its error handler was followed by ~170 lines — a stale copy of steps 2–4 of `_do_regenerate_sessions` (create light sessions, create calibration sessions, link them) with a "Regeneration Complete" dialog — that had lost its own method header and so ended up inside the handler. Whenever auto-regeneration raised, Galileo logged the error and then silently tried to create and link sessions for *all* files, possibly with progress and message dialogs the user never asked for. Found by Ruff (`B025`, two `except Exception` on one `try`); the handler now just logs the error and closes its progress dialog. The regenerate button's real code paths (`_do_regenerate_sessions`, `_do_regenerate_sessions_new_only`) are untouched. Test: `TC-LIB-040` in `tests/test_lib.py`, which fails on the old code.

- **FITS compression on import could destroy or corrupt the image it was compressing; it now never touches the original until the compressed copy is verified** (`galileo/library/core/compress_files.py`, used by every auto-import when "Compress FITS" is on). Found in a code review and reproduced on real files before fixing:
  - The in-place path replaced the original *first* and then "verified" the result by comparing the file with itself, so verification could never fail and a bad result was already permanent. The compressed copy is now written to a temporary file, checked against the untouched original, and only then moved into place; any failure leaves the original byte-identical and removes the temp file (and partial `.gz`/`.xz`/`.bz2` outputs, which are also verified by SHA-256 now instead of by file size).
  - **Floating-point images were not lossless.** Astropy quantizes float data by default, so a float32 frame came back with pixel errors of about 2 ADU while the module claimed lossless compression. Quantization is now off (`quantize_level=0`) and verification demands exact equality, treating NaN as equal to NaN — previously any image containing NaN pixels "failed" verification after already being overwritten.
  - **Decompressing a `.fits` that had been compressed in place deleted it**: it was mistaken for a gzip file, the output path was the input path, and the invalid-result cleanup removed the file. Tile-compressed FITS is now recognised by its structure, and decompressing a file onto itself is refused (astropy reads tile-compressed files transparently, so there is nothing to decompress).
  - `HISTORY` header cards were rewritten as `COMMENT` cards, and extensions or header cards that couldn't be copied were dropped silently. Both now keep their type, and if anything can't be carried over the compression is abandoned rather than shipping a lossy copy. A binary table appearing before the image is no longer mistaken for it.
  - Smaller changes in the same file: the shared compressor is now cached per config path and thread-safe, and `reset_fits_compressor()` (called when Options > Library is saved) makes changed compression settings take effect without a restart; the unused `_select_optimal_compression` and a dead fallback for a config module that always exists were removed; the tile-compression header keywords are only written by hand for older astropy, which fixes a `VerifyWarning` on every read of a compressed file under astropy 8; `mypy`/`ruff` findings in the file (bare `except`, implicit `Optional`, unused imports/variables, f-string logging without tracebacks) were cleared.
  Tests: `TC-LIB-010` group in `tests/test_lib.py` (lossless round trip for uint16/int16/float32/NaN/3-D images, HISTORY/COMMENT and extensions kept, failed compression leaves the original untouched, verifier actually compares, in-place decompress refused, gzip/lzma/bzip2 round trip). Files already compressed by earlier versions may hold quantized float data or COMMENT cards that were HISTORY; those can't be recovered.

- **`HorizonProfile.min_altitude_at` returned the wrong altitude between the last and first azimuth.** Interpolating from the highest azimuth back round through north never matched, so the answer fell back to the first point's altitude for the whole stretch (e.g. 350° with points at 10° and 300° gave the value at 10°, not a blend). It now wraps properly, and also accepts an array of azimuths (`min_altitudes`). This is the profile the Sky Atlas altitude chart uses for `SKY-040`, so its "above horizon" flags change in that stretch.

- **Library fixes found while bringing AstroFiler over.** `fitsSession` had no `fitsBiasMaster` / `fitsDarkMaster` / `fitsFlatMaster` fields although the database columns exist (AstroFiler migration `002`) and the calibration code and Sessions screen read them, so `fitsProcessing.createMasterCalibrationFrames` stopped with an `AttributeError`; the model now has them. The duplicate finder used a raw SQLite connection to `astrofiler.db` in the current folder; it now uses the shared database. Migration `013` recovers a Galileo database that predates migrations without failing on tables it already holds. Known and not fixed: that older `fitsProcessing.createMasterCalibrationFrames` path still creates nothing (it looks sessions up by an id that is `None`); the Sessions screen and the `auto_calibration` command use `galileo.library.core.auto_calibration`, which works and is what the tests exercise.

- **Plate solving with a real ASTAP could never report success.** `PlateSolver` read ASTAP's answer from its `.wcs` file with astropy, but that file is a bare header not padded to FITS's 2880-byte blocks, so every solve — even one ASTAP had solved — came back as "Empty or corrupt FITS file". The answer is now read from the `.ini` file ASTAP writes for both outcomes. Found by running the real ASTAP 2026.09.01 (with the D50 star database) on a rendered star field: it now solves to within 7″ of the true position and reports a pixel scale of 12.0006″/px against a true 12. Tests: `test_tc_plt_010_*` in `tests/test_plt.py`, including one that runs the real ASTAP when it and the Star Atlas catalogue cache are present (marked `integration`, skipped otherwise).

- **A failed plate solve had no reason.** ASTAP exits non-zero with nothing on stderr when it can't solve — the reason ("Not enough stars.") is only in its `.ini` — so `failure_reason` was an empty string, defeating `PLT-050`'s "report failure distinctly". It now comes from the `.ini`, falling back to a message for ASTAP's documented exit codes. An `.ini` left by an earlier solve of the same frame can no longer be mistaken for the current one's. A solve that is cancelled or times out now stops ASTAP instead of leaving it running. Tests: `test_tc_plt_050_*`.

- **Solved rotation and pixel scale were wrong.** Rotation was `atan2(CD1_2, CD1_1)`, which reads ±180° for an ordinary north-up, east-left frame; it is now the angle of north from the top of the frame (0° for that case). Pixel scale was `|CD1_1|`, which shrinks as the frame is rotated (to nothing at 90°); it is now the true size of a pixel. Tests: `test_tc_plt_010_scale_and_rotation_survive_a_rotated_frame`.

- **The solver's downsample setting did nothing.** `PlateSolver` passed `-down N` to ASTAP, which is not an ASTAP option and is silently ignored; the real flag is `-z N`. `SolverParams.downsample` (`PLT-060`) now takes effect, so its default of 2 now really does halve the frame before solving. Test: `test_tc_plt_060_search_parameters_reach_astap`.

- **ASTAP is found when it is installed but not on `PATH`.** The Windows installer never puts it on `PATH`, so `PlateSolver` found nothing and every solve failed with "ASTAP executable not found". Several API details needed adapting rather than a literal port, all confirmed against the live Simbad service: the currently-installed astroquery already returns `ra`/`dec` as decimal degrees (Obsy's `SkyCoord` sexagesimal-string parse is for an older response format) and lowercase `main_id`/`otype` columns (Obsy's `MAIN_ID`/`OTYPE_main`); Obsy's unconditional `wildcard=True` now finds nothing for a plain name like `"M31"` against this Simbad backend (it only matches Simbad's own identifier spacing, e.g. `"M31*"`/`"M 31"`), so wildcard mode is now only used when the query itself contains a `*`/`?`, otherwise Simbad's normal alias-resolving lookup is used; and requesting the `V`/`FLUX_V` magnitude field on the same query as the name/type match — as both Obsy and this port's first pass did — silently drops *any* object with no cataloged V magnitude, which is most nebulae and clusters (a plain search for M42, M45, or "Orion Nebula" returned nothing at all, with no error, while M31 worked — the exact "only M31 ever comes back" symptom reported after the first pass), so magnitude is now a separate, best-effort per-object lookup capped to searches with 10 or fewer matches (avoiding an unbounded number of extra requests for a broad wildcard search) rather than part of the primary query. Also matched `AlpacaAdapter`/`SimbadClient`'s existing per-call `Simbad()` instance pattern rather than Obsy's global-singleton mutation.

### Fixed

- **Manual capture on an Alpaca camera failed with "There is no image available" (`ErrorNumber=1035`).** Alpaca's `startexposure` returns as soon as the exposure begins, but the adapter asked for `imagearray` straight afterwards — a third of a second into a 10 s exposure — so the driver had nothing to give. `AlpacaCameraAdapter.get_image_array` now waits, polling `imageready` every half second until the exposure has finished (it gives up with a clear error if the camera reports an error state, or if the image still isn't ready 60 s after the exposure should have ended), and the download's timeout is raised from 10 s to the exposure time plus 60 s, since the image arrives as a large JSON array. The result is also now a numpy array in `(height, width)` order — ASCOM sends columns first and the adapter used to return the raw nested list, which the preview, statistics and FITS-saving code (which call `.astype`) could not have used. This affects every caller: manual capture, autofocus, plate solving, calibration and the sequencer. INDI cameras already waited for their download and are unchanged. Tests: two new cases in `tests/test_eqp.py` (`TC-EQP-CAM-010`).
- **A device that can't be reached now logs one readable line instead of a Python traceback.** Starting Galileo with a powered-off or off-network device (e.g. a Seestar at `seestar.local`) dumped a ~30-line traceback ending in `RuntimeError: Could not resolve 'seestar.local' via mDNS…` for every device page that tried to connect.
