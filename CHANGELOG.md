- **Two Piers can now run genuinely simultaneous, independent Imaging captures, Autofocus runs and Plate Solves, with every Equipment/Imaging/Focus/Solve control following whichever Pier is currently selected.** Previously the whole UI layer modeled "the selected Pier" as a set of window-global singletons — one camera-adapter dict (`self._camera_backends`), one Mount/Focuser/Filter-Wheel/Rotator adapter slot, one `ImagingService`, one capture thread, one `AutofocusService`/`SolveWorkflow` — so switching Piers meant reconnecting everything from scratch, and starting a second capture on a different Pier while the first was still running would have silently corrupted both (confirmed: `ImagingService.capture_series` resets `self.library_ids` at the top of every call, so a second concurrent call would stomp the first's in-progress list). This was the same root cause already fixed once for Camera specifically (see the removed entry below) — the fuller fix generalizes the pattern `galileo/ui/guider.py`'s `GuiderPage` already used correctly (`self._services: dict` keyed by Pier, never torn down on switch) across the rest of the device/capture/focus/solve pipeline:

  - `galileo/ui/app_window/_imaging_page.py`: `self._imaging_services`/`self._imaging_capture_threads` (both `dict[pier_key, …]`) replace the single `ImagingService`/capture-thread slot. `do_capture()` resolves the current Pier's own service and refuses a second capture only on the *same* Pier; the per-capture signal handlers (`on_frame_done`, `on_capture_finished`, etc.) always update the service's own state but only repaint the shared preview/histogram/progress/buttons while that capture's Pier is still the one displayed. A new `self._device_pages["imaging"]` reload hook (the Imaging tab had none before) repaints those same widgets from whichever Pier's `ImagingService` is now current on every Pier switch — including mid-capture, so switching back to a Pier already running a series shows its progress immediately rather than a blank/idle page.

The Solve screen's results table and live preview deliberately stay a single shared/global log across all Piers (unchanged) — its own docstring already says it "shows every solve… not only the ones started from its own buttons," and existing tests (`test_tc_plt_070_shows_a_solve_started_elsewhere`) depend on that; only the target/error-offset attribution (`_on_solve_finished`) now looks up the *originating* Pier's own workflow via the event's `pier_key`, rather than whichever Pier happens to be on screen, so a backgrounded Pier's own run still gets its own target error filled in correctly.
  - The obstruction-check slew guard (`galileo/core/slew_guard.py`) was a single process-wide `SlewGuard`, overwritten with the current Observatory's horizon/site on every Pier switch (`_observatory_pier.py`'s `_apply_horizon()`) — so two Piers in *different* Observatories running concurrently would have had the wrong one silently checked against whichever Observatory was selected last, a safety-relevant gap for the meridian flip / Star Atlas Goto / plate-solve centring / sequencer routes that all funnel through it. `get_slew_guard()` now takes an optional Pier-key argument and lazily creates/returns a guard per key (defaulting to a shared fallback for callers with no Pier context, e.g. a freshly-constructed mount adapter before its first connect); `_mount_page.py` binds each connected adapter to its own Pier's guard, and `_apply_horizon()` writes to that Pier's guard specifically while still applying the single "Do not slew where obstructed" app setting to every guard that exists.

- **Live-stacking a mosaic capture now composites each pane into its own spot on a full-mosaic canvas, instead of only ever showing the one pane most recently exposed (`IMG-160`/`IMG-180`).** Previously, ticking Live Stack made no difference to a mosaic capture at all — each pane's own frame just replaced the last, the same as with it off. `MosaicStacker` (`galileo/livestack.py`) gives each pane its own `LiveStacker` (so repeat exposures of the same pane still register onto each other) and composites every pane's running result onto a canvas sized to the whole mosaic, at the grid position its pane index implies — spaced the same way `FramingAssistant.create_mosaic` placed the panes' sky positions (`pane size * (1 - overlap_pct / 100)`). `ImagingService.capture_mosaic` now composites from the very first exposure (no `LIVE_STACK_MIN_FRAMES` gate — a mosaic's point is the panes' geometry, not signal-to-noise on one pointing) and shows the composite as `current_frame`, so the existing pan/zoom preview's fit-to-window behaviour zooms out to the mosaic's full extent on its own, no separate UI change needed. `ImagingService.active_stacker` now picks whichever of the single-pointing stack or the mosaic composite currently holds frames, so Save Stack, frame counts and the capture summary all follow whichever one a given run actually built. Each pane's individual sub is still catalogued to the Library exactly as before; only the live preview and Save Stack's composite are new.
- **A Stretch slider above the Imaging tab's histogram (`IMG-190`)**, for a preview that a fixed 0.5%/99.5% percentile clip was leaving too high-contrast/washed-out on background-dominated frames — the fixed clip had no user control at all. `ImagingService.stretch_level` (0..100, `galileo/ui/imaging.py`) sets how much of each colour plane's tails `_auto_stretch` clips to black/white (0 .. 2.5% per tail) before stretching the rest to fill the display range. The clip range tried initially (0 .. 5% per tail, default reproducing the old fixed clip exactly) proved too coarse in hands-on testing — every useful setting sat within the first couple of clicks of the slider — so the range was halved and `DEFAULT_STRETCH_LEVEL` moved to the position testing found gave the best natural-looking preview on that finer scale. `ImagingService.set_stretch` mirrors `set_debayer`'s `rebuild` flag; the Imaging page (`galileo/ui/app_window/_imaging_page.py`) re-renders on the same worker thread as a debayer toggle, debounced 150 ms behind the slider so a drag gesture doesn't queue a render per pixel moved. Preview-only, same as the rest of `IMG-020`: the raw frame, its statistics/histogram and any saved file are untouched.
- **A Windows installer (`NFR-INSTALL-010`).** `Install-Galileo.bat` at the repo root is the one file a new user needs to download — double-clicking it fetches and runs the new `install/install.ps1`, which ensures Git and Python 3.11+ are available (offering a silent per-user install of either if missing — Git via `winget` when present, otherwise the latest Git for Windows release looked up from GitHub), clones the repo (or updates an existing checkout), creates `.venv`, installs `requirements.txt`, and creates a desktop shortcut set to open minimized (`WindowStyle = 7`), so the update-check console the shortcut launches doesn't steal focus on every start — the Galileo window itself opens normally regardless. Because that console is minimized, `launch_galileo.bat`/`.ps1` no longer `pause`/`Read-Host` on an error (virtual environment missing, Galileo exiting non-zero) — a keypress prompt nobody can see would just leave the window stuck open forever; both now append a timestamped line to `%APPDATA%\Galileo\logs\launcher.log` and exit instead. Deliberately not a frozen/Nuitka-style monolithic executable (`docs/SDD.md`'s planned MSI packaging is a separate, later effort) — updates instead work the way the author's AstroFiler installer already does and has proven out: the desktop shortcut's target, `install/launch_galileo.bat` (and its PowerShell twin `launch_galileo.ps1`), checks for and applies updates via git on every launch, falling back to a no-op with a warning rather than discarding anything if the install directory has local changes. `install/upgrade.ps1` covers the manual "update now without starting the app" case with the same git-pull-plus-dependency-refresh approach, in its own console window with a completion dialog. `install/README.md` documents how the pieces fit together. macOS/Linux installers remain future work (`TODO.md`); `run.sh`/`run.ps1` (unchanged) still cover running from a manual checkout everywhere.

### Fixed

- **Autofocus HFR readings were about 10x too small, so the Focus screen's V-curve plotted everything hugging the bottom axis instead of scaling to the actual star sizes.** `galileo/autofocus.py`'s `_measure_stars` computed HFR via `sep.flux_radius` — a curve-of-growth radius (the radius enclosing 50% of a star's total flux out to a bounded search window) — which isn't the same measurement classic autofocus software reports, and came out much smaller for a defocused, near-uniform "donut" star profile. Replaced it with the standard HFD/HFR algorithm from lost-infinity.com's write-up: for each detected star, HFR = Σ(Vᵢ·dᵢ)/ΣVᵢ, the flux-weighted mean distance of background-subtracted (and floored-at-zero) pixels from the centroid out to an outer aperture sized off the star's own SEP shape fit. `_compute_hfr`/`_compute_regional_hfr` (the Aberration Inspector) pick up the same fix automatically since they call through `_measure_stars`. No test changes needed — `test_tc_nfr_perf_020_ui_responsive_during_background_ops`'s `1.0 < hfr < 5.0` sanity check on synthetic Gaussian stars already covered this and still passes, since the two formulas happen to agree closely for a Gaussian profile; the divergence was specific to real, non-Gaussian star shapes.
- **Library > Images didn't show frames that arrived while it was hidden.** It only reloaded after a capture started from the Imaging tab. Frames registered any other way, such as a Session run, a download or another Pier, stayed invisible until the next restart or a change of sort or filter. The Images screen now checks the catalog every time it's shown, including when you click the Library icon, and reloads if the file count or soft-delete count has changed. When nothing has changed, it doesn't reload, so the tree's expanded groups stay as they were. Test: `test_library_images_screen_refreshes_when_reopened_after_new_frames` (TC-LIB-010).
- **Switching Piers left the Imaging tab (and Focus/Plate Solve) still capturing from the previous Pier's camera**, even once the Camera page's fields and top-bar selector visibly showed the new Pier's configured device — `self._camera_backends` was a single window-global dict keyed only by slot label, so the old Pier's adapter survived under the same key. Superseded the same day by the broader per-Pier fix above, which makes `_camera_backends` genuinely per-Pier instead of clearing-and-reconnecting on every switch.
- **`install/launch_galileo.bat`/`.ps1` could self-corrupt into a permanently "locally modified" state, blocking every future `git pull` in that install with `error: Your local changes to the following files would be overwritten by merge` — without the user ever having touched either file.** Both scripts do their own auto-update (`git fetch` + `git reset --hard origin/main`) on every launch, including of the very file currently executing them; a running `.bat` (and, less reliably, a running `.ps1`) reads itself from disk incrementally rather than fully upfront, so rewriting it mid-execution risks the interpreter resuming from the wrong position in the new content — a classic self-modifying-script hazard on Windows, and the actual mechanism behind at least one report of this. Fixed by splitting each launcher into a thin, essentially-frozen-going-forward stub that does only the update check (`launch_galileo.bat`/`.ps1`), plus a new `run_galileo.bat`/`.ps1` holding everything that actually changes release to release (venv check, app launch, error logging) — invoked only *after* the update check completes, so it's never open while `git reset --hard` runs and can change freely without risk. Desktop shortcuts still target `launch_galileo.bat` unchanged; existing installs affected by this recover with a one-time `git restore install/launch_galileo.bat install/launch_galileo.ps1 && git pull`. `install/README.md` updated to describe the split.
- **`install/install.ps1` failed with `The term 'p' is not recognized...` (and cascading `python.exe is not recognized` errors) whenever Python was resolved via the plain `python`/`python3` command rather than the `py -3.11` launcher.** `Resolve-Python` returns a one-element array (`@($cmd)`) in that case, but PowerShell unwraps a function's single-object pipeline output on assignment, so `$PythonCmd` ended up a bare string (e.g. `"python"`) instead of an array. `Invoke-Py`'s `$script:PythonCmd.Length -gt 1` check then read the string's *character count* (6, always `-gt 1`) rather than an element count, and indexed it as characters — `$script:PythonCmd[0]`/`[1]` became `'p'`/`'y'`, so it tried to run a nonexistent `p` command. This silently skipped venv creation, which meant every following step (`pip install --upgrade pip`, installing `requirements.txt`) also failed with "python.exe is not recognized" since the venv was never created. Fixed by forcing array semantics in `Invoke-Py` via `@($script:PythonCmd)` before checking `.Length`/indexing, which is correct regardless of whether Resolve-Python's return value got unwrapped. Reproduced and verified against both the one-element (`python`) and two-element (`py -3.11`) resolution paths.
- **`assets/images/galileo.ico` was raw PNG data (1024×1024) wearing an `.ico` extension, not an actual ICO container** — Explorer can't parse PNG as an icon resource, so the installer's desktop shortcut (`install/install.ps1`, which points `IconLocation` at this file) silently fell back to a generic icon instead of Galileo's. Regenerated the file in place from the same artwork as a real multi-resolution ICO (16/24/32/48/64/128/256 px, via Pillow) — same source image, now actually readable as an icon; dropped from 1.8 MB to ~200 KB in the process. `galileo/app.py`'s `main()` also now calls `app.setWindowIcon(QIcon(...))` against this file, which it never did before, so the running app's own window/taskbar icon matches the shortcut instead of falling back to Qt's default. A desktop shortcut created before this fix keeps showing the generic icon until it's recreated (re-run `install/install.ps1`) or the Windows icon cache is refreshed, since Explorer caches per-shortcut icons.
- **mypy's `attr-defined` findings across `galileo/ui/*` were dominated by PySide6 enum stub noise**, drowning out real bugs (CODE_REVIEW.md Finding 11). PySide6 6.11's stubs only expose enum members under their nested enum class (e.g. `Qt.AlignmentFlag.AlignCenter`) even though the flat, un-nested spelling (`Qt.AlignCenter`) still works at runtime — this accounted for 220 of the 623 project-wide mypy errors, spread across 27 UI files, several of which also had real, unrelated `attr-defined` bugs (e.g. `DeviceBackend.list_available_devices`, `sessions.py`'s `Callable[[], QScreen]` calls) sitting in the same noisy output. Rewrote every flat Qt/PySide6 enum reference project-wide to its nested spelling (`Qt.AlignCenter` → `Qt.AlignmentFlag.AlignCenter`, `QDialogButtonBox.Ok` → `QDialogButtonBox.StandardButton.Ok`, etc. — `QHeaderView`, `QFrame`, `QAbstractItemView`, `QMessageBox`, `QDialog`, `QPainter`, `QSizePolicy`, `QImage`, `QGraphicsView`, `QFileDialog`, `QFontDatabase`, `QFormLayout`, `QLineEdit`, `QPlainTextEdit` also affected), derived from PySide6's own `.pyi` stubs rather than guessed. Purely a typing fix — nested and flat spellings are the same runtime value in PySide6 — verified via `python -c "import py_compile"` over every changed file, a before/after mypy diff showing zero new error messages of any kind (only the 220 Qt-enum lines disappeared), identical `ruff check` counts before/after, and a full `pytest` run showing the same pre-existing failures as before (see below) with no new ones. Brings project-wide `mypy . --ignore-missing-imports` from 623 to 404 errors, leaving `galileo/ui/*`'s remaining mypy output actually worth reading.
- **`Observatory` had no `contact_details` attribute**, so `test_tc_obs_090_observatory_carries_operator_contact_details` (`tests/test_obs.py`) failed at `obs.contact_details is None` — the class's `__init__` never set the attribute and had no `set_contact_details` method, even though `ContactDetails` (OBS-090) was already defined in `galileo/observatory.py`. Fixed by initializing `Observatory.contact_details = None` and adding `Observatory.set_contact_details(email=, phone_number=, channels=)`, which builds and stores a `ContactDetails` instance — one per Observatory, not per Pier, matching NOTIF-040's design of reading the operator's contact info from the owning Observatory rather than per-Pier or per-notification config.
- **Several Equipment/Options/Framing form fields (QComboBox/QLineEdit) were squeezed to a few characters wide on macOS only** — worst on Camera and Focuser's Device selector, where the device name was unreadable, but present anywhere a form field was placed via `QFormLayout.addRow(...)` without an explicit stretch. Cause: `QFormLayout`'s field growth policy default is platform-dependent (`AllNonFixedFieldsGrow` on Windows/Linux, `FieldsStayAtSizeHint` on macOS), so only Mac ever pinned these fields to their tiny size hint instead of filling the row — pages using a `QHBoxLayout` with a stretch factor for the same kind of row (Mount, Filter Wheel, Rotator) were never affected. Fixed by routing every affected form through a new `_new_form_layout()` helper (`galileo/ui/app_window/_common.py`) that pins the policy to `AllNonFixedFieldsGrow` explicitly: Camera and Focuser's Device panels, the Framing Assistant dialog, the Optics page's tube panel, the New Observatory dialog, the Imaging tab's Capture Settings/View groups, the Planning page's criteria panel, and the Imaging Settings options page's BITPIX combo. Forms whose fields are read-only status `QLabel`s (e.g. the Imaging tab's Statistics group) or fixed-size spin boxes were left as plain `QFormLayout()`, since the policy doesn't affect them either way.

### Changed

- **Removed the Imaging tab's Statistics group** (mean/median/min/max/star count/HFR labels) from the settings panel — it duplicated numbers already visible via the star overlay and histogram, and per-frame values that go stale between captures sat awkwardly next to live controls. `ImagingService.get_frame_stats()` (`IMG-040`) is unchanged and still independently tested (`tests/test_img.py`); only the UI labels that mirrored it are gone.
- **The Imaging, Guiding and Focus screens now share the Solve screen's Fit / 1:1 / + / − preview toolbar**, in the same top-right spot above their frame view, instead of each screen having its own (or no) view controls. Added `galileo/ui/_image_view.py` (`ImagePreviewView`, a pan/zoom `QGraphicsView`, plus `build_zoom_toolbar()`) and rebuilt `SolveImageView` (`galileo/ui/solve.py`), the Imaging tab's live preview (`galileo/ui/app_window/_imaging_page.py`), `StarView` (`galileo/ui/guider.py`) and `FocusImageView` (`galileo/ui/focus.py`) on top of it, so all four now fit-to-window until the user zooms and support drag-to-pan, where three of them previously always auto-fit with no zoom or pan at all. On the Imaging tab this replaces the old View group's `Zoom` spinbox and `Reset View` button, which drove the preview's scale directly and didn't support panning; `ImagingService.set_zoom`/`reset_view` (`IMG-060`) are unchanged and still independently tested (`tests/test_img.py`), just no longer wired to the removed controls.
- **The changelog is split so it no longer dominates the context window of anyone (or any tool) reading it.** `CHANGELOG.md` had grown to ~250 KB in one `[Unreleased]` section, so every edit to it meant loading the whole history. All existing entries moved verbatim to [`docs/changelog/2026-09.md`](docs/changelog/2026-09.md); this file now holds only new entries, with a rotation rule (above) for when it grows again. `CLAUDE.md`, `CONTRIBUTING.md`, `TODO.md` and the VSTarget PSD now point at the archive where they cite past entries.
- **`galileo/ui/app_window.py` (a single ~7,900-line file, one `AppWindow` class) is now the package `galileo/ui/app_window/`, split into 22 files along the module's own pre-existing section comments (one file per page/concern — Camera page, Mount page, Imaging page, Framing Assistant, etc.), with `AppWindow` reassembled from mixins in `__init__.py`.** The file's size was itself a maintainability problem, independent of any single bug: window chrome, every device-category dialog, and Pier/Observatory CRUD were all in one module, and it accounted for over a third of the project's mypy findings by sheer bulk, burying the real bugs in there under noise. No behavior changed — this is a pure move, verified via `python -c "import galileo.ui.app_window"`, `ruff check galileo/ui/app_window/` (same pre-existing findings as before, none new), and the full set of `tests/test_*.py` files that exercise `AppWindow` (`test_driver_info`, `test_eqp`, `test_focus_page`, `test_guider_page`, `test_img`, `test_lib`, `test_optics_page`, `test_rotator_page`, `test_sched`, `test_sky`, `test_solve_page`, `test_star_atlas`) still passing. Splitting one class across files created a real mypy wrinkle — each mixin, checked alone, can't see that it'll share `self` with every other mixin once combined — fixed via a generated `Protocol` (`_state.py`) applied as an explicit `self: AppWindowState` type per mixin method (mypy's own documented pattern for mixin classes, no runtime effect). Net result: project-wide `mypy . --ignore-missing-imports` went from 623 errors to 620 — a net improvement, not the regression a naive per-file split would have been. Found by CODE_REVIEW.md (Finding 9); verified via mypy/ruff/pytest as above.
- **Every live/interactive time-of-day display now shows the system's local time instead of UTC.** The Star Atlas page's time field was a `QDateTimeEdit` pinned to `Qt.TimeSpec.UTC` and labeled "Time (UTC)"; it's now `Qt.TimeSpec.LocalTime` and labeled "Time (Local)" (`galileo/ui/app_window/_star_atlas_page.py`) — the underlying `StarAtlasView.when`/`set_time` (`galileo/ui/star_atlas.py`) are untouched, since astronomical position calculations still need UTC internally, only the widget's display/edit conversion moved. The Scheduler's per-job altitude-trajectory chart (`_AltitudeChart`, `galileo/ui/scheduler.py`, SCHED-080 — also reused by the Sky Atlas page's per-result cards) converts its naive-UTC time-axis tick labels to local before formatting. The Planning page's rise/transit/set text (`_fmt_rise_set_time`, `galileo/ui/app_window/_planning_page.py`) does the same and drops the now-inaccurate trailing "UTC" it used to append. The Rotator page's live clock (`galileo/ui/app_window/_rotator_page.py`) switched from `datetime.now(UTC)` labeled "UTC" to `datetime.now()` labeled "Local". Deliberately unchanged: FITS `DATE-OBS`/filename timestamps and other on-disk/recorded metadata, which stay UTC per FITS convention and aren't user-facing "what time is it" displays; `ObservingLocation.timezone` (currently unused metadata, still defaults to `"UTC"`).
