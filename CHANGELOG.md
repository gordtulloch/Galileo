# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). This project does not yet follow Semantic Versioning releases (see `README.md` status) — entries accumulate under `[Unreleased]` until the first tagged release.

**Older entries are archived in [`docs/changelog/`](docs/changelog/)**, one file per rotation (e.g. [`2026-09.md`](docs/changelog/2026-09.md)), so this file stays short enough to read in full. Search the archives (`grep -rn <term> docs/changelog/`) rather than reading them end to end. When this file grows past roughly 40 KB, move everything under `[Unreleased]` to the top of the current month's archive file (creating `docs/changelog/YYYY-MM.md` if needed) and leave `[Unreleased]` empty again.

## [Unreleased]

### Added

- **A new Flats… button on the Imaging tab opens the Flats Assistant dialog, and its Sky Flats method is now a real, working capture routine (`CAL-070`).** The dialog (`galileo/ui/app_window/_flats.py`, a new `AppWindowFlatsMixin`) offers Flat Method (Sky Flats / Observatory Panel / Flat Panel — only Sky Flats runs a real capture; the other two explain they aren't wired up yet), Exposure (blank to calculate), Number of Frames, Filter (with an All option that repeats the run across every filter in the wheel, `CAL-020`), an Average/Median ADU Method, and an Exposure Increment (default 0.1 s). Sky Flats itself (`CalibrationService.run_sky_flats`/`run_sky_flats_all_filters`, `galileo/calibration.py`) refuses to start outside the local dawn/dusk twilight window (new `galileo.planning.visibility.is_twilight`/`sun_altitude_deg`, 0° to -18° solar altitude), then slews the mount to a fixed East, high-altitude vantage point away from bright stars and turns tracking off (new `altaz_to_radec_deg` converts that fixed direction to the moment's RA/Dec) so any star in frame trails into a faint streak instead of biasing the ADU reading. One convergence loop measures each frame's average/median ADU and adjusts the exposure toward 50% of the camera's Max Well Depth (the field added below, used here for the first time), re-checking and retaking every frame — not just the first — since twilight brightness keeps drifting; the adjustment step is ratio-based but floored at one Exposure Increment so it can't stall near zero. Runs off the Qt UI thread (`_FlatsThread`, mirroring `_CaptureThread`) with a Stop button (`CalibrationService.request_stop`, checked between exposures/filters, never mid-exposure) and a close-refusing dialog while a run is active, so its live-progress signal handlers are never left firing against a destroyed window. Every frame Sky Flats captures is now also submitted straight to the Library as it's saved (`CalibrationService._register_with_library`, calling `LibraryRegistrar.register_capture` — the same call a manual Imaging-tab capture uses), which needed `_save_frame` to start writing a `DATE-OBS` header too, since the Library's ingest validator requires one and none of `CalibrationService`'s writers had ever supplied it. `docs/SRS.md`/`SDD.md`/`RTM.md` gain `CAL-070`.
- **The Equipment > Camera page gains a Max Well Depth field, right below Bayer pattern.** A per-camera, hand-entered full-well capacity in electrons (`device_configs.max_well_depth`, new migration `018_add_camera_max_well_depth.py`, nullable/unset by default like `pixel_size_um`), saved/loaded exactly like the existing camera fields via `save_device_config`/`get_device_config` (`galileo/observatory.py`). Now used by the new Flats Assistant's Sky Flats target-ADU calculation (`CAL-070`, above).
- **The What's Up Tonight screen gains a day/night graphic across the top (`WUT-110`), showing the Night/Astronomical/Nautical/Civil Twilight/Daylight periods for the selected observing date and location.** A new pure function, `galileo.planning.visibility.day_night_bands()` (built on a new `sun_altitude_track()`, a single vectorized-astropy Sun-altitude sample across one local calendar day, the same batching technique `altitude_charts_batch` already uses), splits the day into contiguous segments by the Sun's altitude against the standard sunrise/civil/nautical/astronomical thresholds, each boundary linearly interpolated between samples the same way `rise_transit_set` already interpolates horizon crossings, plus the day's solar noon/midnight. A new self-painted `_DayNightBandChart` widget (`galileo/ui/app_window/_widgets.py`) renders the band with an hour axis and solar noon/midnight tick marks, using a single-hue sequential color ramp (dark navy through pale blue) so the ramp itself reads as "darker = closer to true night"; a legend below it (plain `QLabel`s, `galileo/ui/app_window/_whats_up_page.py`) names each segment, its clock-time range(s) — a label can recur, e.g. Night before dawn and again after dusk — and its total duration. Recomputes independently of the Rank Tonight button, on every observing-date change, since it reflects the date/location alone rather than the magnitude/altitude/catalog ranking criteria. `docs/SRS.md`/`SDD.md`/`RTM.md` gain `WUT-110`; `tests/test_wut.py` gained 4 new tests (`TC-WUT-110`) covering segment contiguity/24-hour coverage, the expected label cycle, solar noon/midnight as the altitude extremes, and graceful degradation with no Sun-altitude data.

### Changed

- **The Imaging tab's Framing… button moved from the left settings panel up into the toolbar above the preview, beside Annotate.** Previously Framing… sat in its own row next to Clear Mosaic in the capture-settings column; Clear Mosaic stays there (now on its own, visibility-toggled as before), while Framing… joins Annotate at the top of the preview since both open a dialog against the displayed/selected frame rather than configuring a capture.


- **The Imaging tab's Framing Assistant dialog replaces its Load Sky Image button with Determine Rotation (`FRAME-100`), and pre-fills the rotation field wherever it's already known.** Previously the rotation field always started at 0° and had to be typed in by hand even when a rotator was already sitting at a known angle or the frame had already been plate-solved. The dialog now reads a connected rotator's live position (`RotatorPort.get_status()["position"]`) or the Imaging tab's own last plate-solve result (`ImagingService.last_solve`, shared with Annotate, `IMG-200`) and pre-fills the rotation spin box from whichever is available, showing which source it came from. Determine Rotation is only needed when neither applies: it plate-solves the Imaging tab's current frame (off the Qt UI thread, via a new `_DetermineRotationThread` mirroring `_AnnotateThread`) and sets the rotation field from the solution's position angle, which then rotates the canvas's FOV rectangle exactly as a manually-typed rotation would. The survey-image fetch that button used to trigger now happens on the RA/Dec fields' `editingFinished` instead (still not on every keystroke, to avoid a network call per edit) plus on dialog open when a target was already picked on the Star Atlas. New `ImagingService.solve_current_frame()` factors the write-temp-FITS-and-solve plumbing out of `annotate_current_frame()` so both features share it. `docs/SRS.md`/`SDD.md`/`RTM.md` gain `FRAME-100`. Also fixed `_FramingCanvas.paintEvent` (`galileo/ui/app_window/_widgets.py`) computing separate degrees-per-pixel scales for its X and Y axes — the survey image and FOV/mosaic rectangles stretched non-uniformly as the dialog was resized to an aspect ratio that didn't match the field's own, since each axis was independently fit to the widget's current width/height. Now derives one shared scale (the smaller of the two, letterboxing rather than stretching) so the image and overlay always keep their true proportions. The dialog also now opens at double its natural (layout-driven) size, so the canvas isn't cramped into a sliver from the start.
- **Every Planning > Sessions block now opens its own parameter dialog directly on right-click, closing the long-tracked gap that the Image block's exposure/count/filter/binning/gain/offset had no UI at all and its Framing… control was a no-op stub (`SES-130`).** New module `galileo/ui/session_block_dialogs.py`: a small `QDialog` per block type that has any dataclass fields (Target's name/RA/Dec, Image's exposure/count/filter/binning/gain/offset/frame-type, Filter Change's filter, Cool Camera's setpoint, Autofocus's filter override, Guide Start's calibrate flag, Flat Capture's count/target ADU, Notification's message) — a block with no fields at all (Dither, Park/Unpark Mount, Meridian Flip, Dome Open/Close/Sync, Guide Stop, Warm Camera, Plate Solve) does nothing on right-click instead of opening an empty dialog, and so does a block in a scheduled (locked) session. Wired via `BlockListWidget._on_right_click` (`galileo/ui/sessions.py`, a `customContextMenuRequested` handler) — right-click opens the dialog immediately with no intermediate context menu, since editing parameters is the only thing a right-click here does; dragging from the palette still only ever creates a block at its dataclass defaults. The Image block's dialog also gets a real **Framing / Mosaic…** button, which now actually calls `galileo.planning.framing.open_from_session_image_block` (previously logged and did nothing) and builds a genuine `Mosaic` via the same `FramingAssistant.create_mosaic`/`mosaic_footprint_deg`/`compute_fov` calls the Imaging tab's own Framing dialog uses — independent state per `docs/SDD.md` §4.9's "one design, two callers" note, with no rotator control (an `ImageBlock` has no rotation field) and no survey-image preview (kept intentionally smaller than the Imaging tab's dialog). `docs/SDD.md` §4.6a and `TODO.md` updated to describe the built state instead of the tracked gap. `tests/test_ses.py` gained 8 new tests: `has_parameters` block-type gating, an Image block's field round-trip through its dialog, the Framing button building a real mosaic end to end, the no-menu direct-open behavior for parameter-bearing vs. parameterless blocks, and the locked-session no-op case.
- **Dragging a Plate Solve block onto a session with no Target block yet was silently refused (`SES-170`'s existing ordering rule — a Plate Solve needs a preceding Target — was working as designed, but looked indistinguishable from the block simply "not being placeable").** `BlockListWidget.dropEvent` now shows a `QMessageBox` warning with the actual `BlockOrderError` text, in addition to the existing status-label update, so the rejection is impossible to miss; the Plate Solve (and any future `_REQUIRES_TARGET`) palette tile also gets a tooltip stating the requirement up front. New test `test_dropping_a_block_that_violates_ordering_shows_a_visible_warning`.
- **Dragging a block out of every session panel (the palette and every region's own block list) now deletes it.** New `SessionRegion.remove_block()` (refused, like every other authoring mutation, on a scheduled/locked region) and a `BlockListWidget.startDrag` override: today's default Qt behavior for a drag nothing accepts is to just leave the source list untouched, which gave no way to remove a block once dropped — now, once the drag ends in `Qt.DropAction.IgnoreAction` (nothing accepted it) *and* the release point is outside every `BlockListWidget`/the palette (`_is_outside_every_session_panel`, so an unsupported cross-region drop still just does nothing rather than deleting the block), the block is removed from its region and a locked-region attempt shows a warning instead of silently doing nothing. New tests: `test_remove_block_deletes_it_and_refuses_on_a_locked_region` (model level), `test_dragging_a_block_outside_every_session_panel_deletes_it`, `test_dragging_a_block_onto_another_region_does_not_delete_it`, `test_dragging_a_block_out_of_a_locked_session_shows_a_warning`.
- **Session block colours were reported as "far too bright" — every block type now keeps a fixed colour identity blended into whichever theme is active, instead of an independently saturated, glaring tile.** `_block_color` (`galileo/ui/sessions.py`) previously hashed each class name straight into `QColor.fromHsv(hue, 150, 210)` — fully saturated regardless of theme. Now every built-in block type has a fixed hue (`_BLOCK_HUES`, evenly spaced, still falling back to a hash-derived hue for an unrecognized/plugin-registered type so new block types keep getting one for free) which a new `ThemeManager.block_tint_rgb(hue_deg)` (`galileo/ui/theme.py`) blends lightly into the *active* theme's own surface tone rather than showing at full brightness — so a block reads as a subtle variation of Light/Dark, not a colour-wheel sticker, and switching themes changes its tint too, since colour is now resolved through the window's own `ThemeManager` (threaded down through `_build_palette`/`BlockListWidget`/`_RegionWidget`) instead of a theme-blind hash. Theme.RED (night vision, `UI-011`) is special-cased inside `block_tint_rgb` to vary only red-channel intensity, never introducing a green/blue pixel, preserving that theme's existing invariant. Palette/block tile borders also switched from a hardcoded 2px white border to a 1px theme-border-colour outline, for the same "less glaring" reason. `tests/test_ses.py` gained 2 new tests confirming colour consistency/muting and the night-vision red-only invariant.

- **An Annotate control above the Imaging tab's preview (`IMG-200`) labels catalogued stars and deep-sky objects on the displayed frame, and Save Frame/Save Stack can now save that labelled view.** New domain-core module `galileo/annotate.py`: plate-solves the displayed frame (via the same `PlateSolver`/Options > Solver configuration the Solve screen uses) and projects Galileo's bundled star (`galileo.planning.star_atlas`) and DSO (`galileo.planning.sky_atlas`) catalogs onto it through a tangent-plane projection built from the solve's centre/rotation/scale, drawing a circle, leader line and label at each match with Pillow — the same overlay layout [astronotation](https://gitlab.com/abonengo/astronotation) (MIT licence) draws from astrometry.net's web-service annotations, reused here for the rendering technique so Annotate works fully offline against Galileo's own local solve instead of an uploaded-image/job-ID round trip. This is the actual working overlay renderer the retired `IMG-050` star-overlay checkbox never had — built specifically so this feature isn't shipped the same half-connected way again. While Annotate is on, Save Frame and Save Stack (`IMG-210`) write the annotated view as a PNG in place of the raw FITS they otherwise save; the Library — both auto-save-to-library during a capture and Save Stack > Save to Library (`IMG-220`) — always registers the raw frame/stack and never reads Annotate's state at all, so an annotated image structurally cannot reach the repository. `docs/SRS.md` gains `IMG-200`/`IMG-210`/`IMG-220`; `docs/SDD.md` gains Section 4.5a (`galileo.annotate`); `docs/RTM.md` gains the matching `TC-IMG-200`/`210`/`220` rows. `tests/test_img.py` gained 12 new tests covering the projection/catalog filtering, the overlay renderer, the solve-and-annotate flow (including a failed solve leaving no stale overlay), PNG-vs-FITS save behavior, and — the requirement this feature exists to guarantee — that an annotated frame never ends up in the Library regardless of how it got there.

Every color token in `Theme.RED`'s palette (`galileo/ui/theme.py`) is constrained to `#RR0000` — green and blue channels held at `0x00` — since a stray white/blue/green pixel is what actually resets a dark-adapted eye, not brightness alone. `ThemeManager.accent_color` also forces a fixed red accent while this theme is active, overriding the user's saved accent preference (`UI-030`) rather than reading it through, since a picked accent (the default teal, or anything else) is not guaranteed red and would otherwise leak a non-red pixel into the sidebar icons/histogram accent/buttons. `docs/SRS.md`/`SDD.md`/`RTM.md` updated (`UI-011`, P2 — already covered at scope level by `docs/PSD.md`'s existing `UI` domain entry, no PSD change needed); `tests/test_ui.py` gained two tests (`TC-UI-011`) covering theme selection and that no palette token or the accent carries a green/blue component.

A `_loading_settings` guard around `reload()`'s own `setValue` calls stops that from re-saving what it just loaded, and — importantly — stops a plain Pier switch from ever writing a fresh row of *default* values for a Pier that has never been saved. Three new tests in `tests/test_focus_page.py` cover direct-edit persistence across a Pier switch, live sync with Options > Focus, and the no-spurious-write guarantee.

- **Two Piers can now run genuinely simultaneous, independent Imaging captures, Autofocus runs and Plate Solves, with every Equipment/Imaging/Focus/Solve control following whichever Pier is currently selected.** Previously the whole UI layer modeled "the selected Pier" as a set of window-global singletons — one camera-adapter dict (`self._camera_backends`), one Mount/Focuser/Filter-Wheel/Rotator adapter slot, one `ImagingService`, one capture thread, one `AutofocusService`/`SolveWorkflow` — so switching Piers meant reconnecting everything from scratch, and starting a second capture on a different Pier while the first was still running would have silently corrupted both (confirmed: `ImagingService.capture_series` resets `self.library_ids` at the top of every call, so a second concurrent call would stomp the first's in-progress list). This was the same root cause already fixed once for Camera specifically (see the removed entry below) — the fuller fix generalizes the pattern `galileo/ui/guider.py`'s `GuiderPage` already used correctly (`self._services: dict` keyed by Pier, never torn down on switch) across the rest of the device/capture/focus/solve pipeline:

### Fixed

- **Dragging a Plate Solve block onto a session that already had a Target block still failed `SES-170`'s "requires a preceding Target" check, even when dropped after it.** `BlockListWidget.dropEvent` computed the insertion row from `indexAt(event.pos()).row()` alone, always treating a hover over an existing row as "insert before this row" regardless of where in that row the pointer actually was. With the block list's height fit tightly to its content (`_fit_height_to_contents`), there's no empty space below the last row to drop into for "append after" — so any drop onto the session's only (Target) row, even one aimed at its lower half, was read as "insert before the Target," failing the ordering check even though a Target block was right there. `dropEvent` now checks which half of the hovered row's own rect (`visualRect`) the drop's y-coordinate falls in, inserting after the row instead of before it when the pointer is in the lower half — fixing this for any block, not just Plate Solve. New test `test_dropping_plate_solve_after_an_existing_target_block_succeeds`.
- **The Targets and What's Up Tonight pages' "Catalog" checkboxes (Messier/Caldwell/NGC) overlapped/clipped instead of showing three separate, readable checkboxes.** Both pages laid the three out side by side in a `QHBoxLayout`, but the shared criteria panel (`_build_criteria_panel`) is a fixed 260px wide and its form now uses the `AllNonFixedFieldsGrow` field policy (see the macOS form-field-width fix above), which forces that row's field widget to the panel's own narrow width — nowhere near enough for three checkboxes' indicators plus label text (e.g. "Caldwell") abreast, so they ran past the edge and painted over the row below. Changed to a `QVBoxLayout` (one checkbox per line, 2px spacing) on both pages, matching the Star Atlas page's own catalog-toggle list, which already used this layout for the same reason.
- **Autofocus HFR readings were about 10x too small, so the Focus screen's V-curve plotted everything hugging the bottom axis instead of scaling to the actual star sizes.** `galileo/autofocus.py`'s `_measure_stars` computed HFR via `sep.flux_radius` — a curve-of-growth radius (the radius enclosing 50% of a star's total flux out to a bounded search window) — which isn't the same measurement classic autofocus software reports, and came out much smaller for a defocused, near-uniform "donut" star profile. Replaced it with the standard HFD/HFR algorithm from lost-infinity.com's write-up: for each detected star, HFR = Σ(Vᵢ·dᵢ)/ΣVᵢ, the flux-weighted mean distance of background-subtracted (and floored-at-zero) pixels from the centroid out to an outer aperture sized off the star's own SEP shape fit. `_compute_hfr`/`_compute_regional_hfr` (the Aberration Inspector) pick up the same fix automatically since they call through `_measure_stars`. No test changes needed — `test_tc_nfr_perf_020_ui_responsive_during_background_ops`'s `1.0 < hfr < 5.0` sanity check on synthetic Gaussian stars already covered this and still passes, since the two formulas happen to agree closely for a Gaussian profile; the divergence was specific to real, non-Gaussian star shapes.
- **Library > Images didn't show frames that arrived while it was hidden.** It only reloaded after a capture started from the Imaging tab. Frames registered any other way, such as a Session run, a download or another Pier, stayed invisible until the next restart or a change of sort or filter. The Images screen now checks the catalog every time it's shown, including when you click the Library icon, and reloads if the file count or soft-delete count has changed. When nothing has changed, it doesn't reload, so the tree's expanded groups stay as they were. Test: `test_library_images_screen_refreshes_when_reopened_after_new_frames` (TC-LIB-010).
- **Switching Piers left the Imaging tab (and Focus/Plate Solve) still capturing from the previous Pier's camera**, even once the Camera page's fields and top-bar selector visibly showed the new Pier's configured device — `self._camera_backends` was a single window-global dict keyed only by slot label, so the old Pier's adapter survived under the same key. Superseded the same day by the broader per-Pier fix above, which makes `_camera_backends` genuinely per-Pier instead of clearing-and-reconnecting on every switch.
- **`install/launch_galileo.bat`/`.ps1` could self-corrupt into a permanently "locally modified" state, blocking every future `git pull` in that install with `error: Your local changes to the following files would be overwritten by merge` — without the user ever having touched either file.** Both scripts do their own auto-update (`git fetch` + `git reset --hard origin/main`) on every launch, including of the very file currently executing them; a running `.bat` (and, less reliably, a running `.ps1`) reads itself from disk incrementally rather than fully upfront, so rewriting it mid-execution risks the interpreter resuming from the wrong position in the new content — a classic self-modifying-script hazard on Windows, and the actual mechanism behind at least one report of this. Fixed by splitting each launcher into a thin, essentially-frozen-going-forward stub that does only the update check (`launch_galileo.bat`/`.ps1`), plus a new `run_galileo.bat`/`.ps1` holding everything that actually changes release to release (venv check, app launch, error logging) — invoked only *after* the update check completes, so it's never open while `git reset --hard` runs and can change freely without risk. Desktop shortcuts still target `launch_galileo.bat` unchanged; existing installs affected by this recover with a one-time `git restore install/launch_galileo.bat install/launch_galileo.ps1 && git pull`. `install/README.md` updated to describe the split.
- **`install/install.ps1` failed with `The term 'p' is not recognized...` (and cascading `python.exe is not recognized` errors) whenever Python was resolved via the plain `python`/`python3` command rather than the `py -3.11` launcher.** `Resolve-Python` returns a one-element array (`@($cmd)`) in that case, but PowerShell unwraps a function's single-object pipeline output on assignment, so `$PythonCmd` ended up a bare string (e.g. `"python"`) instead of an array. `Invoke-Py`'s `$script:PythonCmd.Length -gt 1` check then read the string's *character count* (6, always `-gt 1`) rather than an element count, and indexed it as characters — `$script:PythonCmd[0]`/`[1]` became `'p'`/`'y'`, so it tried to run a nonexistent `p` command. This silently skipped venv creation, which meant every following step (`pip install --upgrade pip`, installing `requirements.txt`) also failed with "python.exe is not recognized" since the venv was never created. Fixed by forcing array semantics in `Invoke-Py` via `@($script:PythonCmd)` before checking `.Length`/indexing, which is correct regardless of whether Resolve-Python's return value got unwrapped. Reproduced and verified against both the one-element (`python`) and two-element (`py -3.11`) resolution paths.
- **`assets/images/galileo.ico` was raw PNG data (1024×1024) wearing an `.ico` extension, not an actual ICO container** — Explorer can't parse PNG as an icon resource, so the installer's desktop shortcut (`install/install.ps1`, which points `IconLocation` at this file) silently fell back to a generic icon instead of Galileo's. Regenerated the file in place from the same artwork as a real multi-resolution ICO (16/24/32/48/64/128/256 px, via Pillow) — same source image, now actually readable as an icon; dropped from 1.8 MB to ~200 KB in the process. `galileo/app.py`'s `main()` also now calls `app.setWindowIcon(QIcon(...))` against this file, which it never did before, so the running app's own window/taskbar icon matches the shortcut instead of falling back to Qt's default. A desktop shortcut created before this fix keeps showing the generic icon until it's recreated (re-run `install/install.ps1`) or the Windows icon cache is refreshed, since Explorer caches per-shortcut icons.
- **mypy's `attr-defined` findings across `galileo/ui/*` were dominated by PySide6 enum stub noise**, drowning out real bugs (CODE_REVIEW.md Finding 11). PySide6 6.11's stubs only expose enum members under their nested enum class (e.g. `Qt.AlignmentFlag.AlignCenter`) even though the flat, un-nested spelling (`Qt.AlignCenter`) still works at runtime — this accounted for 220 of the 623 project-wide mypy errors, spread across 27 UI files, several of which also had real, unrelated `attr-defined` bugs (e.g. `DeviceBackend.list_available_devices`, `sessions.py`'s `Callable[[], QScreen]` calls) sitting in the same noisy output. Rewrote every flat Qt/PySide6 enum reference project-wide to its nested spelling (`Qt.AlignCenter` → `Qt.AlignmentFlag.AlignCenter`, `QDialogButtonBox.Ok` → `QDialogButtonBox.StandardButton.Ok`, etc. — `QHeaderView`, `QFrame`, `QAbstractItemView`, `QMessageBox`, `QDialog`, `QPainter`, `QSizePolicy`, `QImage`, `QGraphicsView`, `QFileDialog`, `QFontDatabase`, `QFormLayout`, `QLineEdit`, `QPlainTextEdit` also affected), derived from PySide6's own `.pyi` stubs rather than guessed. Purely a typing fix — nested and flat spellings are the same runtime value in PySide6 — verified via `python -c "import py_compile"` over every changed file, a before/after mypy diff showing zero new error messages of any kind (only the 220 Qt-enum lines disappeared), identical `ruff check` counts before/after, and a full `pytest` run showing the same pre-existing failures as before (see below) with no new ones. Brings project-wide `mypy . --ignore-missing-imports` from 623 to 404 errors, leaving `galileo/ui/*`'s remaining mypy output actually worth reading.
- **`Observatory` had no `contact_details` attribute**, so `test_tc_obs_090_observatory_carries_operator_contact_details` (`tests/test_obs.py`) failed at `obs.contact_details is None` — the class's `__init__` never set the attribute and had no `set_contact_details` method, even though `ContactDetails` (OBS-090) was already defined in `galileo/observatory.py`. Added `galileo/ui/_image_view.py` (`ImagePreviewView`, a pan/zoom `QGraphicsView`, plus `build_zoom_toolbar()`) and rebuilt `SolveImageView` (`galileo/ui/solve.py`), the Imaging tab's live preview (`galileo/ui/app_window/_imaging_page.py`), `StarView` (`galileo/ui/guider.py`) and `FocusImageView` (`galileo/ui/focus.py`) on top of it, so all four now fit-to-window until the user zooms and support drag-to-pan, where three of them previously always auto-fit with no zoom or pan at all. On the Imaging tab this replaces the old View group's `Zoom` spinbox and `Reset View` button, which drove the preview's scale directly and didn't support panning; `ImagingService.set_zoom`/`reset_view` (`IMG-060`) are unchanged and still independently tested (`tests/test_img.py`), just no longer wired to the removed controls.
- **The changelog is split so it no longer dominates the context window of anyone (or any tool) reading it.** `CHANGELOG.md` had grown to ~250 KB in one `[Unreleased]` section, so every edit to it meant loading the whole history. All existing entries moved verbatim to [`docs/changelog/2026-09.md`](docs/changelog/2026-09.md); this file now holds only new entries, with a rotation rule (above) for when it grows again. `CLAUDE.md`, `CONTRIBUTING.md`, `TODO.md` and the VSTarget PSD now point at the archive where they cite past entries.
- **`galileo/ui/app_window.py` (a single ~7,900-line file, one `AppWindow` class) is now the package `galileo/ui/app_window/`, split into 22 files along the module's own pre-existing section comments (one file per page/concern — Camera page, Mount page, Imaging page, Framing Assistant, etc.), with `AppWindow` reassembled from mixins in `__init__.py`.** The file's size was itself a maintainability problem, independent of any single bug: window chrome, every device-category dialog, and Pier/Observatory CRUD were all in one module, and it accounted for over a third of the project's mypy findings by sheer bulk, burying the real bugs in there under noise. No behavior changed — this is a pure move, verified via `python -c "import galileo.ui.app_window"`, `ruff check galileo/ui/app_window/` (same pre-existing findings as before, none new), and the full set of `tests/test_*.py` files that exercise `AppWindow` (`test_driver_info`, `test_eqp`, `test_focus_page`, `test_guider_page`, `test_img`, `test_lib`, `test_optics_page`, `test_rotator_page`, `test_sched`, `test_sky`, `test_solve_page`, `test_star_atlas`) still passing. Splitting one class across files created a real mypy wrinkle — each mixin, checked alone, can't see that it'll share `self` with every other mixin once combined — fixed via a generated `Protocol` (`_state.py`) applied as an explicit `self: AppWindowState` type per mixin method (mypy's own documented pattern for mixin classes, no runtime effect). Net result: project-wide `mypy . --ignore-missing-imports` went from 623 errors to 620 — a net improvement, not the regression a naive per-file split would have been. Found by CODE_REVIEW.md (Finding 9); verified via mypy/ruff/pytest as above.
- **Moved the Imaging tab's Live Stack checkbox from Capture Settings to the View group**, next to Debayer — it toggles how the preview/stack behaves, not what a single exposure captures, so it belongs with the other view-only controls rather than among Exposure/Quantity/Gain. `ImagingService.live_stack_enabled` (`IMG-160`) and its wiring in `galileo/ui/app_window/_imaging_page.py` are unchanged; only which form the checkbox sits in moved.
- **In the Imaging tab's portrait layout (IMG-120), the log now drops to a full-width bar under the Settings and dock columns, and the preview keeps the full height of the page.** Previously the log sat at the bottom of the narrow dock column alongside the nudge pad, stretch slider, histogram and progress bar, cramped to roughly a third of the page's width. `galileo/ui/app_window/_imaging_page.py` now wraps Settings and the dock panel side by side in a `settings_dock_row`, with a new `log_bar` widget beneath spanning both — visible (and holding the log) only in portrait — all inside a `left_column` that sits beside `content` (the preview) as root's other direct child, so the preview's height is no longer shared with the log the way it briefly was in-between. `left_column`'s stretch factor in the page's root layout is toggled between 0 (landscape: it collapses to Settings' fixed width, since the dock and log are hidden) and 1 (portrait: it absorbs whatever width the fixed-width preview column doesn't use) — landscape's own layout (log under the preview in `content_layout`) is unchanged. `tests/test_img.py::test_tc_img_120_portrait_frame_gives_the_preview_the_right_side_and_docks_the_rest_left` updated to check the log's parent, that the preview's height equals the page's, and that the log bar's width matches `left_column`'s (wider than the dock alone).
- **Every live/interactive time-of-day display now shows the system's local time instead of UTC.** The Star Atlas page's time field was a `QDateTimeEdit` pinned to `Qt.TimeSpec.UTC` and labeled "Time (UTC)"; it's now `Qt.TimeSpec.LocalTime` and labeled "Time (Local)" (`galileo/ui/app_window/_star_atlas_page.py`) — the underlying `StarAtlasView.when`/`set_time` (`galileo/ui/star_atlas.py`) are untouched, since astronomical position calculations still need UTC internally, only the widget's display/edit conversion moved. Removed the checkbox and its wiring from `galileo/ui/app_window/_imaging_page.py`, `ImagingService.set_star_overlay`/`star_overlay_enabled` from `galileo/ui/imaging.py`, and `TC-IMG-050` from `tests/test_img.py`. - **PySiril is gone from the Library's Options > Calibration tab and from the codebase entirely.** The `master_manager.py` module never actually called PySiril — it always fell back to its astropy-based sigma-clip/simple-average stacking — so the "Frame Processing Method" dropdown (PySiril vs Internal, defaulting to PySiril) and the PySiril Convert Timeout, PySiril Stack Timeout and Enhanced Siril Logging controls it exposed configured a code path that didn't exist. The unrelated Siril-compatibility note on the FITS compression tooltip (about GZIP2 being readable by Siril/NINA) is unchanged — that's about file-format interop, not the PySiril library integration.
