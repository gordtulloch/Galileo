# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Versions are pre-releases (`0.9.NNalpha`) tagged `v0.9.NNalpha`.

**Each release has its own archive file in [`docs/changelog/`](docs/changelog/)**, named after the version (e.g. [`0.9.03alpha.md`](docs/changelog/0.9.03alpha.md)); the older monthly files (`2026-09.md`, `2026-10.md`) hold entries from before versioned headings began. This file holds only `[Unreleased]` and the index below, so it stays short. Search the archives (`grep -rn <term> docs/changelog/`) rather than reading them end to end.

**At each release:** run `python scripts/archive_changelog.py <version>` (e.g. `0.9.04alpha`). It moves everything under `[Unreleased]` into `docs/changelog/<version>.md`, leaves `[Unreleased]` empty and adds a line to the index. Then bump the version in `galileo/__init__.py` and `pyproject.toml`, write `docs/release-notes/v<version>.md`, and tag.

## [Unreleased]

### Added

- **A remote client can see, pause, resume and stop a running session (`CSURF-180`, `galileo.control_surface.sessions`).** The engine's Control Surface now offers `session.status` (the running session with its block, block n of N and frames done of total, or idle), and `session.pause`, `session.resume` and `session.stop`, which call the same runner the desktop and scheduler use and need the Pier's lease. With nothing running the controls say so instead of failing. **Not done:** skipping a step, which the executor does not support (starting and listing are in the next entry). `TC-CSURF-180` covers the operations that exist. No screen or control changed, so no inline-help or wiki change.

- **A remote client can read the meridian flip's state and trigger a flip (`CSURF-170`, `galileo.control_surface.flips`, `galileo.engine.flips`).** `flip.status` gives where the flip stands (`inactive` when not requested, `waiting` until the mount tracks, `armed`, `due` once the hour angle is past the limit on the west side, `flipping`), the hour angle, the pier side, the clock minutes to the flip limit and how the last flip ended. It reads the Pier's saved Mount-page settings from the database each time, so a change made on the desktop is seen. `flip.now` is a `confirm`-class, long-running operation that does what the Sessions screen's Meridian Flip block does (slew across the meridian, resume tracking) and then checks the mount really changed side of the pier: a mount that stays put is reported `failed`, not `done`. It is refused while a session runs (that session's own block does the flip), when the mount is not tracking, or from the east side. The rules live in `galileo.mount_limits` (`minutes_to_flip`, `flip_phase`) so the desktop can share them; `MeridianFlipService.time_to_flip_minutes` is unchanged (it reads a mount attribute the adapters do not provide). Not done: the engine does not flip on its own (it reports `due`), a flip cannot be deferred (the service has no way to postpone one), and re-slaving a dome and restarting guiding after a remote flip wait for those services in the engine. `TC-CSURF-170` covers it. No screen changed, so no inline-help or wiki change.
- **A remote client can read and acknowledge safety stops, and nothing else is offered until it does (`CSURF-220`, `galileo.control_surface.safety`).** The engine's guard now keeps a log of its safety stops (the last 50: which Pier, why, when, who acknowledged). `safety.events` lists a Pier's stops and `safety.acknowledge` marks them seen. While a Pier has an unacknowledged stop, every operation on it except reads, the three emergency operations and the acknowledgement is unavailable, and the catalogue says "a safety stop must be acknowledged first". Acknowledging is not resuming: it is refused while the monitor still reports unsafe, it restarts nothing, and what happens next is a person's decision (`SAFE-040`). The registry gained a general gate (`Registry.set_gate`) for this. The emergency operations stay offered because they only make things safer; that is a reading of "the only operation offered", recorded in the SDD. Only the engine's guard is wired (the desktop has its own safety handling and no remote gate). `TC-CSURF-220` covers it. No screen changed, so no inline-help or wiki change.

- **A remote client can take frames and read the current one (`CSURF-120`, `galileo.control_surface.imaging`, `galileo.engine.imaging`).** `imaging.capture` takes one frame or a series on the Pier's camera (exposure, count, filter, frame type, gain, offset), answers at once with a correlation id, reports progress after each frame and ends with one finished event; every frame is saved to the Library and announced as a captured frame, so NodeConnect's transfer and the history see it like any other. `imaging.stop` ends the series after aborting the frame in progress, and `imaging.status` returns the series progress and the current frame's shape, statistics, histogram and shot details as plain data. A capture is refused up front, with the reason, when the Pier has no camera, its camera is not connected, a session is running, or a capture is already under way. **Not done:** the picture itself (a JPEG or tile needs a binary route on Connect Link that no document specifies yet; the preview service has no frame source registered), the live-stack view and frame rejection. `TC-CSURF-120` covers it with a fake camera; it has not run against a real one. No screen changed, so no inline-help or wiki change.

- **A remote client can list the Piers a node runs (`CSURF-100`, `galileo.control_surface.piers`).** `pier.list` returns, for every Pier of the engine's Observatory, its id, name, Observatory, the devices connected, any that would not connect, and the running session (or idle); it is a read and needs no lease. A client chooses the working Pier by naming its id in each request, so there is no "select" operation. **Not done:** the Dashboard activity timelines of every Pier (`OBS-150`), which only the desktop records. `TC-CSURF-100` covers it. No screen changed, so no inline-help or wiki change.

- **A remote client can start a saved session template, and the engine can build a session's context without Qt (`CSURF-180`).** `session.templates` lists the saved templates and `session.run` starts one on a Pier with a name, right ascension and declination for the template's placeholder Target; it refuses, in words, a missing target, a missing device, a Pier already running a session, unsafe conditions or an unknown template. To make that possible the assembly of a session's devices, services and notification channels moved out of `ui/session_runner.py` into `galileo/session_context.py`, and the block (de)serialisation into `galileo/ui/session_blocks.py`; the desktop's Run now calls the same code, so the two cannot drift. Differences from a desktop run, which the design records: no guider in the engine yet, and the FITS header does not know the Imaging page's current target. `TC-CSURF-180` covers listing, starting, each refusal and that the engine's side loads without Qt. No screen or control changed, so no inline-help or wiki change; the desktop's behaviour is meant to be unchanged.

### Changed

- **Connect plugins checklist: Phase B marked as built.** The shared request pipeline, catalogue registry, guest allowlist, lease, hold and emergency, and the Master relay already exist in core with tests; the checklist still listed them as open. Documentation only, no code change.

### Fixed

- **A malformed XML element from an INDI server no longer drops the whole connection (`galileo.adapters.indi_client`).** A driver on the Pi sent something the XML parser rejected ("not well-formed (invalid token)"), and the reader treated it as fatal, so every device on that server disconnected. Raw control characters (illegal in XML 1.0) are now replaced before parsing, and if an element is still malformed the reader logs a warning, skips to the next recognisable top-level tag and carries on; it gives up only after 50 such resyncs. Existing INDI tests pass; no test feeds malformed XML yet. No screen changed, so no inline-help or wiki change.
