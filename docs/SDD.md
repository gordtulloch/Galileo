## 1. Introduction

### 1.1 Purpose

This SDD describes how Galileo's architecture and module decomposition satisfy the requirements enumerated in the [SRS](SRS.md). Each module section below states which SRS requirement IDs it is responsible for satisfying, so the RTM can be built as a direct join between this document and the SRS.

### 1.2 Scope

Covers system architecture, the technology-stack decision, module/component decomposition (one section per SRS domain), data design, interface design, concurrency/error-handling design, and deployment topology. It does not specify class-level APIs or pixel-level UI layout — that is implementation detail below the SDD's altitude.

## 2. Design Considerations

### 2.1 Technology Stack Decision (ADR-001)

**Decision:** Galileo is implemented in **Python 3 with PySide6** (Qt for Python) as the UI toolkit.

**Rationale:**
- PySide6 renders through the same native Qt widget engine as a C++/Qt build, giving the same proven performance and memory footprint on ARM SBCs (Raspberry Pi 5-class hardware) that the KStars/Ekos ecosystem already relies on via StellarMate OS. UI performance is therefore not a Python-vs-C++ question — Qt's C++ core does the rendering either way.
- Direct reuse of the domain's existing Python library ecosystem: `astropy.io.fits` for FITS I/O (`META`), `numpy`/`photutils` for star detection and HFR (`IMG-040`, `FOC-010`), a native Python implementation of the INDI wire protocol (see Section 4.2 for why not `pyindi-client`), and the official ASCOM `alpyca` Alpaca client. This avoids reimplementing or wrapping these in a language without equivalent libraries.
- Python is the most common scripting language in the amateur-astronomy tooling community (ASTAP/astrometry.net wrapper scripts, PHD2 event scripts, Siril scripting), which materially lowers the barrier for third-party plugin authors (`PLUG` domain).
- Faster development velocity than C++ for the same Qt-based UI fidelity target.

**Reinforcing evidence:** [AstroFiler](https://github.com/gordtulloch/astrofiler-gui) — merged directly into Galileo core per ADR-002 — and [VSTarget](https://github.com/gordtulloch/VSTarget) — shipped as the VSTarget plugin, documented separately ([`docs/plugins/vstarget/SDD.md`](../plugins/vstarget/SDD.md)) rather than merged into core — are two existing, shipping applications by the same author that already run Python 3 + PySide6 + AstroPy in production across Windows/Linux/macOS. AstroFiler already uses `SEP` for star-detection/quality metrics and Peewee/SQLite for persistence; VSTarget already uses `astropy`/`photutils`/`astroquery`/`astroalign` for FITS/WCS handling, aperture photometry, and image registration. This is direct evidence from two independent codebases, not just a projection, that the stack performs adequately for this domain, and it fixes several of the library choices below (Section 2.5) rather than leaving them open.

**Accepted risks and mitigations:**

| Risk | Mitigation |
|---|---|
| Packaging/installer maturity is weaker than a native compiled build (`NFR-INSTALL`) | Use Nuitka (Python-to-C compilation) rather than a pure interpreter bundle to reduce startup overhead and produce a more native binary; wrap with platform-native installer tooling (Section 2.4). |
| CPU-bound work (star detection, registration) contends with the UI thread under the GIL (`NFR-PERF-020`) | Work that holds the GIL — measured: SEP star detection and astroalign registration, which stall the event loop for seconds even from a background thread — is dispatched to a `ProcessPoolExecutor` (`galileo.core.compute`, Section 2.3). Pure-numpy work (stretch, debayer, histogram, FFT) releases the GIL and runs via `asyncio.to_thread` instead, which avoids copying frames between processes. |
| ARM64/Raspberry Pi wheel availability for PySide6 and scientific libraries | Build pipeline includes an ARM64 Linux CI target producing tested wheels/AppImage for Pi 5-class hardware (Section 7). |

### 2.2 Architectural Style

Galileo uses a **layered, ports-and-adapters (hexagonal) architecture**:

- **Domain core** — device-abstraction interfaces ("ports"), the sequencer engine, and workflow services (autofocus, plate solving, calibration, etc.) are plain Python with no direct dependency on INDI, Alpaca, Qt, or the filesystem.
- **Adapters** — INDI adapter, Alpaca adapter, filesystem/persistence adapter, external-process adapters (solvers, guiders), notification-channel adapters, and the PySide6 UI itself, all implemented against the domain core's port interfaces.
- **Plugin boundary** — a plugin registers new adapters (device backends) or new domain-core extensions (sequencer instructions) against the same port interfaces used internally; there is no separate "plugin API" distinct from the internal module boundary (`PLUG-010`, `PLUG-020`, `NFR-EXT-010`).

This directly satisfies `ARCH-010` (per-category device abstraction implemented independently by INDI/Alpaca backends) and keeps `NFR-PORT-010` (platform-specific code isolated to adapters) structurally enforced rather than aspirational.

### 2.3 Concurrency Model

| Concern | Approach |
|---|---|
| Qt UI thread | Owns the Qt event loop exclusively; never performs blocking I/O. |
| Async I/O (Alpaca HTTP calls, external solver/guider process calls) | `asyncio` event loop bridged into the Qt event loop via `qasync`, so awaitable I/O is non-blocking without a proliferation of manual `QThread` classes. |
| INDI I/O | `galileo.adapters.indi_client` runs one reader thread per INDI server connection, which parses the XML stream into a thread-safe property cache. Adapter calls use the blocking, thread-safe client API via `asyncio.to_thread`, so they work from any event loop (including the short-lived `asyncio.run` loops the UI uses); results reach the domain core through the event bus / queued Qt signals (`Qt.QueuedConnection`). |
| CPU-bound work that holds the GIL (SEP star detection for autofocus HFR, aberration inspection, imaging-tab statistics and Library quality metrics; astroalign registration for live stacking, Library light stacks and the VSTarget photometric stack) | Dispatched to the shared `concurrent.futures.ProcessPoolExecutor` in `galileo.core.compute` via `await run_cpu(fn, *args)` (or `run_cpu_sync` from a worker thread, and `imap_cpu` for an ordered batch with at most one task per worker in flight, which is how Library stacks register frames in parallel), because a thread would still stall the Qt event loop for the length of the C call. The pool is created lazily, uses `spawn`/`forkserver` (never `fork`, which is unsafe alongside Qt/INDI threads), defaults to `min(4, cpus − 1)` workers, recycles each worker after 100 tasks (`NFR-PERF-030`), and is rebuilt after a worker crash (`ARCH-060`). `GALILEO_CPU_WORKERS=0` falls back to threads. Worker functions must be module-level and picklable, and should return small results, since frames cost about 1.5 ms/MB each way to copy. |
| CPU-bound work that releases the GIL (numpy stretch, debayer, histogram, FFT phase correlation) | `asyncio.to_thread`, or a `QThread` for UI-triggered work (the Imaging page's Debayer toggle re-renders on `_PreviewRenderThread`, dropping any render made stale by a newer toggle or frame): measured event-loop stalls stay under 40 ms on a 26 MP frame, and a worker process would only add copy cost. |
| Cross-module communication | A lightweight in-process event bus (publish/subscribe over Qt signals) decouples the sequencer, device layer, and safety/notification modules, so e.g. a safety-monitor "unsafe" event reaches the sequencer without a direct dependency (`SAFE-010`, `ARCH-060`). |

This model is the mechanism behind `NFR-PERF-020` (UI responsiveness during download/solve/autofocus), `NFR-REL-010`/`NFR-REL-020` (device errors surface rather than stall), and `ARCH-060` (fault isolation between devices).

### 2.5 AstroFiler Merge Strategy (ADR-002)

**Decision:** AstroFiler's core (non-GUI) modules — repository scanning, hashing/dedup, metadata-driven organization, session linking, master-calibration creation/application, quality-metric computation, smart-telescope ingestion, and cloud sync — are vendored into Galileo as the `galileo.library` module (Section 4.23). AstroFiler's own standalone entry point (`astrofiler.py`) and its independent GUI shell are retired; the equivalent functionality is exposed as a new "Library" tab within Galileo's own PySide6 UI, driven by the same `galileo.library` module.

**Persistence unification:** rather than running two ORMs/two SQLite files, Galileo adopts AstroFiler's existing **Peewee** ORM as the project-wide persistence layer (superseding the unqualified "SQLite" choice made elsewhere in earlier drafts of this document — see Section 5). AstroFiler's `astrofiler.db` schema (via `peewee-migrate`) becomes the basis for Galileo's combined catalog/session-history/repository database, with Galileo-specific tables (equipment profiles remain JSON per Section 4.4; session-history metrics per Section 4.17) added as additional Peewee models in the same migration chain.

**Star-detection library unification:** AstroFiler already uses **SEP** (Source Extractor for Python) for FWHM/HFR/eccentricity/SNR quality metrics. Galileo adopts SEP as the single star-detection library throughout — including the autofocus service (Section 4.11) and imaging-tab statistics (Section 4.5) — rather than introducing `photutils` as a second, overlapping dependency as earlier drafts of this document proposed.

**New external adapters required:** SMB/CIFS (`pysmb`, for SEESTAR/StellarMate ingestion), FTP/FTPS (standard library `ftplib`, for DWARF/iTelescope ingestion), and Google Cloud Storage (`google-cloud-storage`/`google-auth`, for cloud sync) — all carried over directly from AstroFiler's existing, proven dependency set (Section 4.23).

**Licensing (resolved):** Galileo is licensed GPL-3.0, matching AstroFiler (Project Scope Document, Section 11, C4). Every dependency in this document was chosen to be GPL-3.0-compatible; `google-cloud-storage`/`google-auth` (Apache-2.0) in particular requires GPL-3.0 rather than GPL-2.0. Any future third-party dependency added to Galileo must also be GPL-3.0-compatible, and the in-process plugin design (Section 4.20) means third-party plugins must be GPL-compatible-licensed too — this is an accepted, deliberate constraint, not an oversight.

### 2.6 VSTarget Plugin Strategy — Moved

Previously "VSTarget Merge Strategy (ADR-003)": VSTarget's planning and analysis modules are no longer vendored directly into core SDD as `galileo.plugins.vstarget.planning`/`galileo.plugins.vstarget.analysis` sections here. They are packaged as two first-party pre-loaded plugins, with their own packaging decision now recorded as the VSTarget plugin's own ADR-VST-001 — see [`docs/plugins/vstarget/SDD.md`](../plugins/vstarget/SDD.md) Section 2.1. Nothing about the *packaging outcome* changed (still two plugins, same module split, same dependencies); what changed is that it's no longer asserted as a core architectural decision. This section number is kept as a placeholder, consistent with this document's practice elsewhere of not renumbering around a removed section (e.g. Section 4.23 in the SRS).

### 2.7 AstroLlama Selective Tool Harvest (ADR-004)

**Decision:** Unlike AstroFiler/Obsy (both directly ported/merged into core — ADR-002/005), [AstroLlama](https://github.com/gordtulloch/AstroLlama)'s [MCP (Model Context Protocol) server tools](https://github.com/gordtulloch/AstroLlama/tree/main/mcp_server/tools) are GPL-3.0 (no license tension) but architecturally a grab-bag of independent, mostly self-contained tool functions built for an AI-agent/MCP context — only the astronomy-device-specific ones are harvested, each adapted directly into the existing module it corresponds to (Project Scope Document Section 6.5 has the full file-to-module mapping). AstroLlama's generic AI-assistant tools (news/wiki/YouTube/web search, arXiv, Wolfram Alpha, chat orchestration) are not relevant to Galileo and are excluded outright.

**Notably validating, not just informing:** `telescope_interface_tool.py` + `telescope_registry_tool.py` already implement, in working form, the exact pattern Galileo's own `ARCH`/`PROF` design calls for — one control interface routed to an INDI or Alpaca backend based on an active profile in a registry, with per-platform device-type filtering differences already handled. This is treated as validating evidence for the `ARCH`/`PROF` design (Sections 4.1, 4.4), not merely a reference.

**Direct implementation reuse:**
- `astap_plate_solve_tool.py` → `galileo.platesolve`'s ASTAP `SolverAdapter` (Section 4.12): binary-path resolution, RA/Dec regex parsing, a solved/not-solved heuristic, and — worth calling out specifically — path-traversal-safe filename validation, a concrete security detail carried over rather than reinvented.
- `alpaca_telescope_imaging_tool.py` → `galileo.adapters.alpaca` (Section 4.3) and the `PLT-040` solve-and-center workflow: proven slew/capture/plate-solve-verify/park orchestration and FITS-metadata-on-write pattern.
- `alpaca_device_discovery_tool.py` / `indi_device_discovery_tool.py` → `ARCH-050` discovery implementation reference (Section 4.1).
- `variable_comparison_stars_tool.py` / `generate_aavso_map_tool.py` → the VSTarget plugin's `galileo.plugins.vstarget.analysis` ([`docs/plugins/vstarget/SDD.md`](../plugins/vstarget/SDD.md) Section 3.2, not a core module): AAVSO comparison-star retrieval (reinforcing `VST-AN-040`) and finder-chart rendering (new: `VST-AN-090`) — the one row in this table whose target is a plugin, not a core domain.
- `get_latlong_tool.py` / `get_weather_tool.py` → `galileo.planning.sky_atlas` (Section 4.8, `SKY-090`) and `galileo.safety` (Section 4.16, `SAFE-050`) respectively, both via the Open-Meteo API. The weather forecast is explicitly a planning aid, never an input to `SAFE-010`'s automated-abort logic — that remains the sole responsibility of a connected safety-monitor device, preserving the `ARCH`/`NFR-REL` boundary between advisory internet data and safety-critical device state.
- `generate_constellation_map_tool.py` / `generate_map_tool.py` → `galileo.planning.framing` (Section 4.9, `FRAME-060`) rendering reference.

**New dependency:** an Open-Meteo API client (lightweight `requests`-based, no separate SDK needed — matching AstroLlama's own `data_sources.open_meteo` approach) for `SKY-090`/`SAFE-050`/`EXT-130`. No API key required; GPL-3.0-compatible by construction since Galileo only calls the API at runtime rather than redistributing Open-Meteo data (Project Scope Document, Section 11, C7).

### 2.7a Obsy Port Strategy (ADR-005)

**Decision:** [Obsy](https://github.com/gordtulloch/obsy) was originally CC BY-NC-ND 4.0, which forced treating it as architectural reference only — reimplemented clean-room, never ported (this section previously reflected that treatment). **Obsy has since been relicensed to GPL-3.0** (Project Scope Document, Section 11, C6), removing that constraint. Its contribution to `galileo.planning.sky_atlas` (Section 4.8) and `galileo.planning.framing` (Section 4.9) — `astroplan`-based rise/transit/set computation and DSS-cutout thumbnail-fetch logic (`SKY-080`) — is now treated the same as AstroFiler: **ported directly**, not rewritten from scratch. This is a promotion from the "selective harvest" pattern (Section 2.7) to the same "direct port" pattern as ADR-002, reflecting the license change.

**What doesn't change:** this is a license change, not an architecture one. Obsy is still a Django web application with no structural counterpart in Galileo's PySide6 modules — there's no Django-shaped hole in Galileo's design for the rest of Obsy to drop into. Direct porting is therefore still practically scoped to the function/algorithm level (the rise/transit/set computation, the thumbnail-fetch helper) rather than wholesale module reuse. Obsy's Django scheduling functionality is still not reused at all (Project Scope Document, Section 5) — that exclusion was always about scope/maturity ("only cursory"), not license, and the relicense doesn't change it.

**Diligence note carried forward:** if Obsy ever had contributors other than the author, that should be confirmed before reuse, independent of the license change (Project Scope Document, Section 11, C6).

The `galileo.library` module (Section 4.23, merged from AstroFiler) sits alongside the other domain-core services; it owns the repository/catalog data and the SMB/FTP/FTPS/GCS adapters, and shares the Peewee/SQLite persistence adapter with session history rather than maintaining a separate database. The VSTarget plugin's `galileo.plugins.vstarget.planning`/`galileo.plugins.vstarget.analysis` modules ([`docs/plugins/vstarget/SDD.md`](../plugins/vstarget/SDD.md) Sections 3.1–3.2) are not part of this core module inventory, but follow the identical pattern from outside it: sharing the same persistence adapter and reusing `galileo.platesolve` and `galileo.planning.sky_atlas` rather than duplicating solver or visibility logic, entirely through core's plugin extension points (Section 4.20).

The domain core depends only on the abstract port interfaces; every box in the bottom row is an adapter implementing one or more ports and is individually replaceable — including by a plugin (Section 2.2). `galileo.observatory` (Section 4.4a) sits above `galileo.equipment.profiles`, grouping Piers rather than adding a new adapter row — a single running Galileo instance holds one `DevicePool` per Pier (Section 4.1, `ARCH-080`) and one sequencer/scheduler pair per Pier, with `galileo.observatory` only adding the cross-Pier grouping/scoping layer on top (Section 4.4a).

## 4. Module / Component Design

Each module lists its responsibility, key design elements, external libraries, and the SRS requirement IDs it satisfies (the seed for the RTM's Component column).

### 4.1 `galileo.core.devices` — Device Abstraction Layer

- **Responsibility:** Defines the abstract port interface per device category (camera, mount, filter wheel, focuser, rotator, guider, switch, flat panel, weather, dome, safety monitor, aux); capability negotiation; connection-state and fault-isolation management.
- **Key design:** One `abc.ABC` interface per device category (e.g. `CameraPort`, `MountPort`) declaring only behavior, not transport. A `DeviceCapabilities` value object is populated per-instance from the adapter's introspection of the underlying INDI property set / Alpaca `Can*` flags, and the UI layer queries it to decide what controls to render. This design is validated, not just informed, by AstroLlama's `telescope_interface_tool.py`/`telescope_registry_tool.py` (ADR-004, Section 2.7), which already implement the same one-interface-routed-by-active-profile pattern in working form. `MountPort` supports a non-sidereal tracking-rate parameter (`EQP-MNT-040`) alongside standard sidereal slew/track. `EQP-060`'s raw property inspector reads directly from each adapter's underlying INDI-property/Alpaca-parameter representation, bypassing the port abstraction deliberately, since its purpose is to expose what the abstraction normally hides. Device instances are held in a `DevicePool` keyed by Pier ID (`ARCH-080`) rather than a single global registry — a design decision made specifically so `galileo.observatory` (Section 4.4a) could add multi-Pier support later without this layer needing to change, since retrofitting a device layer that assumed one global device set would have been far more disruptive than designing for multiple pools from the start. **`DevicePool` itself is not instantiated by the running UI** — the UI layer realizes the same one-per-Pier intent directly, with its own per-Pier live-state dicts rather than this class; see Section 4.4b for why, and for where the multi-Pier device/capture/focus/solve concurrency this class was built for is actually wired up. `FocuserController` clamps every absolute/relative move to the connected backend's reported `0..MaxStep` range before issuing it (`EQP-FOC-030`) — a transport-agnostic guard, since an ASCOM/Alpaca `IFocuserV3` driver is documented to hard-stop at those limits itself but INDI focuser drivers give no equivalent guarantee, and a silently-clamped hardware move would otherwise leave this controller's cached position out of sync with the device.
- **Aux: a generic, driver-described property port (`EQP-AUX-010`):** unlike every other category's typed port (`slew_to_coordinates`, `move_to`, ...), `AUX` has no fixed operation set — it exists for a driver that doesn't fit, or that the user wants to drive directly rather than through, one of the guided categories. `AuxController` exposes `get_property_groups() -> list[AuxPropertyGroup]`/`write_property(name, values)` against whatever the connected adapter reports, built from new plain dataclasses (`AuxPropertyGroup`/`AuxProperty`/`AuxElement`) carrying a kind (`"text" | "number" | "switch" | "light"`), group (tab), permission, state, and element list — distinct from `EQP-060`'s diagnostic-only raw-property dict in that it's a first-class Equipment category with its own scan/connect/save flow and a real (if driver-shaped rather than fixed) control panel, not a read-only inspector layered onto an already-categorized device.
- **Libraries:** none beyond the standard library at this layer (transport lives in the adapters).
- **Driver identification (`EQP-070`):** `DeviceBackend.get_driver_info()` returns `name`, `description`, `driver_info` and `driver_version` for any device, and is specified to work *before* connecting — the INDI adapter reads the device's `DRIVER_INFO` property from the (shared, reference-counted) server connection without sending `CONNECT`, and the Alpaca adapter reads the ASCOM `DriverInfo`/`DriverVersion`/`Name`/`Description` common properties, which drivers must serve while disconnected. The equipment pages therefore show a "Driver info" / "Driver version" row as soon as a device is picked from a scan (Camera, Focuser and Rotator per panel; the five scan-only categories at page level — the Guider is not one of them, since it connects to PHD2 by host and port and has no driver to report), and refresh it from the live adapter after connect. The Mount and Filter Wheel pages continue to fill the same fields from their `get_status()` polling. A saved device is deliberately not looked up when a Pier is loaded, so switching Piers never waits on an unreachable server; the row fills on the next device pick or connect.
- **Tracking after a slew (`EQP-MNT-050`):** `galileo.tracking` is a small domain-core module that waits for a mount to stop reporting itself slewing, then selects the rate the target needs — lunar for the Moon, solar for the Sun, sidereal otherwise — and enables tracking, in that order so the mount is never briefly tracking at the wrong rate. It reads the target from anything that names one (a `CurrentObject`, a Star Atlas selection dict, or a plain string), so the Star Atlas Goto can pass the object it was sent to while the Mount page's coordinate slews fall back to the Pier's current object (Section 4.5, `IMG-140`). The wait tolerates a mount that has not yet started moving — a short grace period before a not-slewing answer is believed — and one that never reports the state at all, which is taken as arrived; it gives up rather than commanding a mount that is still moving. `SolveWorkflow` calls it directly since it already awaits its slews; the UI runs it on a worker thread, because the wait lasts as long as the slew does.
- **Mount flip and limits (`EQP-MNT-060`, `EQP-MNT-070`):** `galileo.mount_limits` holds the Mount page's settings (`MountLimits`) and the rules as pure functions — `evaluate` turns a live mount status into "stop", "flip" or nothing, `check_target` judges a slew destination. A monitor on the Mount page polls every 5 s on a worker thread (not gated on the page being visible, so it keeps watching during a session): a mount that is tracking or slewing outside an enabled limit is aborted and stops tracking; with the flip requested, a mount tracking on the west pier side past the flip hour angle is flipped through `MeridianFlipService` and tracking is resumed. A flip the driver did not carry out is not retried for ten minutes. Slew commands are checked by `SlewGuard.limits` (always enforced, unlike the horizon switch) and raise `MountLimitError`; the adapters now consult the guard bound to their Pier rather than the shared fallback one. "Tracking only" spares a slew in progress from the altitude limits, never a slew command. Settings are `device_configs` columns (migration 026).
- **Satisfies:** `ARCH-010`–`ARCH-080`, `EQP-010`–`EQP-070`, `EQP-MNT-040`, `EQP-MNT-050`, `EQP-MNT-060`, `EQP-MNT-070`, `EQP-FOC-030`.

### 4.2 `galileo.adapters.indi` — INDI Adapter

- **Responsibility:** Implements every device port against an INDI server connection.
- **Key design:** Implemented on `galileo.adapters.indi_client`, a native Python client for the INDI XML wire protocol (v1.7) over TCP, rather than on `pyindi-client`. `pyindi-client` is a SWIG wrapper around the `libindi` C++ library, which has no Windows port, so it cannot be built on Windows — a stated target platform (`NFR-PORT`) — whereas a pure-Python client behaves identically on Windows, macOS, Linux and Raspberry Pi. One shared connection per `host:port` (reference-counted) keeps a live property cache updated by a reader thread; each adapter targets one named INDI device and maps Galileo's port methods onto that device's standard properties (`CCD_EXPOSURE`, `EQUATORIAL_EOD_COORD`, `FILTER_SLOT`, `ABS_FOCUS_POSITION`, ...). Devices are classified per category from each driver's `DRIVER_INTERFACE` bit mask; `DeviceCapabilities` are derived from the properties a driver actually defines. Exposures are delivered as FITS BLOBs (zlib-compressed `.z` handled), which the adapter routes to this client only (`UPLOAD_CLIENT`). A device another client (e.g. Ekos) had already connected is left connected on `disconnect()`. `SAFETY_MONITOR` has no INDI interface, so no devices are discoverable for it.
- **`IndiAuxAdapter` (`EQP-AUX-010`):** the one adapter that doesn't translate standard properties into typed methods. Discovery (`list_available_devices`) returns every device name on the server unfiltered by `DRIVER_INTERFACE` — Aux is the deliberate catch-all, so it must not inherit any other category's interface-mask restriction. Once connected, `get_property_groups()` reads `IndiClient.device_properties()` (already grouped/typed by the wire client — see `galileo.adapters.indi_client`'s `IndiProperty`/`IndiElement`) and reshapes it 1:1 into `AuxPropertyGroup`/`AuxProperty`/`AuxElement` (Section 4.1), one group per INDI `group` attribute (i.e. tab), skipping BLOB vectors (image/data payloads, not a control-panel field). `write_property(name, values)` looks the named property's `kind` back up in the live cache and calls the matching `IndiClient.send_number`/`send_switch`/`send_text`.
- **Libraries:** none beyond the standard library (`socket`, `xml.etree`, `zlib`) plus `astropy.io.fits` for decoding frames. An alternative binding (`pyindi-client`) can be built on Linux/macOS where `libindi` is available, but is not required.
- **Satisfies:** `ARCH-010`, `ARCH-020`, `ARCH-030`, `ARCH-050`, `EXT-020`, `EXT-030`, and the INDI-transport implementation of every device-specific `EQP-*` requirement: `EQP-CAM-010`–`EQP-CAM-040`, `EQP-MNT-010`–`EQP-MNT-030`, `EQP-FW-010`–`EQP-FW-020`, `EQP-FOC-010`–`EQP-FOC-020`, `EQP-ROT-010`, `EQP-GDR-010`, `EQP-SW-010`, `EQP-FP-010`, `EQP-WX-010`, `EQP-DOME-010`, `EQP-SAFE-010`, `EQP-AUX-010`.

### 4.3 `galileo.adapters.alpaca` — Alpaca Adapter

- **Responsibility:** Implements every device port against an Alpaca (REST/JSON) device.
- **Key design:** Wraps `alpyca`; UDP discovery per the Alpaca spec for device enumeration; HTTP calls issued through the `asyncio`/`qasync` bridge (Section 2.3) to stay non-blocking. Every `_get`/`_put` call parses the device's Alpaca JSON envelope and raises `DevicePropertyError` on a nonzero `ErrorNumber`, so a real driver rejecting a command (e.g. a focuser move outside its range) surfaces instead of being discarded. `AlpacaFocuserAdapter` reads `MaxStep`, `MaxIncrement`, and `Absolute` from the live device on `connect()` rather than assuming simulator-style constants — needed for real `IFocuserV3` hardware such as a Seestar's Alpaca bridge, which may be relative-only and has a device-specific travel range that feeds `FocuserController`'s clamp (`EQP-FOC-030`, Section 4.1).
- **`AlpacaAuxAdapter` (`EQP-AUX-010`):** Alpaca has no cross-device-type generic property introspection — unlike INDI's single wire protocol, each Alpaca DeviceType is its own fixed, separately-specified interface — so this adapter is deliberately scoped to the one ASCOM interface built for this purpose, ISwitchV2 (the "Switch" DeviceType; `_ALPACA_WIRE_TYPE[DeviceCategory.AUX] = "switch"` reuses the base adapter's existing discovery filter rather than needing an override). `get_property_groups()` reads `MaxSwitch` then, per channel, `GetSwitchName`/`GetSwitchDescription`/`CanWrite`/`Min-`/`MaxSwitchValue`/`SwitchStep` and the live value; a declared range of exactly `0..1` step `1` (`_is_boolean_switch_range`) becomes a `"switch"` kind (On/Off), anything else a `"number"` kind (slider/spinbox) — both as a single-element `AuxProperty` in one "Switches" group, since ISwitchV2 has no grouping/tab concept of its own. `write_property` calls `setswitch`/`setswitchvalue` by channel index (the property's `name`).
- **Libraries:** `alpyca` (ASCOM's official Python Alpaca client).
- **Satisfies:** same requirement set as 4.2, via the Alpaca transport instead of INDI — including the Alpaca-transport implementation of the same device-specific `EQP-*` requirements enumerated in 4.2 (`ARCH-010`, `ARCH-020`, `ARCH-030`, `ARCH-050`, `EXT-020`, `EXT-030`, `EQP-AUX-010`).

### 4.4 `galileo.equipment.profiles` — Equipment Profiles (Piers)

- **Responsibility:** Persist and load named equipment configurations. Each profile is a **Pier**: one mount plus one or more **optical trains** — an ordered chain of device-port references from telescope/lens through reducer/flattener, filter wheel, rotator, and off-axis guider to the final camera — rather than a flat per-device settings list. This refines the data model described in earlier drafts of this document, adopted from the KStars/EKOS "Optical Trains" precedent (Project Scope Document, Section 6.6), because it is what makes automatic focal-length/plate-scale derivation (`PROF-090`) and clean multi-rig support (`PROF-080`, `SES-090`) possible without ad-hoc special-casing.
- **Key design:** An `OpticalTrain` is an ordered list of `(DevicePort, role)` references; effective focal length and plate scale are computed by walking the train's optical elements rather than being separately configured, and are consumed directly by `galileo.planning.framing` (`FRAME-010`) and `galileo.platesolve`. A `Pier` wraps one `MountPort` plus its `OpticalTrain`s and owns the `DevicePool` slot (Section 4.1) it's keyed under. Profiles serialize to human-readable, schema-validated JSON files under a per-platform config directory; import/export is a file-copy of the same schema. The active-profile/active-train-selection model follows AstroLlama's `telescope_registry_tool.py` precedent (ADR-004, Section 2.7).
- **Optical tube definitions (`PROF-100`):** the telescope/lens end of a train is defined on the Equipment section's Optics page, one panel per tube on the selected Pier: name, focal length (mm), aperture (mm), optical system (Newtonian / Schmidt-Cassegrain / Mak-Cassegrain / Refractor / Other), and image alignment as two independent flags, reversed (mirrored left-right) and inverted (flipped top-bottom), since a tube can be either, both, or neither. Optics is a UI/persistence concept only — it has no device port and does not appear in `DeviceCategory` (`ARCH-010`). Tubes persist as `OpticalTubeRecord` rows (`optical_tubes` table, Pier foreign key, ordered by position) in the project-wide Peewee database (ADR-002), alongside the per-Pier `DeviceConfigRecord` rows they reference. A tube's associated devices are stored as `"<category>:<slot>"` keys into those device-config rows rather than as foreign keys, because the device pages delete and recreate their rows on Save; an association whose device no longer exists degrades to a visible "not configured" entry instead of losing the tube. Columns added to an existing table after release are applied at `init_db` time (`_add_missing_columns`), since Peewee's `create_tables(safe=True)` never alters an existing table. Deriving plate scale from a tube (`PROF-090`) is not yet wired to these records.
- **Active optics selection (`PROF-110`):** the main window's top bar carries an Optics selector beside the Pier selector, populated from the selected Pier's `OpticalTubeRecord`s (each entry: name, or "Optical Tube N" if unnamed, plus focal length and focal ratio when known). It is shown only on the primary sections listed in `_OPTICS_SECTIONS` (Imaging and Solve) — Framing is not itself a section (`FRAME-070`), so it isn't listed there, but it reads the same selection via the Imaging tab's own Framing… control (`IMG-180`, Section 4.9). It is refreshed on Pier change, section change, and after the Optics page saves. The choice is held as the tube's position in the Pier's ordered list (tube rows are rewritten wholesale on save, so row ids are not stable) and exposed to screens via `AppWindow.active_optical_tube()`.
- **Active camera selection (`PROF-120`):** a Camera selector sits beside it, filled from the Pier's camera `DeviceConfigRecord` slots and shown on the same sections (`_CAMERA_SECTIONS` is `_OPTICS_SECTIONS`), since an optical train is the tube and the camera it feeds. It is shown whatever the number of cameras — the screens that capture frames can do nothing without one, so which camera they will use, and whether it answered, has to be visible rather than inferred — and each entry is marked “not connected” while `_camera_backends` holds no adapter for its slot. Slots come from `list_device_config_slots`, which sorts them primary-first; the database's own order is alphabetical, which would put `camera_2` ahead of `primary`. The selected slot maps to a backend key through `_camera_backend_key_for_slot`, and `AppWindow.camera_not_connected_message` is what the Imaging and Solve screens show when that lookup comes back empty.
- **Libraries:** `pydantic` (schema validation/serialization).
- **Satisfies:** `PROF-010`–`PROF-120`.

### 4.4a `galileo.observatory` — Multi-Mount Observatory Management (exceeds EKOS, Section 6.6)

- **Responsibility:** Groups multiple Piers (Section 4.4) into a named Observatory; scopes shared resources (dome, safety monitor) at the Observatory or Pier level; provides the multi-Pier status dashboard; carries the operator's own notification contact details (`OBS-090`). This is the one module in Galileo's design with no EKOS precedent to draw on — EKOS's own Scheduler explicitly isn't built for multiple parallel mounts, and its real-world workaround is running separate application instances. Galileo deliberately goes further.
- **Key design:** An `Observatory` is a named collection of `Pier` references plus a `ResourceScope` map (`{dome: observatory|pier, safety: observatory|pier}`, `OBS-030`/`OBS-050`) — deliberately with no `guide` key, since `galileo.guiding` (Section 4.14) has no Observatory-scoped mode at all (`GUIDE-060`). When a safety source is Observatory-scoped, `galileo.safety` (Section 4.16) publishes its unsafe-state event tagged with the Observatory ID rather than a single Pier ID, and every subscriber (each member Pier's `galileo.sequencer.basic`/`galileo.scheduler`) reacts to events tagged with its own Observatory (`OBS-040`) — this reuses the existing event-bus fault-isolation pattern (`ARCH-060`) rather than adding a new cross-Pier call path. Because `galileo.core.devices` already keys device pools per-Pier (`ARCH-080`), this module only has to add the grouping/scoping layer on top — it does not touch the device layer itself. Each Pier's sequencer/scheduler instance runs independently and concurrently (`OBS-020`); this module does not introduce a second execution engine, it just lets more than one `SequenceRunner`/scheduler job queue exist at once, one per Pier. The adjacent, UI-layer half of `OBS-020`/`OBS-080` — two Piers each running their own manual Imaging capture, Autofocus or Plate Solve at once, with the shell's own controls following whichever is displayed — is `galileo.ui.app_window`'s responsibility, not this module's; see Section 4.4b.
- **Contact details (`OBS-090`):** an `Observatory` record carries an operator email address, phone/SMS number, and an enabled-channel flag set (email, text, or both), read by `galileo.notify` (Section 4.19) rather than duplicated into a separate notification-settings store — notification is scoped to the Observatory's operator, not to a Pier, because a multi-Pier Observatory has one operator to reach.
- **Libraries:** `pydantic` (Observatory/ResourceScope/contact-details schema, alongside `galileo.equipment.profiles`).
- **Satisfies:** `OBS-010`–`OBS-090`.

### 4.4b `galileo.ui.app_window` — Main Window Shell & Per-Pier Live Sessions

- **Responsibility:** The `AppWindow` shell (top bar Observatory/Pier/Optics/Camera selectors, primary-section navigation, and one page-builder mixin per Equipment device category and per primary section — `_camera_page.py`, `_mount_page.py`, `_focuser_page.py`, `_filter_wheel_page.py`, `_rotator_page.py`, `_flat_panel_page.py`, `_aux_page.py`, `_weather_page.py`, `_safety_monitor_page.py`, `_imaging_page.py`, `_observatory_pier.py`, `_topbar_optics_camera.py`, plus `galileo.ui.focus`/`galileo.ui.solve`/`galileo.ui.guider` for the Focus/Solve/Guiding sections). Owns turning a Pier switch into a repaint of every visible control, and — the design point this section exists to record — owns keeping each Pier's live device connections and in-flight Imaging/Autofocus/Plate-Solve work running independently of which Pier is currently displayed, so `OBS-020`/`OBS-080`'s "concurrent, independently-addressable" device pools and `ARCH-080`'s one-pool-per-Pier intent are actually realized at the UI layer, not only in the currently-unwired domain-core `DevicePool` class (Section 4.1's caveat above).
- **Key design — per-Pier live state, not a per-Pier `DevicePool`:** `galileo.core.devices.DevicePool` (Section 4.1) is architected for exactly this ("one pool per Pier," `ARCH-080`) but is not instantiated anywhere the running UI reaches — confirmed by inspection, its only user is `tests/test_arch.py`'s isolated unit test of the class itself. Retrofitting the UI onto it would have meant giving it multi-slot-per-category support (`PROF-120`'s multiple cameras) and a way to hand back the higher-level `*Controller` wrappers (`CameraController.start_exposure`, `FocuserController`'s clamp, Section 4.1) the UI actually calls — a larger, riskier change than the UI layer's problem needed. Instead, `AppWindow` extends the pattern `galileo.ui.guider.GuiderPage` already used correctly and in isolation (`self._services: dict` keyed by `galileo.current_object.pier_key()`, one live `GuidingService` per Pier, never torn down on a Pier switch — Section 4.14) to every other live/in-flight resource the shell owns:
  - `self._camera_backends` (slot label → connected camera adapter) is a `@property` resolving to `self._camera_backends_by_pier[pier_key(current)]` — every existing reader (`galileo.ui.focus`, `galileo.ui.solve`, the Imaging page, the top-bar Camera selector) needed no change, since each just reads "the" dict and transparently gets whichever Pier is current.
  - Mount/Focuser/Filter-Wheel/Rotator/Flat-Panel/Aux/Weather/Safety-Monitor each keep a closure-local `adapters_by_pier` dict beside their page-builder's existing widget state; a Pier switch's `reload_page()` restores this Pier's own adapter (repainting its live status) instead of unconditionally dropping it, and `autoconnect_page()` only reconnects a slot this Pier doesn't already have — so a Pier's mount/focuser/wheel/rotator/flat-panel/aux/weather/safety-monitor connection, even mid-move, survives switching away and back without a spurious reconnect. `_aux_page.py` (`EQP-AUX-010`) follows the same scan/connect/save shape as every other device page, but the control panel itself (a `QTabWidget` of property rows) has no fixed widget set to repaint — it's rebuilt from `AuxController.get_property_groups()` right after connect, then refreshed in place on the shared 2-second status timer: a row's own `refresh(prop)` closure updates its state dot/value widgets without rebuilding, and the panel only rebuilds wholesale when the live property name set actually changes (a driver (re)defining its properties), so an in-progress slider drag or line-edit isn't clobbered by routine polling.
  - `_weather_page.py`/`_safety_monitor_page.py` (`EQP-WX-020`, `EQP-SAFE-020`) are the one cross-page exception to "each page owns its own device connection": the Safety Monitor page never opens a second connection to the Weather Station a Pier already has connected on the Weather page — it reaches it read-only through `self._device_pages["weather"]`'s accessor functions (`poll_once`, `get_rules`, `get_latest_readings`), the same per-category dict every page already registers itself into (previously used only for `reload`/`autoconnect`/`disconnect`/`connected`), extended here as a lightweight read-only query surface between two sibling Equipment pages rather than a new direct import between page modules. Each page's own visibility-gated status timer (`_when_visible`, consistent with every other category) drives the actual polling — so the shared history buffer (`self._weather_history_by_pier`, Section 4.1's per-Pier-dict convention, capped at 1000 samples) keeps growing whichever of the two pages is the one currently on screen, and goes quiet (rather than erroring) when neither is. The safety verdict itself (`galileo.safety.evaluate_weather_safety`, Section 4.16) is computed identically on both pages from the same rule set, so the Weather screen's own banner and the Safety Monitor screen's per-measure verdicts can never disagree.
  - `self._imaging_services`/`self._imaging_capture_threads` (`dict[pier_key, …]`) give each Pier its own `ImagingService` (Section 4.5) and capture thread — required, not merely tidier, because `ImagingService.capture_series` resets shared mutable state (`library_ids`, `stop_requested`, …) at the top of every call, so two Piers sharing one instance would corrupt both the moment they captured concurrently. `do_capture()` refuses a second capture only on the *same* Pier; a capture's own signal handlers always update its owning service's state but only repaint the shared preview/histogram/progress/buttons while that capture's Pier is still the one on screen, and a `self._device_pages["imaging"]` reload hook repaints those widgets from whichever Pier's service is now current on every switch — including mid-capture, so switching back to a Pier already running a series shows its progress immediately.
  - `galileo.ui.focus.FocusPage`/`galileo.ui.solve.SolvePage` carry the identical per-Pier dict treatment for `_services`/`_active`/`_workflows`/`_running`/`_mount_busy`. Because both are single instances subscribed to the process-wide event bus (`FocusStartedEvent`/`FocusFrameEvent`/`FocusCompleteEvent`, `SolveStartedEvent`/`SolveCompleteEvent` — Sections 4.11/4.12), those events now carry a `pier_key` payload field (set from a new `pier_key=` constructor argument on `AutofocusService`/`PlateSolver`) so a Pier's own events never paint another Pier's screen state; each page still repaints its whole display from a per-Pier `_last_run`-style cache on every Pier switch, the same reload-hook shape as Imaging. The Solve screen's results table and live preview are the one deliberate exception, kept as a single shared/global log across every Pier (Section 4.12) — that was already this screen's documented behavior before any of this work, not something introduced by it.
  - The obstruction-check slew guard (`galileo.core.slew_guard`) moved from one process-wide `SlewGuard` — silently overwritten with whichever Observatory a Pier switch selected last — to a registry keyed the same way, `get_slew_guard(pier_key)`, with `_mount_page.py` binding each connected mount adapter to its own Pier's guard at connect time and `_observatory_pier.py`'s `_apply_horizon()` writing only the current Pier's entry (while still applying the single app-wide "Do not slew where obstructed" flag to every guard that exists). Without this, two Piers connected from *different* Observatories — a real configuration once captures can run concurrently on both — would have had one of them silently obstruction-checked against the wrong site/horizon, a safety-relevant gap rather than a display one.
  - The same per-Pier-dict treatment also covers three single-in-flight-thread slots that would otherwise have let one Pier's activity block another's: the Imaging tab's filter-wheel-move thread, and the Star Atlas reticle's mount-position-poll and post-slew tracking-resume threads (both in `_observatory_pier.py`).
- **What stays intentionally single/shared, not per-Pier:** the Solve screen's results table/preview (above); the horizon points and `SlewGuard.enabled` flag's *source values* (Observatory-scoped and app-wide respectively, per their own requirements — only where each is *applied* became per-Pier); and — out of scope for now, tracked as a known gap rather than fixed here — two Piers cannot yet run concurrent Autofocus *and* concurrent Plate Solve simultaneously with each other's guiding dithers coordinated, since `galileo.guiding`'s existing per-Pier `GuidingService` (Section 4.14) is not called from any of `ImagingService.capture_series`/`AutofocusService.run`/`SolveWorkflow` today — each of those already documents that it does not trigger a guider dither itself.
- **Satisfies:** `ARCH-080`, `OBS-020`, `OBS-080`, `PROF-120`, `EQP-MNT-050` (per-Pier slew guard), `EQP-WX-020`, `EQP-SAFE-020`, `IMG-150`, `FOC-090`, `PLT-070`, `GUIDE-060` (existing precedent, unchanged).

### 4.5 `galileo.ui.imaging` — Imaging Tab

- **Responsibility:** Live frame display, histogram, auto-stretch preview, optional debayering of the preview (`IMG-110`, pattern set per camera on the Camera page), per-frame statistics, manual capture, panel layout (portrait/landscape, auto-detected from the frame or chosen by the user — `IMG-120`), a mount nudge pad that drives the Mount page's connected adapter through `move_axis` (`IMG-130`), the per-Pier current object (`galileo.current_object`, set from the Star Atlas selection, announced as a `CurrentObjectChangedEvent`, and read by the frame-naming and Solve code — `IMG-140`), sequential multi-frame capture with a per-run gain and optional registration of each frame into the catalog through `LibraryRegistrar.register_capture` (`IMG-150`), live stacking of a run into a running mean (`galileo.livestack`, `IMG-160`), an Options > Imaging screen for the desired saved-frame sample format (`IMG-170`), a Framing… control opening `galileo.planning.framing` (Section 4.9) against the currently selected camera/optical train, including running a mosaic capture directly from this tab (`IMG-180`), a slider above the histogram for adjusting the auto-stretch preview's strength (`IMG-190`), an Annotate toggle above the preview that labels catalogued objects on it (`IMG-200`, `galileo.annotate`, Section 4.5a), and the entry point for the flat-wizard workflow (`CAL-060`) — a Flats… button opens the Flats Assistant dialog (`galileo.ui.app_window._flats`), which drives `galileo.calibration.CalibrationService`'s Sky Flats run (`CAL-070`) off the Qt UI thread; the UI is hosted here rather than in its own primary-navigation section, and the capture logic itself stays in `galileo.calibration` (Section 4.10).
- **Key design:** Frame data is decoded off the UI thread. `ImagingService._analyse_current_frame` builds the preview, statistics and histogram together on the capture thread: statistics (SEP) in the process pool, and the numpy stretch/debayer and histogram via `asyncio.to_thread`. The UI thread only reads the cached `frame_stats`/`frame_histogram`. The result is handed to a Qt `QGraphicsView`-based renderer for pan/zoom; layout persistence uses Qt's `QDockWidget` state save/restore. One `ImagingService` instance (and capture thread) is kept per Pier, not one for the whole window, specifically so two Piers can each have a capture in flight at once without sharing mutable per-run state — see Section 4.4b for the shell-level per-Pier session design this and the Focus/Solve screens share.
- **Libraries:** `numpy` (pixel math), `astropy` (FITS decode), `SEP` (star detection for the HFR/star-count statistics, unified with the autofocus service per ADR-002), Qt Graphics View framework.
- **Live stacking (`IMG-160`):** `galileo.livestack` is a domain-core module (plain numpy, no Qt, no file access) holding a `LiveStacker` that keeps a running per-pixel sum and a per-pixel coverage count, so the mean is taken over the frames that actually cover each pixel and a drifting run's partly-covered edges keep their brightness instead of fading. Registration prefers `astroalign` (a full affine solve, so field rotation is handled) and falls back to whole-pixel translation from FFT phase correlation when astroalign is absent or finds no transform for a frame; which was used is recorded rather than hidden, since the two differ in what they can correct. Registration runs in the CPU worker pool (`LiveStacker.add_async` → `galileo.core.compute.run_cpu`, Section 2.3): astroalign holds the GIL for 4–8 s on a 26–61 MP frame, which froze the UI even from the capture thread. The running sum stays in the capture thread. The stack replaces `ImagingService.current_frame`, so the preview, statistics and histogram follow it; the individual subs are what `IMG-150`'s auto-save catalogues, and the stack is saved separately with `NCOMBINE`/`EXPTOTAL` recording what it is made of.
- **Mosaic live stacking (`IMG-160` + `IMG-180`):** `MosaicStacker` (`galileo.livestack`) is what `ImagingService.capture_mosaic` stacks into when live stacking is on: one `LiveStacker` per pane index, so repeat exposures of the same pane still register onto each other, and each pane's running result is composited onto a canvas sized to the whole mosaic — allocated from the first pane's own pixel shape, at `pane size * (1 - overlap_pct / 100)` spacing per axis, the same spacing `FramingAssistant.create_mosaic` used to place the panes' sky positions, and at the row-major grid position `pane_index` (`= row * cols + col`) implies. Unlike a single-pointing stack, there is no `LIVE_STACK_MIN_FRAMES` gate — a mosaic composites from its first exposure, since the point is the panes' geometry, not signal-to-noise on one pointing — and the overlap band is left unblended (the most recent pane wins there), since this composite is `ImagingService.current_frame`'s live-capture preview, not a deliverable stacked product. `ImagingService.active_stacker` is whichever of `stacker`/`mosaic_stacker` currently holds frames, and is what `stack_frame_count`/`stack_metadata`/`save_stack`/`save_stack_to_library` read — so Save Stack, after a mosaic capture, saves the mosaic composite. Because the composite becomes `current_frame`, the existing pan/zoom preview's fit-to-window behaviour (Section 4.5's `ImagePreviewView`) is what shows the mosaic zoomed out to its full extent as it fills in, with no separate UI path needed.
- **Sample format (`IMG-170`, `META-010`):** every frame Galileo writes — the imaging tab's saved frames, its Library auto-save, the live stack, and the frames written for plate solving — passes through `galileo.metadata.normalise_pixels` before being written. Left to "Auto" (the default and, before `IMG-170`, the only behaviour) it picks the smallest of a fixed portable set (`uint8`/`uint16`/`int32`/`float32`) that holds the data without loss; Options > Imaging's "Desired BITPIX" instead forces every saved frame to one chosen format, clipping out-of-range values and rounding a float rather than wrapping or raising, recorded per `ImagingService` instance (`self.bitpix`, loaded from `galileo.imaging_settings` at construction and updated live when the setting is changed) and threaded through every `_save_fits` call site. No path may write a 64-bit sample format (`BITPIX` 64, or -64 for a double): it is legal FITS and astropy reads it back without complaint, but ASTAP and Tenmon both refuse it as an unsupported sample format — the root cause of a "reading the image file failed" report traced during development to an Alpaca-sourced frame's `int64` array being written verbatim. The frames written for plate solving (`galileo.platesolve._write_frame`/`frame_for_solver`) go through the same `normalise_pixels` but are not affected by the Options > Imaging setting — what the solver can read is a correctness question, not a user preference, so those frames always use "Auto". A second, separate defect surfaced after the 64-bit fix: every writer built its HDU as `PrimaryHDU(pixels, header=a_pre_built_header)`, which is valid FITS that astropy reads back fine, but for unsigned pixel data pushes the `BSCALE`/`BZERO` cards astropy adds to the very end of the header, behind every custom keyword, instead of immediately after `NAXIS2` — which ASTAP's parser requires and refuses a file without. `galileo.metadata.build_primary_hdu` is the fix: it builds the HDU from the pixel data alone first, so astropy places `BSCALE`/`BZERO` on its own immediately after `NAXIS2`, and only then appends the metadata header's cards; every writer in this module and in `galileo.platesolve` goes through it (or the same data-first pattern) rather than merging a header in at HDU construction.
- **Stretch slider (`IMG-190`):** `ImagingService.stretch_level` (0..100, default `DEFAULT_STRETCH_LEVEL`) sets how much of each colour plane's low/high tail `_auto_stretch` clips to black/white (0 .. 2.5% per tail) before stretching the remainder to fill the display range — higher clips more, giving a brighter, higher-contrast but more washed-out preview. The full 0..5% clip range tried initially proved too coarse in practice — every useful setting sat within the first few clicks of the slider — so the range was halved and the default moved to what testing found to be a good, natural-looking setting on that halved scale. `ImagingService.set_stretch` mirrors `set_debayer`'s `rebuild` flag: the Imaging page passes `rebuild=False` and re-renders on a worker thread (`_PreviewRenderThread`), debounced (150 ms) behind a `QTimer` so a drag gesture doesn't queue a render per pixel moved — `apply_preview`'s generation check drops any render that finishes after a newer one started. Only the preview changes; `current_frame`, `frame_stats`, `frame_histogram` and any saved file are untouched.
- **Satisfies:** `IMG-010`–`IMG-190` (`IMG-050` retired — see SRS Section 4.4), `CAL-060`, `CAL-080`.

### 4.5a `galileo.annotate` — Preview Object Annotation

- **Responsibility:** The Annotate control above the Imaging tab's preview (`IMG-200`): plate-solves the displayed frame and labels every catalogued star/DSO it finds within it. New module — this is the working overlay renderer the retired `IMG-050` star-overlay checkbox never had (SRS Section 4.4's note); it exists specifically so this feature isn't shipped the same way again.
- **Key design:** `galileo.annotate` is domain-core (numpy, Pillow — no Qt/INDI/Alpaca, per Section 6.1's module-boundary rule) and takes a preview array plus a `galileo.platesolve.SolveResult`, returning a new RGB array; it never touches `ImagingService.current_frame`/`current_preview` itself. `find_annotations` projects every catalog entry within the frame's field of view (from the solve's centre and scale, widened 15%) to a preview-pixel position via a tangent-plane (gnomonic) projection (`_gnomonic_pixel`) built from `SolveResult`'s centre/rotation/scale alone — there is no CD matrix or distortion term available (`platesolve._result_from_astap_ini` only ever derives those three scalars), so this is a first-order approximation adequate for placing a label, not a re-measurement of a position. Catalog sources are the two already used elsewhere in Planning: `galileo.planning.star_atlas.load_star_catalog()` for named/designated bright stars (an unnamed star is skipped — labelling every detected star was the un-costed idea behind the retired `IMG-050`, and would clutter the preview with hundreds of unlabelled circles) and `galileo.planning.sky_atlas.SkyAtlas` for DSOs, brightest-first, each capped (40 stars / 25 DSOs) so a dense field doesn't produce an unreadable preview. `render_annotations` draws a circle, a short leader line and a text label at each position with Pillow (`ImageDraw`) — the same layout [astronotation](https://gitlab.com/abonengo/astronotation) (MIT licence) draws from astrometry.net's own web-service annotation JSON, reused here for the rendering technique only: Galileo has no such web service and needs Annotate to work fully offline, so positions instead come from the local solve and bundled catalogs above rather than an uploaded-image/job-ID round trip.
- **`ImagingService` integration (`IMG-200`):** `annotate_current_frame(solver)` writes `current_frame` to a temp FITS (`platesolve._write_frame`, same as the Solve screen's capture-and-solve path), calls `solver.solve(...)` — a fresh solve every time Annotate turns on for a frame it hasn't already got a valid overlay for, rather than reusing whatever the Solve screen last did, so Annotate works standalone on whatever is on screen — and builds the overlay via `galileo.annotate.annotate_preview`. `annotated_preview`/`last_solve`/`annotate_note` (a status string for the page's hint) are new instance state; `_annotated_frame` records the `current_frame` identity the overlay was built for, the same staleness pattern `_analysed_frame` already uses for stats/histogram — a capture that replaces `current_frame` (a fresh single shot, or a live stack's frame swap, Section 4.5) silently invalidates a stale overlay rather than showing one that no longer matches what's on screen. `display_preview`/`save_preview` are read-only properties gating, respectively, what the page shows and what a save writes on `annotate_enabled` and that same staleness check. On the Qt side, `_AnnotateThread` (`galileo/ui/app_window/_threads.py`) runs the solve+render off the UI thread, mirroring `_CaptureThread` — solving is an external process that can take tens of seconds.
- **Save behaviour (`IMG-210`) and the Library boundary (`IMG-220`):** `ImagingService.save_current_frame`/`save_stack` check `save_preview` first and, when it is set, write the overlay via a new `_save_png` helper instead of the usual `_save_fits` call — an annotated view is a rendered picture, not scientific pixel data, and a 3-plane colour FITS cube is exactly the kind of file `galileo.platesolve.frame_for_solver`'s own docstring already flags as inconsistently read across tools, so PNG was chosen over forcing it through the FITS path. `suggested_filename`/`stack_filename` (used by the Save Frame/Save Stack file dialogs) and the new `save_file_filter` property switch to `.png`/"PNG files" under the same condition; `_save_png` also redirects a hand-typed `.fits` path to `.png` so the file on disk always matches its extension. Critically, the two Library-bound paths — `_auto_save_to_library` (`IMG-150`'s auto-save) and `save_stack_to_library` — call `_save_fits` on `current_frame`/`active_stacker.result` directly and never read `save_preview`/`annotate_enabled` at all, and `save_stack_to_library`'s own filename (`_stack_fits_filename`, split out from the now annotate-aware `stack_filename` specifically to keep the Library path unconditionally `.fits`) is unaffected by Annotate's state. `IMG-220` therefore holds structurally, not by a conditional check that could be missed on a future edit.
- **Libraries:** `numpy`, `Pillow` (both already project dependencies — Section 3.6/`pyproject.toml`), `galileo.platesolve` (solving), `galileo.planning.star_atlas`/`galileo.planning.sky_atlas` (catalogs).
- **Satisfies:** `IMG-200`, `IMG-210`, `IMG-220`.

### 4.6 `galileo.sequencer.basic` — Sessions (Execution Engine, formerly Sequencer Basic)

- **Responsibility:** Linear action-block-list execution: exposure parameters, dynamic file naming, pause/resume/stop, progress reporting. Domain-core execution only — the Sessions screen itself (authoring, Pier-scoping, templates, Schedule/Deschedule) is Section 4.6a; the nested instruction/condition/trigger block model is Section 4.7.
- **Key design:** A single `SequenceRunner` state machine consumes an ordered list of `SequenceStep` objects (one per action block — `SES-130`/`SES-140`); runs on the domain core, issuing device-port calls and awaiting results via the event bus; persists progress so a crash mid-session does not lose completed-frame records (`NFR-REL-040`). Publishes a "frame written" event, tagged with the current step's `SessionContainer` ID, after each capture — `galileo.library` (Section 4.23, `LIB-150`/`LIB-160`) is the subscriber, not a direct call, keeping this module unaware of the repository/cataloging layer entirely. Multi-rig parallel capture (`SES-090`) runs one `SequenceRunner` instance per optical train (Section 4.4) in a lead/follower arrangement — the lead train's `SequenceRunner` owns the shared `MountPort` (slew/dither/align/meridian-flip), publishing those events on the event bus for follower trains' `SequenceRunner`s to synchronize against, matching EKOS's own multi-train model (Project Scope Document, Section 6.6). This is a P3 capability and not required for v1's single-train path.
- **Note on module naming:** the Python package remains `galileo.sequencer.basic`/`.advanced` for now — the class names (`SequenceRunner`, `SequenceStep`, `SessionContainer`) already used "session" vocabulary before the Project Scope Document's Section 8.1 rename, which is why no code rename is forced by this revision; renaming the package to `galileo.sessions` is a candidate future refactor, not committed here (doc-only propagation, per the scope of this change).
- **Satisfies:** `SES-010`–`SES-090`, `NFR-REL-040`.

### 4.6a `galileo.ui.sessions` — Sessions Screen (Authoring, Templates, Scheduling)

- **Responsibility:** The Sessions screen itself (Project Scope Document, Section 8.1–8.2): per-Pier session ownership, multiple concurrent bounded/scrollable session regions, the right-hand drag-and-drop action palette, target-driven session creation, block-ordering-integrity validation, Save/Save as Template/Load from Template/Schedule/Delete controls, and the scheduled-session lock/Deschedule state machine. New module versus the previous revision of this document, which had no explicit UI-layer section for the sequencer.
- **Key design (target architecture):** a session region is a thin Qt view over one `SequenceRunner`-backed session definition (Section 4.6) held in `galileo.sequencer`'s domain-core session store; the action palette (`SES-120`/`SES-130`/`SES-140`, and the nested-block catalog of Section 4.7) is a declarative registry sharing the `SequencerNode`-registration mechanism `galileo.sequencer.advanced` already exposes to plugins (`PLUG-020`), so a block's palette entry and its execution behavior are defined once; block-ordering-integrity rules (`SES-170`) are evaluated via `SequencerNode.validate()`.
  **Current implementation:** the model (`SessionsScreen`/`SessionRegion`/the block classes, in `galileo.ui.sessions`) is self-contained and does **not** yet integrate with `galileo.sequencer`'s `SequenceRunner`/`SequencerNode` — blocks are plain dataclasses with a `label` and (for `NotificationBlock` only) an `execute()`, per-Pier ownership is a plain dict keyed by Pier name rather than reusing `DevicePool`, the action palette is a static tuple rather than a plugin-extensible registry (so `SES-340`'s plugin-registered block types don't yet appear in it), and ordering rules (`SES-170`) are a small hardcoded table (`_REQUIRES_TARGET`), not `SequencerNode.validate()` calls. This is a deliberate scope boundary, not an oversight: translating an authored session's blocks into real device I/O via the execution engine is separate, tracked work (`TODO.md`'s "Domain logic with no UI" entries) — this module covers authoring and lifecycle (`SES-100`–`230`) only. The target design above remains the intended direction once that execution-engine integration is built.
- **Templates (`SES-180`/`SES-190`):** Save as Template serializes a session's block list, placeholder Target substituted, into a `SessionTemplateRecord` Peewee row (`galileo.library.models.session_template`, same shared database, ADR-002), keyed by a user-entered name rather than a file path — Save as Template overwrites any existing template of that name; Load from Template offers a picker over `SessionTemplate.list_names()`. This closes the JSON-file gap this section previously tracked (a `.gstpl` file per template); the block (de)serialization itself is unchanged — still stdlib `dataclasses.asdict`/`json` against the `{class name: class}` registry, only the storage target moved.
- **Scheduling and the lock state (`SES-200`/`SES-210`):** the Schedule control calls into `galileo.scheduler` (Section 4.9b) to enqueue a `SchedulerJob` referencing the session, its target, and its Pier (`SCHED-010`); this module does not talk to `SCHED` at any earlier point, so an unscheduled session genuinely has no side effect, matching `SES-200`. A scheduled region renders read-only with a red boundary token and swaps its Schedule action for Deschedule. The two ways a job leaves the queue produce **different** outcomes, not one converged state: Deschedule (the user withdraws the job) returns the region to its normal, editable state; completion (the job satisfies its completion condition, `SCHED-050`) deletes the session outright, since a completed session has nothing left to author. Implementation note: rather than an event-bus subscription, each screen reaps completed jobs (`ObservatoryScheduler.reap_completed_jobs`, Section 4.9b) on its own `reload()` — Planning > Sessions and Planning > Schedule (Section 4.9c — there is no separate Planning > Scheduler screen any more) both already refresh via the same per-Pier reload convention every other page uses, so a second notification path wasn't needed for the same effect. Both screens also share one `ObservatoryScheduler` instance per Pier (owned by the shell, not by either screen), so a job scheduled from one is immediately visible to the other.
- **Image block Framing/mosaic control (`SES-130`/`SES-230`):** target architecture — the Image block's Framing… control opens `galileo.planning.framing` (Section 4.9) against this block's own stored framing definition; when that definition includes a mosaic grid, this block's `SequenceStep` expands, at run time, into the shared pane-major capture-order helper (Section 4.9) instead of a single-target capture (`SES-230`).
  **Current implementation:** `ImageBlock.execution_model()` returns the literal string `"mosaic_round_robin"` or `"single_target"` (matching `TC-SES-230`'s exact assertion) once `set_mosaic()` has been called — there is no actual `SequenceStep` expansion wired up yet (that step still needs `SES`/`SCHED`'s execution-engine integration, `TODO.md`). `open_framing_assistant()` (the domain-core hook on `ImageBlock` itself) is still a logged no-op — the real UI wiring lives one layer up, in `galileo.ui.session_block_dialogs._open_framing_assistant_for_block`, which now calls `galileo.planning.framing.open_from_session_image_block` the same way the Imaging tab's own Framing… control calls `open_from_imaging_tab` (Section 4.9's "Current implementation" note), reusing `FramingAssistant.create_mosaic`/`mosaic_footprint_deg`/`compute_fov` against the block's own independent state. Every session block now has block-parameter-editing UI (`galileo.ui.session_block_dialogs`, new module): right-clicking a block on `BlockListWidget` (`_on_right_click`) opens its per-block-type `QDialog` directly, with no intermediate context menu — a block type with no fields at all (e.g. Dither/Park Mount) or a block in a scheduled/locked session does nothing on right-click instead — and the Image block's own dialog exposes its exposure/count/filter/binning/gain/offset/frame-type fields plus a "Framing / Mosaic…" button into the above. Also: `SES-170`'s existing Target-block ordering rule (a Plate Solve block requires a preceding Target block) previously failed a drop silently enough to look like a bug rather than a rule — `dropEvent` now surfaces the rejection via a `QMessageBox` warning, and the Plate Solve palette tile has an explanatory tooltip. `dropEvent`'s insertion-row calculation was also a real bug independent of that rule: it always read a hover over an existing row as "insert before this row," regardless of which half of the row the pointer was actually in — with the list's height fit tightly to its content, there's no empty space below the last row to drop "after" it into, so dropping Plate Solve after an already-present Target block still failed the ordering check. Fixed by comparing the drop's y-coordinate against the hovered row's own `visualRect` midpoint. `remove_block()` on `SessionRegion`, plus a `BlockListWidget.startDrag` override, now support deleting a block by dragging it out of every session panel (the palette and every region's block list) and releasing elsewhere — detected as the drag ending in `Qt.DropAction.IgnoreAction` *and* the release point falling outside every such widget, so an unsupported cross-region drop still just does nothing rather than deleting the block; a scheduled/locked region refuses with a warning instead.
- **Libraries (target):** Qt Graphics View framework for the draggable block regions; Peewee for template persistence (ADR-002).
  **Current implementation:** plain `QListWidget` drag/drop (`Qt.UserRole` item data + a custom `dropEvent`), not Graphics View — no drag-and-drop precedent existed anywhere in this codebase to extend, and nothing in `tests/test_ses.py` requires a graphics-scene canvas. Template persistence uses Peewee, per target; a template's blocks themselves still (de)serialize via stdlib `dataclasses.asdict`/`json` into a `TextField` against the same `{class name: class}` registry, not `pydantic`.
- **Satisfies:** `SES-100`–`SES-230`.

### 4.7 `galileo.sequencer.advanced` — Sessions (Nested Instruction/Condition/Trigger Blocks, formerly Sequencer Advanced)

- **Responsibility:** Nested instruction/condition/trigger execution model, exposed from the same single palette as Section 4.6a rather than a separate advanced-mode screen (Project Scope Document, Section 8.1); live-editing of not-yet-run blocks.
- **Key design:** Instructions, conditions, and triggers are all implementations of a common `SequencerNode` interface (`execute()`, `validate()`, `describe()`); the built-in catalog from `SES-310`/`SES-320` ships as first-party `SequencerNode` implementations registered through the same entry-point mechanism a plugin uses (`PLUG-020`), so there is architecturally no distinction between "built-in" and "plugin" instructions. There is no separate basic-to-advanced migration path (former `SEQ-ADV-100`) to implement: a session mixes plain action blocks (Section 4.6) and nested blocks (this section) freely from one palette, so there is nothing to migrate between.
- **Satisfies:** `SES-300`–`SES-360`.

### 4.8 `galileo.planning.sky_atlas` — Sky Atlas / Targets

- **Responsibility:** Presented as the **Targets** screen (Project Scope Document, Section 6.4/6.9), look-and-feel informed by a reference layout image (`assets/samples/planning.png`, not distributed with the repository) adjusted to Galileo's own UI. Deep-sky object catalog, search/filter, altitude charting, horizon profiles, observing locations, and (new in this revision) optional Telescopius augmentation.
- **Key design:** Catalog (≥10,000 objects) is bundled and loaded into a local SQLite database at install time, so search/filter/chart operate fully offline (`NFR-OFFLINE-010`); altitude charting is ported directly from Obsy's `targets` app in spirit (astropy `AltAz` transforms against a configured observer location, Section 2.7), but **not via `astroplan`** as this section previously claimed — that was never actually added as a dependency (a doc/code gap, corrected here rather than left standing). Rise/transit/set (`galileo.planning.visibility.rise_transit_set`) is derived directly from the same altitude curve `altitude_chart()` already computes (transit = its peak sample, rise/set = linearly-interpolated horizon crossings either side of it) — astropy-only, since `astroplan`'s own rise/set functions are themselves thin wrappers over the same underlying astropy time/coordinate transforms, and adding it as a real dependency was explicitly declined (untested on macOS/Linux/RPi5, `NFR-PORT` still open). Observing-location geocoding (`SKY-090`) is adapted from AstroLlama's `get_latlong_tool.py` (ADR-004, Section 2.7), via Open-Meteo.
- **Targets screen results — no details panel, per-result criteria (`SKY-020`/`SKY-030`):** `AppWindow._build_sky_atlas_page` originally showed rise/transit/set (`SkyAtlas.rise_transit_set`) and an altitude-over-the-night chart in a separate details panel on selection; that panel is removed (user's call) and every result's own tile carries this instead — see the "Result tiles" bullet below for the tile layout itself. Both reuse `galileo.ui.app_window._widgets`' `_AltitudeChart` self-painted widget rather than a second copy of the same line-chart paint code — need the active Observatory's latitude/longitude (top-bar selector, via a local `_current_location()` closure), and degrade to an em-dash/empty-chart placeholder, not an error, when no Observatory location is configured. A **Visible tonight** checkbox in the search-criteria panel threads through to `SkyAtlas.filter(visible_tonight=True, location=...)` (`SKY-020`'s "current/tonight visibility" clause), silently falling back to an unfiltered search (with a status-bar note) when no Observatory location is set rather than refusing to search. Two more criteria fields, only applied when Visible tonight is checked: **Reach an altitude of** (`min_altitude_deg`, default 20°) and **…for at least** (`min_duration_hours`, default 0 — any single moment, the original check), matching the reference Telescopius layout's compound altitude filter — `is_observable_tonight` (`galileo.planning.visibility`) checks for a run of consecutive altitude-chart samples at/above the threshold spanning at least that many hours, rather than just any one sample. A **Max size** field alongside the existing **Min size** makes apparent-size filtering a range (`SkyAtlas.filter`'s new `max_size_arcmin`, 0 meaning no upper bound — an unmeasured-size catalog object, `size_arcmin` 0, only ever fails the min bound, never the max one). A **Min. Moon separation** field (`min_moon_separation_deg`, independent of the Visible tonight checkbox — its own filter, matching the reference layout's separate "Distance from the Moon" category) excludes anything closer to the Moon than that, at local midnight tonight (`galileo.planning.visibility.moon_position_deg`/`moon_separation_deg` — the Moon's position computed once per `filter()` call via `astropy.coordinates.get_body`, then compared per object with plain spherical trig rather than a repeated per-object astropy call, so it stays cheap against the full catalog); needs the same Observatory location as Visible tonight and degrades the same way (skipped, with the same status-bar note, when none is set). Three **Catalog** checkboxes (Messier/Caldwell/NGC, `DSO_CATALOGS`) — none checked means no catalog filter, any checked means an object must belong to at least one of them (`catalogs_of()`) — reuse the exact same catalog-membership logic the Star Atlas/skymap's own overlay toggles already use (`galileo.ui.star_atlas`'s `dso_catalogs`/`_dso_members`, both built on `catalogs_of()`) rather than a second, separate notion of "catalog" for this screen; `SkyAtlas.filter`'s new `catalogs` parameter calls that same `catalogs_of()` per object.
- **Result tiles — one per row, no details panel, no grid (`SKY-020`/`SKY-030`/`SKY-050`):** each match gets a `setItemWidget` tile (name/type, magnitude/size/constellation/RA/Dec, rise/transit/set, a mini `_AltitudeChart` with a labelled time axis, and — rightmost — three per-tile action buttons) instead of the earlier plain text line or the details-panel design that preceded it — every piece of information the (now-removed) details panel used to show on selection is on the tile itself, unconditionally, per the reference layout image. Each tile is white-bordered and narrowed to `_TILE_WIDTH_FRACTION` (50%) of the results list's own width via a `_tile_row` wrapper (a `QListWidget` row's item widget otherwise always stretches to the full viewport width in Qt's default list mode, so narrowing the tile widget alone has no visible effect) — one tile per row, not a wrapping grid (an icon-mode/grid layout was tried and explicitly rejected in favour of this). The altitude chart/rise-transit-set for every tile is computed in one batched call (`SkyAtlas.altitude_charts_batch`, a single vectorized astropy transform across all shown results) rather than per tile — computing it individually for up to 200 results measured at ~10s, genuinely UI-blocking; batched, ~1s. Per-tile thumbnails stay individually fetched and capped at the first `_MAX_AUTO_THUMBNAILS` (12) results, unlike the chart/rise-set data — each is a real hips2fits network request, not a local computation, so the same batching approach doesn't apply and the existing bound still holds; the rest of a large result set still gets a full tile, just without an image.
- **Per-tile action buttons (`SKY-050`, `SKYMAP-060`, `SES-160`):** **Select** calls the same `AppWindow._set_current_object(obj.as_sequence_target())` hook the Star Atlas/skymap's own object-selection signal already drives, making the result the active Pier's current object (`IMG-140`) — no new selection mechanism. **Slew To** calls the same `_mount_to_object("goto", ...)` the skymap's slew-to-clicked-location uses (`SKYMAP-060`), needing a freshly-computed current altitude for its below-horizon guard — `galileo.planning.star_atlas`'s `julian_date`/`local_sidereal_deg`/`precess_from_j2000`/`equatorial_to_horizontal` (the exact technique its own live renderer already uses for every star/DSO/body, not a second alt/az implementation), computed once per click, not batched with the chart data above (only needed if the button is actually pressed). **Add to Session** calls the shared `AppWindow._add_to_session(name, ra_deg, dec_deg)` (`create_session_for_target` when the Sessions screen has been opened, `SES-160`) — the same entry point the Star Atlas's own right-click "Add to Session" context-menu action uses, so the two never drift apart; `_set_current_object` itself no longer creates a session as a side effect of a plain click (see Section 4.9a's note) — all three tile buttons reuse existing cross-module entry points rather than adding new ones. All three degrade to a status-bar message, not a crash, when their precondition isn't met (no Observatory location for Slew To's altitude check, no connected mount for the slew itself, Sessions screen not yet opened for Add to Session). Sized to fit their own text (`max(b.sizeHint().width() for b in (...))`, all three then made uniform to that widest one), not a hardcoded fixed width — an earlier fixed width clipped "Add to Session," the longest label, and would clip again for a differently-worded or differently-localized label in the future.
- **Object-name search priority — reordered, `SKY-100`:** `SkyAtlas.search_online()` is now **catalog-first, Simbad-fallback** — `search()` (`SKY-010`) against the bundled offline catalog runs first, and Simbad (`_search_simbad_sync`, `astroquery.simbad`) is only called when the catalog has no match, so ordinary object-name search now satisfies `NFR-OFFLINE-010` the same way catalog browse/filter/chart already did, not just as a side effect of Simbad happening to be unreachable. The Simbad-lookup mechanics themselves are unchanged (wildcard mode only when the query contains `*`/`?`, per-instance `Simbad()` calls consistent with `galileo.plugins.vstarget.planning.simbad_client.SimbadClient`, magnitude as a separate capped query, constellation via `astropy.coordinates.get_constellation`) — only the call order moved.
- **Size-aware survey thumbnails (`SKY-080`):** `SkyAtlas._fetch_thumbnail()` (ported from Obsy's `Target.save()`, `targets/models.py`, ADR-005) is changed from a fixed 15×15 arcmin DSS cutout to a field size derived from the object's own angular size (from the catalog/Simbad result), clamped to sane min/max bounds so a point-source star and a multi-degree nebula both crop sensibly, fetched as a pre-rendered JPEG from the `CDS/P/DSS2/color` HiPS survey via the CDS hips2fits service (retargeted from the STScI dss_search CGI, which caps cutout size — `galileo.planning.framing`'s Section 4.9 note has the same change) and resized to 150×150 off the UI thread via `asyncio.to_thread`; degrades to no thumbnail (rather than raising) on any failure, unchanged. **Disk-cached as fetched:** `_fetch_thumbnail()` checks `_cached_thumbnail()` (keyed by ra/dec/field size, `galileo.platform.get_cache_dir()`) before hitting hips2fits, and writes a successful fetch to it via `_cache_thumbnail()` — the same technique `galileo.planning.framing`'s survey-image cache already uses, so re-selecting a result (details panel) or the same object turning up again in a later search's result cards is a disk read, not another network request. Separate from `add_to_target_list`'s own name-keyed `"<object name>_thumbnail.jpg"` file, which still writes independently for its own permanent-copy purpose. **Bulk pre-caching (Options > Planning's "Cache All Catalog Thumbnails…" button):** `AppWindow._ThumbnailCacheThread` walks the whole offline catalog calling `SkyAtlas._fetch_thumbnail()` per object off the Qt UI thread (`QThread`, the same worker-thread/`QProgressDialog` pattern `galileo.ui.library.download_dialog`'s telescope download already uses, not a new one) — an already-cached object returns instantly with no network call, so this is safe to cancel and resume, or re-run later to pick up new catalog objects, without redoing work. No added concurrency (one fetch at a time, matching every other thumbnail fetch already in this codebase) and a confirmation dialog states the object count and that this can take hours before starting, since the full catalog is tens of thousands of objects at one real network request each. **Target-list reconciliation:** `add_to_target_list` and the live "current object" flow (`galileo.current_object`, `IMG-140`) were previously two parallel, non-communicating mechanisms — nothing ever called `add_to_target_list`. A Targets-page result tile's **Select** button (`AppWindow._select_result`) now calls both: `_set_current_object` as before, and `add_to_target_list` on a single persistent `SkyAtlas` instance (`AppWindow._shared_sky_atlas`, lazily created) — a persistent instance matters here specifically, unlike the throwaway per-call instances this page's search/filter code uses elsewhere, since `_target_list`'s whole point is to accumulate across selections, which a fresh instance per call would silently prevent. A thumbnail-caching failure inside `add_to_target_list` is never fatal to Select itself. **Click-to-enlarge full image:** each tile's thumbnail is a `_ClickableThumbnail` (a `QLabel` subclass emitting `clicked` on a left-button press, `AppWindow`) — clicking it opens `AppWindow._show_full_image`, a modal dialog fetching the same survey-image field at `_FULL_IMAGE_SIZE_PX` (640) instead of upscaling the already-small 150px tile crop, which would just look blurry this large. `SkyAtlas._fetch_thumbnail()`/`_thumbnail_cache_path()`/`_cache_thumbnail()`/`_cached_thumbnail()` all gained a `size_px` parameter (default 150, so every thumbnail cached before this change keeps the same filename and stays valid) so the 640px full view gets its own disk-cache entry rather than colliding with, or being satisfied by, the small one — reopening the same object's full view later is a disk read, same caching principle as the tile thumbnail itself. The dialog shows immediately with a "Loading…" placeholder before the (blocking, same as every other single-object thumbnail fetch in this app) fetch runs, so it doesn't look broken while the request is in flight; degrades to a "No image available." message on failure.
- **Telescopius augmentation (`SKY-110`/`SKY-120`, `EXT-150`), optional and P2 — gating/plumbing built, the actual HTTP call deliberately stubbed:** `SkyAtlas.set_telescopius_api_key()` (bring-your-own-key, no bundled/shared credential — the API is Patron/Sponsor-gated, Project Scope Document §6.9) gates `search_online()`'s Telescopius augmentation (layered additively on top of the offline-first/Simbad-fallback result, never a substitute) and `import_telescopius_observing_list()` (`TelescopiusNotConfiguredError` with no key set). The module-level `_search_telescopius_sync`/`_fetch_telescopius_observing_list_sync` that would make the actual REST calls both raise `NotImplementedError` rather than guessing at a request shape — per PSD §6.9's own review, Telescopius's public API launched in 2023 with only a "quote of the day" endpoint and its staff describe target-search/suggestion endpoints as roadmap items, not a documented, stable surface, so there is no real endpoint to implement against yet. Search augmentation catches that (and any other) exception and continues without Telescopius data — the same "advisory-only, degrade silently" pattern `SAFE-050`'s weather lookup uses, since there's an offline/Simbad result to fall back to; the explicit user-triggered import (`SKY-120`) does *not* swallow it, since there's no meaningful "imported nothing" fallback for an action the user asked for directly. No Options UI to enter the key exists yet either (Options > Science is still a placeholder, `TODO.md`) — `set_telescopius_api_key()` is in-memory-only per `SkyAtlas` instance, not yet persisted via keychain the way `NFR-SEC-030`'s iTelescope password is.
- **Libraries:** `astropy.coordinates` (altitude charting and rise/transit/set, `SKY-030` — no `astroplan`), SQLite (bundled catalog), `astroquery.simbad` (fallback object-name search, `SKY-100`), Pillow (HiPS-cutout-to-JPEG thumbnail conversion, `SKY-080`), an Open-Meteo API client (geocoding); no Telescopius client library yet (`SKY-110`/`SKY-120`'s HTTP calls are stubbed, see above).
- **Satisfies:** `SKY-010`–`SKY-120`, `NFR-OFFLINE-010`, `EXT-110`, `EXT-130`, `EXT-150`.

### 4.8a `galileo.planning.recommend` — What's Up Tonight (ranking engine)

- **Responsibility:** The domain-core ranking/recommendation layer behind the What's Up Tonight screen (Section 4.8b) — not a second catalog or ephemeris engine. Composes four existing modules rather than reimplementing any of them: `galileo.planning.sky_atlas`'s catalog and `HorizonProfile` (Section 4.8, `SKY-010`/`SKY-040`), `galileo.planning.visibility`'s altitude/rise-transit-set/Moon-separation functions (`SKY-020`/`SKY-030`, reused by `galileo.planning.sky_atlas` itself), `galileo.equipment.profiles`' `OpticalTrain` (Section 4.4, `PROF-080`), and `galileo.safety`'s three advisory clients (Section 4.16): the Open-Meteo weather forecast (`SAFE-050`), the aurora Kp-index estimate (`SAFE-090`), and the smoke/transparency estimate (`SAFE-100`). Plain Python, no Qt/INDI/Alpaca, per the domain-core layering rule (`ARCH`).
- **Key design:** A 4+1 decomposition — Target Astrometry (from `DeepSkyObject`, sky-independent), Sky State (darkness window, altitude curve, Moon separation, horizon obstruction, weather/aurora/smoke advisories — equipment-independent, produces an `ObservabilityScore`), Equipment Envelope (per optical train: limiting magnitude, field-of-view fit, mosaic-required — sky-independent, produces a `FitScore`), Recommendation (`ObservabilityScore × FitScore`, adjusted by session context, plus a human-readable `reasons` list), and Confidence (a parallel indicator of input completeness — missing forecast, missing horizon profile — never multiplied into the score, `WUT-030`). The module-level `rank_tonight(location, pier, catalog, forecast, night_date=None, aurora_estimate=None, smoke_estimate=None, library_lookup=None) -> list[Recommendation]` entry point is pure and I/O-free — callers (the UI layer, Section 4.8b) fetch the forecast, aurora/smoke advisories, catalog slice, and Library history beforehand, the same pattern `galileo.planning.sky_atlas.SkyAtlas.filter` already uses — so it is directly unit-testable against hand-constructed inputs without mocking network calls. **Horizon obstruction (`WUT-080`):** where the active location has a `HorizonProfile` configured (`SKY-040`), the Observability Score computation excludes altitude/time ranges behind it, exactly as `galileo.core.slew_guard`'s obstruction check already treats obstructed altitude/azimuth as unreachable (Section 4.9a, `SKYMAP-080`) — not a second obstruction model. Where none is configured, ranking proceeds on open-horizon altitude alone and the omission is reflected via `Confidence`, never blocking the ranked list. **Library integration time (`WUT-050`):** the optional `library_lookup` callable populates `Recommendation.prior_integration_hours` from `galileo.library`'s catalog (Section 4.23) for display only — it is never read by the scoring computation itself, enforced by keeping it out of the `score`/`ObservabilityScore`/`FitScore` value objects entirely rather than by a runtime check. **Re-ranking on Pier/train change (`WUT-040`):** `ObservabilityScore` is Pier-independent (sky state alone), so a caller re-ranking after switching optical trains needs only to recompute `FitScore` and the combination step against an already-computed `ObservabilityScore` set, not re-fetch/recompute sky state — this module's pure-function design makes that caller-side caching straightforward rather than requiring an internal cache of its own. **Arbitrary observing date (`WUT-090`):** `night_date` (default `None`, meaning tonight) is threaded straight through to the same `galileo.planning.visibility` altitude/rise-transit-set/Moon-separation calls `galileo.planning.sky_atlas` already parameterizes by date — there is no separate "tonight" code path to generalize. A `night_date` outside `galileo.safety`'s forecast horizon simply yields no forecast data for that night, which is indistinguishable to this module from a forecast-fetch failure and so is already covered by `WUT-030`'s existing missing-forecast confidence degradation, rather than needing its own out-of-range case. **Aurora/smoke advisory integration (`WUT-100`):** `aurora_estimate`/`smoke_estimate` (each `None` when unavailable for `night_date`, mirroring `forecast`) are folded into `ObservabilityScore.value` the same way weather already is — a stronger-than-threshold Kp index or a heavier smoke rating each apply a modest downward adjustment to the whole night's score, uniformly across every entry, since both describe location-wide sky transparency/glow rather than anything object-specific. Consistent with `SAFE-090`/`SAFE-100`'s own advisory-only tier (never a driver of automated abort, `SAFE-010`), neither is required for ranking to proceed: either being `None` degrades `Confidence` exactly as a missing weather forecast already does (`WUT-030`), rather than being treated as "clear/no aurora" by default.
- **Not built (v1 non-goals, Project Scope Document Section 5.3-equivalent):** no second weather client (reuses `SAFE-050`/`SAFE-090`/`SAFE-100`), no second catalog/ephemeris engine (reuses `SKY`), no solar-system/comet/transient-event calendar, no exposure-planning advisor, no visual-observing (eyepiece/Barlow) Fit Score — imaging (camera-sensor) only in v1.
- **Libraries:** none beyond the standard library — composes existing modules' public functions rather than adding a new dependency.
- **Satisfies:** `WUT-010`, `WUT-020`, `WUT-030`, `WUT-040`, `WUT-050`, `WUT-080`, `WUT-090`, `WUT-100`.
- **Current implementation:** built as designed above, with the signature refined from this section's earlier illustrative sketch to what `PROF-080`'s Fit Score actually needs — `rank_tonight(location, train, catalog, forecast=None, night_date=None, aurora_estimate=None, smoke_estimate=None, library_lookup=None, min_altitude_deg=20.0)` takes the specific `OpticalTrain` the Fit Score is computed against (a `galileo.equipment.profiles.OpticalTrain`, or `None`), not a whole Pier — a Pier can hold more than one train (`PROF-080`), and this module has no reason to know which one a caller means. Internally split into two public functions rather than one, so `WUT-040`'s re-ranking is a real second entry point, not just a documented calling convention: `compute_observability(location, catalog, night_date=None, forecast=None, aurora_estimate=None, smoke_estimate=None, min_altitude_deg=20.0) -> list[_ObjectObservability]` (Sky State only) and `rank_for_train(observability_results, train, library_lookup=None) -> list[Recommendation]` (Equipment Envelope + Recommendation, sorted by score descending); `rank_tonight` is the two called back to back. `_fit_for_train`'s limiting-magnitude estimate is the standard visual-limiting-magnitude-by-aperture formula (`7.7 + 5·log10(aperture_mm)`), explicitly not exposure/stacking-aware; field-of-view fit divides the train's `plate_scale_arcsec_px` (`galileo.equipment.profiles.OpticalTrain`, Section 4.4) by the shorter sensor dimension. Field-of-view fit is two-sided, not just a fits/doesn't-fit check: an object smaller than `_TARGET_FIELD_FILL_FRACTION` (30% of the frame's shorter dimension) has its `FitScore.value` ramped down linearly toward 0 as it shrinks toward a speck, since a technically-visible 4′ galaxy in a 71′×128′ field is not a reasonable single-frame target even though it "fits"; an object *larger* than the frame is not penalized this way — mosaicking is a legitimate option, already covered by the existing `fits_field`/`mosaic_required` 0.5× factor. Moon-separation, aurora-Kp, and smoke-AQI penalties are each a documented, simple linear-threshold model (module-level `_MOON_FULL_PENALTY_DEG`/`_AURORA_KP_THRESHOLD`/`_AURORA_KP_SEVERE`/`_SMOKE_AQI_THRESHOLD`/`_SMOKE_AQI_SEVERE` constants) rather than a calibrated one, matching this section's own "reasonable, documented heuristic" framing.

### 4.8b `galileo.ui.whats_up` — What's Up Tonight (screen)

- **Responsibility:** The What's Up Tonight screen itself: a primary-navigation Planning entry positioned first in the sidebar, ahead of Targets (`WUT-070`) — not a modal like Framing (Section 4.9). Presents `galileo.planning.recommend.rank_tonight`'s output (Section 4.8a) as one tile per recommended object.
- **Key design:** Reuses `galileo.planning.sky_atlas`'s result-tile pattern (`AppWindow._build_sky_atlas_page`, Section 4.8) rather than a new tile layout: one tile per `Recommendation`, an altitude mini-chart via the same shared `_AltitudeChart` widget (`galileo.ui.app_window._widgets`) `galileo.planning.sky_atlas` already reuses (Section 4.8), a thumbnail, and the same Select / Slew To / Add to Session action buttons as the Targets screen's own tiles (`WUT-060`) — calling the identical shared entry points those buttons already use (`AppWindow._set_current_object`, `_mount_to_object`, `_add_to_session`), not a new selection mechanism. A "why this ranking" line per tile surfaces `Recommendation.reasons` (`WUT-020`); a confidence badge, shown only when inputs were incomplete, surfaces `Recommendation.confidence` (`WUT-030`) without blending it into the tile's rank position. Where `Recommendation.horizon_applied` is true, this is consistent with the horizon shading `galileo.ui.star_atlas` already draws (Section 4.9a, `SKYMAP-070`) and the obstruction check its slew guard already applies (`SKYMAP-080`) — the same underlying `HorizonProfile`, not a second rendering of it. A prior-integration annotation (`Recommendation.prior_integration_hours`, `WUT-050`) is shown per tile as text only, never used to reorder tiles. The top-bar Pier/optical-train selector (`PROF-110`) drives which `OpticalTrain` feeds `rank_tonight`'s Fit Score layer; switching Pier re-ranks by recomputing only Fit Score against the session-cached Observability Score set (Section 4.8a's `WUT-040` note), not a full catalog re-fetch. Degrades exactly like the Targets screen (Section 4.8) when no Observatory location is configured: an empty-state placeholder with setup guidance, not an error.
- **Observing-date control (`WUT-090`):** a date picker in the screen's own criteria panel (defaulting to today, matching `rank_tonight`'s `night_date=None` default) sets the `night_date` passed into `rank_tonight`; changing it re-runs the full ranking (both Observability and Fit Score, since sky state itself changes with the date, unlike a Pier/train switch) rather than reusing the cached Observability Score set the `WUT-040` re-ranking path uses for a same-night Pier switch. A date outside the weather-forecast horizon is not refused — the affected tiles simply show the reduced-confidence badge already defined for a missing forecast (`WUT-030`), with no separate error state for this case.
- **Aurora/smoke advisory display (`WUT-100`):** since `aurora_estimate`/`smoke_estimate` are location-wide, not per-object, the screen fetches them once per selected date (alongside the weather forecast) and shows them in the criteria panel's date/location summary — a "Kp index: N, Smoke: <rating>" line — rather than repeating identical text on every tile; each ranked tile's own confidence badge (`WUT-030`) still reflects whether that night's estimates were available, same as it already does for weather. Where either is unavailable for the selected date, the summary line states that plainly (e.g. "Aurora: no data for this date") instead of omitting it silently.
- **Day/night band (`WUT-110`):** a graphic across the top of the screen, below the heading and above the criteria panel's effect on the results list — a colored band spanning the selected observing date's local calendar day (local midnight to local midnight), split into Night / Astronomical / Nautical / Civil Twilight / Daylight segments by the Sun's altitude, an hour axis above it, and solar noon/midnight tick marks, modeled on the reference day-length graphic commonly seen on sunrise/sunset sites. Backed by a new pure function, `galileo.planning.visibility.day_night_bands(location, date_str)` (itself built on a new `sun_altitude_track()`, a vectorized-astropy `get_sun` sample across one local day, the same batching technique `altitude_charts_batch` already uses) — segment boundaries are linearly interpolated between samples the same way `rise_transit_set` already interpolates its own horizon crossings, not just snapped to the sampling resolution. Unlike the rest of this screen, this graphic is independent of the magnitude/altitude/catalog ranking criteria, so it recomputes on every date change and on Rank Tonight, not only the latter; it degrades to a plain "set the Observatory's location" placeholder with no Observatory location configured, the same convention every other location-dependent element on this screen already uses. A single-hue sequential color ramp (dark navy through pale blue) encodes the five segments in their natural brightness order; the legend below the band still names each segment in text (never color-alone) and states its clock-time range(s) and total duration, since a segment's label can recur within one day (e.g. Night before dawn and again after dusk).
- **Libraries:** Qt widgets, consistent with `galileo.planning.sky_atlas`'s tile-based results list (Section 4.8) — no new dependency.
- **Current implementation:** built in `galileo/ui/app_window/_whats_up_page.py` (`AppWindowWhatsUpPageMixin`), following this package's per-page-mixin convention (Section 4.4b) rather than a separate `galileo.ui.whats_up` module — every other Planning sub-page (`_planning_page.py`, `_star_atlas_page.py`, ...) is organized the same way, so a standalone module for this one screen would have been the odd one out. Registered as `PLANNING_ITEMS`'s first entry (`_common.py`, `WUT-070`) and the `"whats_up"` builder in `_build_primary_nav`'s Planning submenu map (`_core.py`), with a new flat-icon glyph (`galileo/ui/icons.py`, three ascending bars). A criteria-panel date picker (`QDateEdit`, defaulting to today, `WUT-090`), a max-candidate-magnitude spin box, a min-altitude spin box, and the Messier/Caldwell/NGC catalog checkboxes (reusing `SKY-020`'s own catalog-membership logic) sit above a **Rank Tonight** button; results are one tile per `Recommendation`, built with the same tile/action-button code shape as `_planning_page.py`'s `_build_result_card` (Section 4.8) — a deliberate, small duplication rather than factoring out a shared helper, matching the level of duplication already between this codebase's other pages. **Bounding the pre-filter (`WUT-010`):** unlike `SkyAtlas.filter`'s own magnitude/type checks, `compute_observability` (Section 4.8a) calls `astropy`'s `altitude_chart` per candidate, so `run_rank()` pre-filters via `SkyAtlas.filter(max_magnitude=..., catalogs=...)` (cheap — no altitude computation) and caps the result at `_MAX_CANDIDATES` (300) before ranking, then shows only the top `_MAX_SHOWN` (50) — the same "bound before the expensive per-object computation" precedent the Targets page's own up-to-200-shown cap already sets (Section 4.8), just applied earlier here since ranking, unlike a plain search, always touches every pre-filtered object rather than only the ones actually displayed. **Thumbnails, cache unbounded / network bounded:** `run_rank()` fills every shown tile's `_ClickableThumbnail` slot from `SkyAtlas`'s on-disk thumbnail cache (`_cached_thumbnail`/`_thumbnail_field_arcmin`, Section 4.8's `SKY-080`) first — a plain file read, so there is no reason to bound it, and an object thumbnailed elsewhere (e.g. selected on the Targets/Planning page) shows its image immediately regardless of where it lands in the ranked list. Only the tiles left without a cache hit fall back to a real `SkyAtlas._fetch_thumbnail` network request (same hips2fits call the Targets page's own auto-fill uses, Section 4.8), and only that fallback is capped at `_MAX_AUTO_THUMBNAILS` (12), so a long ranked list can't fire an unbounded number of network requests — the remaining uncached tiles beyond the cap simply stay blank. Neither `WUT-010`–`100` nor the Project Scope Document's `WUT` domain row require a thumbnail; ranking's own no-network-dependency property (beyond the today-only advisory fetch below) now has this one bounded exception, matching the Targets page's already-established behavior rather than being stricter than it for no reason. **Imager field-of-view display:** a line above the results list states the active train's field of view in arcminutes (`_imager_fov_arcmin()`, derived from the same plate-scale/sensor-geometry inputs `recommend._fit_for_train`'s field-of-view fit check already uses, kept display-only in this module rather than added to `FitScore`) — or why it couldn't be computed (no active train, or one with no camera pixel-size/sensor-geometry configured) — each time Rank Tonight runs, so the "fits field"/"needs a mosaic" reasons on individual tiles have a stated reference size. Each tile's subtitle also shows the object's own `size_arcmin` next to its magnitude, the same format the Targets page's result tiles already use (Section 4.8). **Optical-train bridging:** the active optical train isn't a `galileo.equipment.profiles.OpticalTrain` anywhere in the running app — Equipment > Optics persists tubes as `OpticalTubeRecord` rows with a separately-persisted camera `DeviceConfigRecord` (`PROF-100`/`PROF-120`, Section 4.4), not that dataclass — so a local `_optical_train_for_fit()` helper reads the active tube (`AppWindow.active_optical_tube()`) plus its associated camera slot's sensor geometry and constructs a throwaway `OpticalTrain` instance from them, purely to hand `galileo.planning.recommend` (Section 4.8a) the shape it expects; `galileo.planning.recommend` itself stays unaware of the Optics/DeviceConfig persistence models, preserving the ports-and-adapters rule that domain core doesn't import persistence. **Advisory fetch, today only (`WUT-100`):** `_fetch_advisories()` constructs a page-local `galileo.safety.SafetyMonitorService` with an `OpenMeteoClient` as its forecast client (`SAFE-050`, already implemented) but no Kp/smoke client — none exists anywhere in the codebase yet, `SAFE-090`/`SAFE-100` being P3 with no concrete client built (Section 4.16's own "stubbed" pattern, mirroring Telescopius in Section 4.8) — so `get_aurora_advisory()`/`get_smoke_advisory()` correctly return `None` today, which `WUT-030`'s confidence badge already handles; wiring a real client to a shared `SafetyMonitorService` later needs no change here. Advisories (and the forecast) are fetched only when the selected date is today — the Open-Meteo client has no historical/future-date support (`forecast_days=1`) and neither hypothetical client would either, so any other date is simply "unavailable," which is exactly `WUT-030`'s existing degradation path rather than a special case. `_fetch_advisories()` passes the active Observatory's own latitude/longitude into `get_forecast_advisory()` (Section 4.16) — a fix alongside this display work, since that call previously carried no coordinates at all and so silently forecast latitude/longitude 0,0 for every Observatory. **Advisory detail, not just presence:** the advisory line no longer just says "available" — `_weather_summary_text()` parses the forecast's hourly `cloudcover`/`precipitation`/`windspeed_10m` arrays into an average/peak cloud cover, total precipitation and peak wind for the fetched window (degrading to "no usable detail" rather than raising on anything missing/malformed, so a summarization bug can't break ranking); `_aurora_summary_text()`/`_smoke_summary_text()` add the fixed reference bands (Kp quiet/unsettled-active/storm at 3/5; AQI good/moderate/unhealthy-for-sensitive/unhealthy/very-unhealthy/hazardous at the standard EPA breakpoints) next to each raw number, so the line reads as actual conditions rather than a bare figure.
- **Satisfies:** `WUT-010`, `WUT-020`, `WUT-030`, `WUT-050`, `WUT-060`, `WUT-070`, `WUT-090`, `WUT-100`, `WUT-110`.

### 4.8c `galileo.library.integration_time` — Prior Integration Lookup (`WUT-050`)

- **Responsibility:** `prior_integration_hours(object_name) -> float | None` — the read-only Library catalog query behind `WUT-050`'s per-entry annotation, not a new Library capability of its own. Sums `fitsFile.fitsFileExpTime` for every non-soft-deleted `"LIGHT FRAME"` row matching `fitsFileObject == object_name` and returns hours, or `None` (not `0.0`) when nothing is catalogued for that name — the same "`None` means no data, not a zero reading" distinction `galileo.safety`'s aurora/smoke advisories now make (`WUT-100`, Section 4.16). Returns `None` on any database error too, rather than raising, since a failed lookup must never block the ranked list (`WUT-050`).
- **Key design:** A small standalone module (`galileo/library/integration_time.py`) rather than added to the vendored AstroFiler `galileo.library.core` package (Section 4.23) — it is a new, Galileo-native read path over the existing catalog schema, not part of AstroFiler's original ingest/calibration/quality code. Re-exported from `galileo.library` (`__init__.py`) alongside `LibraryRegistrar`. Consumed by `galileo.ui.whats_up` (Section 4.8b) as the `library_lookup` callable passed into `rank_for_train`/`rank_tonight` (Section 4.8a) — display only, per that function's own contract.
- **Satisfies:** `WUT-050`.

### 4.9 `galileo.planning.framing` — Framing Assistant

- **Responsibility:** A contextual tool, not a primary-navigation panel (`FRAME-070`) — invoked from `galileo.ui.imaging`'s Framing… control (Section 4.5, `IMG-180`) or a Session Image block's own Framing… control (`galileo.ui.sessions`, Section 4.6a, `SES-130`), and closed back to whichever opened it. FOV overlay, sky-survey/offline star-field background, rotation preview (rotator-gated), Compare Cameras multi-rig overlay, mosaic panel grid definition with a shared configurable overlap, constellation/grid overlay, and the round-robin mosaic capture execution model.
- **Key design:** FOV rectangle computed from the active `CameraPort`/`MountPort` capability data (sensor size, focal length) already held by the device abstraction layer, so it stays in sync with whatever equipment is actually connected. The rotation control (`FRAME-030`) is never disabled: with the active optical train's `RotatorPort` connected, accepting the change drives it to the requested angle; with none connected, the tilt can't be physically achieved, so it's instead covered by an automatically-sized mosaic of un-rotated panels spanning the tilted rectangle's axis-aligned bounding box — an explicit mosaic grid the user set themselves takes priority over this fallback. Constellation/grid rendering (`FRAME-060`) is informed by AstroLlama's `generate_constellation_map_tool.py`/`generate_map_tool.py` (ADR-004, Section 2.7).
- **One design, two callers, independent state:** both entry points render the same view and share every `FRAME-*` requirement, but a framing/mosaic definition belongs to whichever context created it — the Imaging tab's own current immediate-capture setup, or a specific Session Image block's stored definition (persisted with the rest of that block's parameters, `galileo.ui.sessions`, Section 4.6a) — there is no shared/global framing state between them.
- **Compare Cameras (`FRAME-080`):** iterates every camera configured on every Pier in the current Observatory (via `galileo.observatory`, Section 4.4a, not just the active Pier), computing each one's FOV rectangle against the same displayed survey image and auto-scaling the image to the largest of them — a planning aid, not a capture-target selector.
- **Mosaic definition and capture (`FRAME-040`/`FRAME-050`/`FRAME-090`):** a mosaic is an N×M grid of panes plus a pane-overlap percentage read from a single shared setting on the Imaging settings screen (`IMG-170`'s kin), not duplicated per entry point. Whichever context owns the definition (an Imaging-tab run or a `SequenceRunner`-executed Image block, Section 4.6) captures it pane-major: one exposure per pane per pass through the whole grid, repeating the pass for additional exposures per pane, rather than exhausting one pane before the next — via the module-level `mosaic_capture_order(mosaic, exposures_per_pane)` helper (not a `FramingAssistant` method, since executing a mosaic needs only the already-built `Mosaic`, no optical-train state), so both callers order panes identically without either duplicating the walk. `galileo.ui.imaging` (Section 4.5) is wired to it today; `galileo.sequencer.basic` (Section 4.6a) is not yet (see that section's note). **This retires the earlier "each mosaic panel becomes its own sequencer target" design** — a mosaic is now a single target the owning context captures internally, never decomposed into separate per-panel targets upstream of capture.
- **Rotation determination (`FRAME-100`):** the dialog pre-fills the rotation field from whichever source already knows the sensor's position angle — a connected rotator's live position (`RotatorPort.get_status()["position"]`) takes priority as the current physical truth, else the Imaging tab's own `ImagingService.last_solve` (shared with Annotate, `IMG-200`) when it holds a successful solve. A Determine Rotation control plate-solves the Imaging tab's current frame when neither is available: it drives `ImagingService.solve_current_frame` (the same write-temp-FITS-and-solve plumbing `annotate_current_frame` uses, factored out so Annotate and Determine Rotation share it rather than duplicating it) off the Qt UI thread and reads `SolveResult.rotation_deg` back out of the solution into the rotation field, which then rotates the canvas's FOV rectangle the same way a manually-typed rotation does.
- **Satisfies:** `FRAME-010`–`FRAME-100`.
- **Current implementation:** the domain logic above (FOV, `RotatorUnavailableError`-gated `set_rotation_angle`, `rotated_frame_bounding_box_deg`/`mosaic_grid_to_cover_deg` for the no-rotator mosaic fallback, `MosaicPanel`/module-level `mosaic_capture_order`, `compare_cameras`/`FovSpec`, `mosaic_footprint_deg`, and the `open_from_imaging_tab`/`open_from_session_image_block` entry-point functions) is built in `galileo.planning.framing`, and the Imaging tab's own Framing… control (`IMG-180`) is wired to it via `AppWindow._open_framing_dialog`: a modal with the parameter form beside a self-painted `_FramingCanvas` showing a DSS2 color survey-image cutout (`_fetch_hips_cutout_sync`, via the CDS hips2fits service — the Obsy-ported technique as `galileo.planning.sky_atlas`'s thumbnail fetch, ADR-005, retargeted from the STScI dss_search CGI to hips2fits since dss_search caps cutout size and hips2fits doesn't; cached to the user cache directory for the offline/cached mode) with the FOV rectangle — or every pane's rectangle, for a defined mosaic grid — overlaid; rotation and mosaic-grid changes redraw the overlay immediately (no new fetch needed), while a new sky position refetches on the RA/Dec fields' `editingFinished` (deliberately not every keystroke, to avoid a network call per edit) rather than a dedicated Load Sky Image button, which `FRAME-100`'s Determine Rotation control now occupies instead. The pane-overlap setting (`MosaicSettings`) is a process-wide in-memory singleton, not yet backed by a persisted Options > Imaging field (`IMG-170`'s kin, per the Mosaic definition note above). The Session Image block's own Framing… control (`SES-130`) is not wired up at all yet, including `FRAME-100` — see Section 4.6a's note below.
- **Mosaic capture execution from the Imaging tab (`IMG-180`, `FRAME-090`):** `ImagingService.run_mosaic_from_framing` previously only recorded the mosaic (`active_mosaic`) with nothing that ever read it back — Capture always took a single-position series regardless. `ImagingService.capture_mosaic` now walks `mosaic_capture_order(active_mosaic, exposures_per_pane)`: for each step it slews the mount (set on `ImagingService._mount`, mirroring how the page already refreshes `_camera` before a run; precessed J2000→JNow via the same `galileo.planning.star_atlas` helpers `AppWindow._mount_to_object` uses, when the connected mount isn't J2000-native) to that pane's centre, waits for the slew with `galileo.tracking.wait_for_slew`, then exposes via the existing `capture_and_preview`/auto-save-to-Library path — the re-slew between passes is the dither, so no separate guider-dither command is sent, matching the design above. `_MosaicCaptureThread` (mirroring `_CaptureThread`) runs it off the Qt UI thread; `do_capture()` branches into it whenever `active_mosaic` is set, refusing (a `QMessageBox`, not a silent single-frame fallback) when no mount is connected. **Visual indication (reported as missing):** the Imaging page shows a status line ("Mosaic active — C×R panels (N total)…") and switches Capture's own label to "Capture Mosaic" whenever a mosaic is active, so it's visible before Capture is pressed that the whole grid will be shot pane by pane rather than a single frame; a Clear Mosaic button (next to Framing…) discards it. ### 4.9a `galileo.ui.skymap` — Interactive Star Map / Planetarium (KStars/EKOS-informed)

- **Responsibility:** Live, rendered, pannable/zoomable sky view distinct from `galileo.planning.sky_atlas`'s catalog/list UI and `galileo.planning.framing`'s FOV-preview UI (Project Scope Document, Section 6.6). Click-to-identify, double-click-to-track, constellation/grid overlay, comet/asteroid/satellite rendering, live FOV/pointing overlay, slew-to-clicked-location.
- **Key design:** Rendered via a `QGraphicsView`-based canvas (consistent with `galileo.ui.imaging`, Section 4.5) rather than a second GUI toolkit; star/DSO rendering reads from the same bundled catalog database as `galileo.planning.sky_atlas` (Section 4.8) rather than a separate one. FOV/pointing overlay (`SKYMAP-050`) shares geometry computation with `FRAME-010`, and slew-to-clicked-location (`SKYMAP-060`) issues the same `MountPort.slew_to_coordinates()` call the equipment panel uses — no separate command path.
- **Libraries:** `astropy.coordinates` (coordinate transforms, shared with `galileo.planning.sky_atlas`), Qt Graphics View framework.
- **Current implementation (Star Atlas section):** the first slice is a `QPainter`-drawn widget (`galileo.ui.star_atlas.StarAtlasView`) over plain-numpy sky maths (`galileo.planning.star_atlas`: precession, sidereal time, alt/az, stereographic `Viewport`), not yet the `QGraphicsView` canvas described above — projecting a few thousand points per frame with numpy and painting them directly was simpler than managing a scene-graph item per star. Stars come from the Yale Bright Star Catalogue (VizieR `V/50`, cached in the user cache directory, with a small built-in named-star fallback offline); deep-sky objects come from the Sky Atlas catalog; Sun/Moon/planets from astropy's built-in ephemeris. Constellation boundaries come from the Delporte catalogue (VizieR `VI/49`, B1875 vertices densified along constant RA/Dec, then precessed to J2000). Implements `SKYMAP-010` and `SKYMAP-020`, and the boundary half of `SKYMAP-030` (figures/art are not built); `SKYMAP-040`–`SKYMAP-060` are not yet built. **Click-to-identify only selects, it never creates a session:** a plain click (left, double, or right) selects an object and makes it the Pier's current object (`IMG-140`) via `AppWindow._set_current_object`, but that method used to also auto-create a session for it — reported as "incorrect," since a plain click then looked identical to deliberately building a session. Session creation is now exclusively an explicit **Add to Session** action, added to the right-click context menu (`StarAtlasView.contextMenuRequested` → `AppWindow.show_context_menu`, alongside the existing Goto/Sync), going through the shared `AppWindow._add_to_session(name, ra_deg, dec_deg)` (`SES-160`) — the same entry point the Targets page's own Add to Session tile button uses. `SKYMAP-070` (horizon obstructions) is built: an Observatory's uploaded azimuth/altitude pairs are kept in the `horizon_points` table (migration `015`), interpolated by `galileo.planning.visibility.HorizonProfile` (linear, wrapping through north) and shaded translucent red by `StarAtlasView` under the page's "Horizon" checkbox. `SKYMAP-080` is built as `galileo.core.slew_guard.SlewGuard`, a process-wide guard the INDI and Alpaca mount adapters consult in `slew_to_coordinates`/`slew_to_altaz`, so the Mount page, Star Atlas Goto, sequencer, plate-solve centring and meridian flip are all covered by one check; it raises `SlewObstructedError` and is off until Options > Planning enables it. A coordinate slew is converted to altitude/azimuth at the Observatory's latitude/longitude, treating the coordinates as of date; a slew is checked at its destination, not along its path. `SKYMAP-090` (telescope reticles) is built in `StarAtlasView.set_pier_markers`/`_draw_pier_markers`, fed by `AppWindow.pier_markers`: one labelled reticle per Pier of the current Observatory, drawn at the mount's live pointing (converted to J2000) where `AppWindow._poll_pier_pointing` could read it on its worker thread, and otherwise at the Pier's current object (Section 4.5, `IMG-140`). Polling is page-visible only and runs faster while a mount reports slewing, which is what makes a slew watchable; this also covers the pointing-overlay half of `SKYMAP-050`, whose FOV rectangle is still unbuilt. Because the Equipment pages hold connections for the selected Pier only, the other Piers' reticles normally show their target rather than a live position.
- **Satisfies:** `SKYMAP-010`–`SKYMAP-090`.

### 4.9b `galileo.scheduler` — Observatory Scheduler (KStars/EKOS-informed)

- **Responsibility:** Multi-night/multi-target job queue: per-job altitude/moon/twilight/horizon constraints, startup/completion conditions, weather-gated execution, priority-based preemption, multi-night progress tracking. Distinct from and layered above `galileo.sequencer.basic`/`galileo.sequencer.advanced` — a job doesn't duplicate sequence-execution logic, it *triggers* an existing `SequenceRunner` when its constraints are satisfied. **Current implementation:** this triggering doesn't exist yet — `SchedulerJob.sequence` holds the `SessionRegion` (`galileo.ui.sessions`) it was scheduled from, not a `SequenceRunner`/`SequenceDef`, and nothing currently starts execution from a job becoming runnable; progress (`frames_captured`) only advances via an explicit `record_frames_captured()` call, which today only this module's own tests drive. Consistent with the Sessions screen's own scope boundary above — the job queue's authoring/lifecycle (`SCHED-010`–`100`) is built; triggering real capture from it is the same deferred execution-engine work.
- **Key design:** A `SchedulerJob` references a target, a sequence definition, and a Pier/optical train; constraint evaluation reuses `galileo.planning.sky_atlas`'s visibility service (`SKY-030`) rather than a separate ephemeris path. Weather-gating subscribes to the same unsafe-state event bus `galileo.safety` publishes to (`SAFE-010`) — the scheduler is a consumer of that event, not a second safety authority. The replanning algorithm (`SCHED-070`) is a continuously-reevaluated priority queue (EKOS's own "Greedy Scheduling" approach is the direct precedent — Project Scope Document, Section 6.6); this is explicitly P2, so v1 can ship with static (non-preempting) priority ordering and add continuous replanning after. One `galileo.scheduler` job queue exists per Pier; `galileo.observatory` (Section 4.4a) is what lets several of these run side by side and coordinates the shared-resource constraints (e.g. a shared dome) between them (`OBS-070`) — this module itself stays single-Pier and unaware of Observatory grouping, consistent with the layering elsewhere in this design. **Completion (`SCHED-050`):** `ObservatoryScheduler.reap_completed_jobs()` removes every job whose completion condition is satisfied and deletes the `SessionRegion` it came from (`job.sequence`, per `SES-210`) — called by both Sessions' and the Schedule screen's (Section 4.9c) own `reload()` rather than a dedicated background poller, since neither screen needs faster-than-reload freshness for this.
- **Reopened gap — no priority/constraint/condition-editing UI, no trajectory chart (user's call, `galileo.ui.scheduler` removed):** the `Planning > Scheduler` table screen (priority reordering, an Edit… dialog for `JobConstraints`/startup/completion conditions, and a `SCHED-080` altitude-trajectory chart per job) was removed outright rather than folded into the Schedule timeline screen (Section 4.9c), which only edits a job's timeline placement (start/end/duration). `SCHED-020`'s "modified" clause, `SCHED-030`/`040`/`050`'s constraint/condition editing, and `SCHED-080`'s chart display are consequently unimplemented at the UI layer again — the domain-level `JobConstraints`/`StartAtTime`/`RepeatNTimes`/`get_job_trajectory_chart` machinery and its tests are untouched, so `SCHED-010`–`100` stay satisfied at the domain level (RTM's own verification column already points there, not at either screen), but nothing in the running app lets a user actually reach this editing/charting today. Priority ordering/removal itself is still reachable (Schedule's own Remove, plus each job's `priority` field, unedited, still governs `get_ordered_jobs()`).
- **Libraries:** `peewee`/`peewee-migrate` — job/progress persistence (`SCHED-100`) lives in the same shared database as `galileo.library` (ADR-002, and the Data Design table in Section 5) via `SchedulerJobRecord` (`galileo.library.models.scheduler`), not a separate file. `ObservatoryScheduler.set_persistence(pier_name)` scopes an instance to its Pier's rows (one queue per Pier, per the Key design note above); `save()`/`load()` (and every queue mutator — `add_job`/`remove_job`/`move_job`/`update_job`/`reap_completed_jobs`/`record_frames_captured`, which all call `save()`) are a no-op until `set_persistence` is called, matching every pre-existing test that never enabled persistence. `AppWindow._scheduler_for_pier` enables it (keyed by Pier name) and loads once at first use, so a Pier's queue now survives an application restart, closing the previous "no separate-file migration ever reached the real app" gap along with the storage-format one. Constraints and startup/completion conditions round-trip too (as small JSON blobs on the row) — the pre-Peewee JSON `save()`/`load()` silently dropped them, and the separate, never-read-back `set_progress_store()`/`_flush_progress()` path (a second, redundant JSON file) is retired in favor of one `save()`/`load()` pair.
- **Satisfies:** `SCHED-010`–`SCHED-100`.

### 4.9c `galileo.ui.schedule` — Schedule Calendar Screen

- **Responsibility:** A per-Pier calendar view over the same `ObservatoryScheduler` queue Section 4.9b manages — placement/duration/conflict-visibility on top of the queue's priority/constraint/completion model, not a second scheduler. The only UI onto that queue now: the earlier `Planning > Scheduler` table screen (`galileo.ui.scheduler`, priority order/progress table, Edit… dialog, trajectory chart) was removed outright once this screen existed (see 4.9b's "Reopened gap" note) rather than kept alongside it.
- **Key design:** A multi-day calendar grid (`_CalendarCanvas`): one column per observing night, a shared hour axis down the left, and a mini `QCalendarWidget` in the left rail for jumping to a start date — a deliberately more calendar-like layout than the single-day timeline this replaced (user's call). The axis runs dusk (top) to dawn (bottom), not a plain midnight-to-midnight calendar day — a calendar day's own Sun-altitude track carries a night split across both its edges (the pre-dawn tail at the top, the post-dusk start at the bottom), which would draw as two disconnected dark bands instead of one; the shared window is instead `_shared_night_window()`'s widest sunset-to-sunrise span (`_night_window_hours`, via `sun_altitude_track`, padded 1h) across every visible night when the active Pier's Observatory has a latitude/longitude configured, or a fixed 17:00–07:00 default otherwise, so night sits centered in every column. A job's calendar column follows the same evening-owns-its-night convention (`_night_column_and_hour`): hour-of-day >= noon belongs to that date's night, earlier hours belong to the *previous* date's night (its early-morning tail) — and a job scheduled outside the shared window entirely (a genuinely daytime task) still renders, pinned to whichever edge is closer, rather than vanishing from a screen that is deliberately night-focused. There is no side palette of block *types* to drag from (the earlier design's `SessionsPageWidget`-style layout, removed along with it): the five standalone pier-level operations that make sense run outside any session — `DomeOpenBlock`, `DomeCloseBlock`, `DomeSyncBlock`, `ParkMountBlock`, `UnparkMountBlock` (all already defined in `galileo.ui.sessions`, SES-140) — are placed instead via an "Add Pier Operation" entry on the grid's own right-click menu, at whatever day/time was clicked; this still creates a `SchedulerJob` with `sequence=None` and `kind="pier_op"` rather than a new block type, so calendar entries stay one model. A session's own Schedule control (`SES-200`) gives its `SchedulerJob` the same timeline placement fields: `SchedulerJob.scheduled_start_utc`/`scheduled_end_utc`/`duration_minutes` (all optional; unset means "unpositioned, left for the autoscheduler," `SCHED-120`) and `run_state`/`run_log` (`"pending"`/`"running"`/`"completed"`/`"error"`, `SCHED-140`). The grid is a custom-painted `QWidget` (no `QGraphicsView` needed); a block's height is `duration_minutes` (default 60 when unset) mapped to the current zoom (pixels/hour, adjustable via Zoom In/Out), its vertical position is `scheduled_start_utc`'s hour-offset into its night, and its column is that night's own date — concurrent same-night entries pack into side-by-side lanes within their column. A job with no start at all is itself a small draggable block (`_UnscheduledBlockWidget`, a `QDrag` source) in a separate "Unscheduled" tray below the grid; dragging it onto the grid (`_CalendarCanvas.dropEvent`, reading `SchedulePageWidget.dragging_job` — the same "what's being dragged" side-channel role the removed palette's `currentItem()` played) is how it gets a start time in the first place, exactly like dragging an already-positioned block to move it. Right-click on a block opens a small dialog (mirroring `session_block_dialogs`' pattern) to set/clear start, end, and duration; dragging a positioned block to a new day/time position rewrites `scheduled_start_utc` (and `scheduled_end_utc` when duration is held fixed). Each column is shaded by that night's own Sun altitude (`sun_altitude_track`, remapped to a continuous daylight-to-astronomically-dark gradient — Theme.RED, UI-011, renders this red-only instead) and labelled with that night's Moon phase (`moon_phase_info`, added to the same module) when a location is configured — a "Show Almanac Shading" checkbox toggles it, and a "Show Past Events" checkbox reveals otherwise-hidden entries whose window has already elapsed (most such entries are pier-ops, which — unlike sessions — are never reaped once their `run_state` settles, per `reap_completed_jobs`' own `is_complete` gate in Section 4.9b). Conflict detection (`ObservatoryScheduler.overlapping_jobs(job)`) is a same-Pier, same-time-window check only — the cross-Pier "one Pier's dome request loses to another Pier's active imaging" rule described in the PSD is real-time execution arbitration, which (like triggering itself, Section 4.9b) is deferred; today a cross-Pier collision is neither auto-ignored nor flagged, it simply isn't evaluated. The **Run** control added to each Sessions-screen region (`SES-110`) calls `SessionRegion.run_now()`, which schedules the session (same path as Schedule) with `scheduled_start_utc` set to "now" and reports `overlapping_jobs()`'s result to the user in a warning dialog rather than blocking the action (`SCHED-150`) — conflicts are surfaced, not resolved automatically. **Autoschedule** (`SCHED-160`, P3) is a top-bar button with no handler behind it yet, deliberately: automatic placement needs the same visibility/constraint machinery `SCHED-070`'s replanning does, and is out of scope until that lands.
- **Libraries:** Qt Widgets/`QPainter` only, the same self-painted-widget approach as `_AltitudeChart` (Section 4.8, `galileo.ui.app_window._widgets`); no new dependency.
- **Satisfies:** `SCHED-110`–`SCHED-160`.

### 4.10 `galileo.calibration` — Flat Wizard / Calibration

- **Responsibility:** Automated flat/dark/bias *capture* routines during a live session, flat-panel integration, target-ADU convergence, and Sky Flats (`CAL-070`): a twilight-gated, mount-directed variant of the same adaptive-exposure idea that needs no flat panel. Master-frame *creation* and *application* to light frames is a repository-time operation and lives in `galileo.library` (Section 4.23), not here — this module only produces the raw calibration exposures (Sky Flats additionally files each one into the Library's repository as it's captured, via `LibraryRegistrar.register_capture` — see below; `CAL-010`–`CAL-050`'s older flat-wizard/dark/bias routines still only write to `_output_dir` and don't register with the Library, unchanged by this revision).
- **Key design:** An iterative exposure-time (or brightness) search loop against the `CameraPort`/`FlatPanelPort`, with a bounded iteration count and explicit failure reporting rather than an unbounded retry loop. Captured calibration frames are handed off to `galileo.library` for session linking and master-frame creation.
- **Sky Flats (`CAL-070`):** `CalibrationService.run_sky_flats_all_filters`/`run_sky_flats` add a `MountPort` dependency and an `ObservingLocation` (`galileo.planning.visibility`, which also gained `sun_altitude_deg`/`is_twilight`/`altaz_to_radec_deg` for this). The run refuses to start outside the local civil-through-astronomical twilight band (`is_twilight`, 0° to -18° solar altitude), then slews to a fixed East, high-altitude vantage point (`SKY_FLAT_ALTITUDE_DEG`/`SKY_FLAT_AZIMUTH_DEG`, converted to the moment's RA/Dec via `altaz_to_radec_deg`) and disables tracking, so any star in frame trails into a faint streak instead of staying a sharp point that would bias the ADU reading. One convergence loop (`_converge_sky_flat_exposure`) is reused both to find the starting exposure and to re-check/retake every one of the requested frames, since twilight brightness keeps drifting during the run — each attempt's average/median ADU (the dialog's Method field) is compared against a configured fraction (50% default) of the camera's Max Well Depth (a new `device_configs.max_well_depth` field, set on Equipment > Camera), moving the exposure by a ratio-based step floored at one Exposure Increment (the dialog's own field) so the search doesn't stall near zero ADU. The Filter field's All option repeats the capture set across every filter in one run, without re-slewing between them. A cooperative `stop_requested`/`request_stop()` flag (checked between exposures and between filters, never mid-exposure) backs the Flats Assistant dialog's Stop button. Every saved frame is immediately handed to `galileo.library.registrar.LibraryRegistrar.register_capture` (`_register_with_library`, logged not raised on failure) — the same call a manual Imaging-tab capture uses — so a Sky Flats run files itself into the repository as it goes rather than needing a separate import step; `_save_frame` now also writes `DATE-OBS`, which the Library's ingest validator requires and the pre-existing calibration writers never supplied.
- **Satisfies:** `CAL-010`–`CAL-050`, `CAL-070`, `NFR-USE-020`. (`CAL-060` and `CAL-080`, the Imaging-tab placements of the Flats Assistant and the Darks Assistant UI respectively, are satisfied by `galileo.ui.imaging`, Section 4.5, whose Flats… and Darks… buttons open their respective dialogs in `galileo.ui.app_window._flats` and `galileo.ui.app_window._darks`; this module stays UI-free.)

### 4.11 `galileo.autofocus` — Autofocus Service

- **Responsibility:** HFR sampling across focuser positions, curve fitting, best-focus move + confirmation, per-filter offsets, manual/triggered invocation, aberration inspection.
- **Key design:** Star detection/HFR computation for each sample runs in the process pool (Section 2.3); curve fitting (`scipy.optimize`) selects among configured fit models; a run's sample points and fit are recorded for `HIST` review. The Aberration Inspector (`FOC-080`, KStars/EKOS-informed — Project Scope Document, Section 6.6) reuses the same HFR-computation pipeline, applied per-region (3- or 4-point) across a single frame rather than across focuser positions, to surface sensor-tilt/collimation indicators.
- **Libraries:** `numpy`, `SEP` (star detection — unified with `galileo.ui.imaging` and `galileo.library` per ADR-002, superseding the `photutils` choice in earlier drafts of this document; the VSTarget plugin reintroduces `photutils` for aperture photometry, a distinct problem SEP doesn't attempt — see [`docs/plugins/vstarget/SDD.md`](../plugins/vstarget/SDD.md) Section 2.1), `scipy` (curve fitting).
- **Focus screen (`FOC-090`):** `AutofocusService` reports a run on the event bus (`FocusStartedEvent`, one `FocusFrameEvent` per measured exposure carrying the frame, star count, HFR and FWHM, and `FocusCompleteEvent` however the run ends) instead of being called by the UI, so the screen in `galileo.ui.focus` follows a run started by a sequencer trigger exactly as it follows one started from the screen, and redraws only between a run's start and end events. Its handlers run on the autofocus thread; they prepare the preview there and pass it to the UI thread through queued signals. Every published event carries a `pier_key` (from a constructor argument of the same name), since `FocusPage` keeps one `AutofocusService` per Pier and is itself a single instance subscribed to the process-wide bus — without it, two Piers running autofocus at once would have their events cross-contaminate each other's V-curve (Section 4.4b).
- **Satisfies:** `FOC-010`–`FOC-090`.

### 4.12 `galileo.platesolve` — Plate Solving

- **Responsibility:** Invoke configured external/local solvers, solve-and-sync, solve-and-center iteration, failure reporting.
- **Key design:** Each solver backend (ASTAP, local astrometry.net, etc.) implements a common `SolverAdapter` interface (subprocess invocation + result parsing) behind the async I/O bridge, so adding a solver is an adapter, not a core change. The ASTAP `SolverAdapter` is adapted directly from AstroLlama's `astap_plate_solve_tool.py` (ADR-004, Section 2.7), including its path-traversal-safe filename validation.
- **Solving details:** ASTAP is given the mount's position as a search hint (`-ra`/`-spd`/`-r`) whenever it is known: a blind search of a sparse field can match the wrong patch of sky, and the search is slower. A solve is read from ASTAP's `.ini` result file, which it writes for success and failure alike — on failure ASTAP exits non-zero with nothing on stderr, so the reason (`ERROR=…`) is only there. `PlateSolver.solve` publishes `SolveStartedEvent` and `SolveCompleteEvent` on the event bus for every solve.
- **Solve screen (`PLT-070`):** `SolveWorkflow` (capture → solve → sync, or sync-then-slew-to-target repeated until within the requested accuracy) is domain-core: it drives the camera, mount and solver through their ports and reports progress through a log callback, and `stop()` cancels it from any thread, aborting the exposure and any slew. The screen in `galileo.ui.solve` does not call the solver; it follows the bus events, so it shows a solve started by any other workflow (variable-star analysis today; sequencer centring and meridian-flip recentring once they use the solver) exactly as it shows its own. The handlers run on the solving thread, gather what the screen needs there (the frame, the nearest catalogue star) and hand it to the UI thread through queued signals. While the screen is not in view it decodes and draws nothing and does not poll the mount; the results are still recorded, and it catches up from them when it is shown. `PlateSolver` carries an optional `pier_key`, published on `SolveStartedEvent`/`SolveCompleteEvent`, so `SolvePage` can attribute a completed solve's target/error-offset back to the Pier whose own `SolveWorkflow` actually ran it (`_workflows` is per-Pier, Section 4.4b) even while a different Pier is on screen; the results table and live preview stay deliberately global across every Pier regardless of which one solved — that is this screen's documented behavior (see the first sentence of this bullet), not something scoped per Pier.
- **Polar alignment (`PLT-080`):** `galileo.polaralign` is domain-core and builds on `SolveWorkflow`, reusing its capture, solve and slew steps; its method follows KStars/Ekos' `PolarAlign`. The mount is fixed to the Earth, so in the Earth-fixed horizon frame (x north, y east, z up) a camera on the mount moves on an exact circle about the RA axis, tracking or not. `PolarAlignWorkflow` therefore solves three frames, turning the mount a set number of degrees in RA between them, converts each solve to altitude/azimuth at its own mid-exposure time (raising the altitude by refraction unless disabled), and `fit_rotation_axis` takes the normal of the plane through the points (least-squares for more than three). It needs no knowledge of how far the mount really turned, so it does not depend on the mount's own RA readout. `polar_error` compares that axis with the geometric pole (refraction does not move the target) and returns the total angular distance and the altitude and azimuth errors, the azimuth both along the sky and as the rotation the mount is turned through (altitude positive when too high, azimuth positive when east of the pole, sign-corrected for the southern hemisphere). After measuring, the workflow keeps solving at the final position. `knob_adjustment` finds the smallest pair of turns, about the east-west horizontal axis (altitude knob) then the vertical (azimuth knob), that carry the third measuring position (first rotated about the axis by the mount's tracking since, `tracking_angle`) onto the newly solved one, and `axis_after_adjustment` rotates the axis by the same pair, so the live figure is exact wherever the camera points, given a level mount. Before moving anything the workflow refuses a rotation that would cross the meridian (a flip would ruin the measurement; not checked within 2° of a pole) and logs when the mount turns less than 90% of what was asked. `galileo.ui.solve` runs it through the same per-Pier workflow slot, Stop button and bus-driven results table as Capture & Solve, and takes the site from the Pier's Observatory rather than from the mount, since a device call there would block the UI thread.
- **Satisfies:** `PLT-010`–`PLT-080`, `EXT-040`.

### 4.13 `galileo.meridianflip` — Meridian Flip

- **Responsibility:** Flip-time computation, automatic pause/flip/resume, post-flip re-center and guiding restart.
- **Key design:** A domain-core service subscribed to the mount's tracked position via the event bus; on limit approach it emits a sequencer-pausable event consumed by `galileo.sequencer.advanced`'s Meridian-Flip-on-Trigger block (`SES-320`).
- **Satisfies:** `MFLIP-010`–`MFLIP-040`.

### 4.14 `galileo.guiding` — Guiding Integration

- **Responsibility:** External guider connection, start/stop, dither + settle wait, guide-error reporting, disconnect handling.
- **Key design:** A `GuiderAdapter` interface with a first-party PHD2-protocol implementation (JSON-RPC-over-TCP event stream) run through the async I/O bridge. Exactly one `GuiderAdapter` instance is owned per Pier (`GUIDE-060`), each connecting to its own PHD2 process/instance (typically a distinct host:port pair) — unlike `galileo.dome`/`galileo.safety`, this module has no Observatory-scoped mode at all: `galileo.observatory` (Section 4.4a) never fans a guiding command or event out across Piers, since one guiding application cannot reasonably guide more than one mount.
- **Guider screen (`GUIDE-070`–`GUIDE-090`):** `galileo.adapters.phd2.Phd2Adapter` is the PHD2 implementation of that interface — a socket plus one reader thread (the same shape as `galileo.adapters.indi_client`), so it works from the Qt thread, from the sequencer's asyncio loop and from tests alike. It matches PHD2's request replies to callers by JSON-RPC id (`request()` returns a future; `call()` blocks) and passes every unsolicited event (`GuideStep`, `StarLost`, `SettleDone`, …) to one callback. `GuidingService` feeds those events into a `GuideModel`, a lock-protected mirror of PHD2's state — app state, guide-step history, running RMS (Welford, since guiding started, in arcsec once PHD2's pixel scale is known), calibration points, the last guide-star image and an event log — and issues the screen's commands as non-blocking futures, logging any PHD2 rejects. `galileo.ui.guider.GuiderPage` never sees a PHD2 thread: a 250 ms timer takes a `GuideModel.snapshot()` and redraws only when the model's version changed, and polls the things PHD2 does not push (equipment-connected, the star cut-out) once a second while the page is visible. One `GuidingService` is kept per Pier record — the reference implementation of the per-Pier-keyed-dict pattern Section 4.4b later generalized to the Imaging/Focus/Solve screens and to Equipment device connections. PHD2 does not stream the full guide frame to network clients, so the page shows the guide-star cut-out (`get_star_image`) rather than the whole frame; PHD2 also has no per-axis RA enable or gain setting over the event server, so the page offers a Dec guide mode instead of the reference screen's RA/Dec direction check-boxes.
- **Satisfies:** `GUIDE-010`–`GUIDE-090`, `EXT-050`.

### 4.15 `galileo.dome` — Dome Control

- **Responsibility:** Azimuth slaving to mount position, shutter/park sync with sequence and meridian-flip events, slaving disable for third-party-controlled domes.
- **Key design:** A dome instance is owned either by a single Pier or, when `OBS-050` scopes it at the Observatory level, by `galileo.observatory` (Section 4.4a) — this module itself is agnostic to which, it just receives park/shutter commands and reports state to whichever module (Pier or Observatory) owns it, the same fault-isolated event-bus pattern used throughout.
- **Satisfies:** `DOME-010`–`DOME-030`.

### 4.16 `galileo.safety` — Safety & Weather Monitoring

- **Responsibility:** Poll safety-monitor/weather devices, apply configurable abort/warning policy, gate sequence resumption.
- **Key design:** Publishes unsafe-state events on the event bus, tagged with either a Pier ID or an Observatory ID depending on `OBS-030`'s scoping; the sequencer and dome modules subscribe independently rather than the safety module calling into them directly, keeping the fault-isolation property from `ARCH-060`. `galileo.observatory` (Section 4.4a) is what fans an Observatory-scoped event out to every member Pier (`OBS-040`) — this module doesn't need to know how many Piers are listening. The internet weather-forecast planning aid (`SAFE-050`, adapted from AstroLlama's `get_weather_tool.py` via Open-Meteo — ADR-004, Section 2.7) is deliberately kept out of the unsafe-state event path: it is display-only and cannot publish an abort event, preserving the connected safety-monitor device as sole authority over `SAFE-010`. The Watchdog (`SAFE-060`, KStars/EKOS-informed — Project Scope Document, Section 6.6) is **not reimplemented from scratch**: where an INDI server is in use, Galileo sends periodic heartbeats to INDI's own existing `indi_watchdog` driver, which independently parks the mount and closes the dome on timeout — this runs outside Galileo's own process, so it still protects against Galileo itself crashing or hanging. For Alpaca-only setups (no INDI server), a lightweight local watchdog thread provides the equivalent behavior directly against the Alpaca `MountPort`/`DomePort`.
- **Device-tier vs. internet-advisory trust tiers:** a general principle applied consistently across this module — **any connected Safety Monitor device**, Tier 1 (hardware, e.g. `SAFE-070`'s rain sensor via `indi-hydreon`) or Tier 2 (software-computed, e.g. an ML-based all-sky-camera cloud classifier, `SAFE-080`), is trusted as an input to automated abort decisions (`SAFE-010`), because both reach this module through the identical `SafetyMonitorPort`/`ARCH-010` path — this module has no code path that distinguishes them, by design, which is what `SAFE-070`/`SAFE-080` actually require. A Tier 2 device backend may be its own standalone INDI/Alpaca driver process, **or** an in-process device backend a plugin registers through `PLUG-010`, the same extension point every other device category already has (`ARCH-070`) — both are ordinary implementations of `SafetyMonitorPort`, so this module cannot tell, and does not need to, which one it's talking to. **Revised from an earlier draft**, which required a Tier 2 device to run as a standalone driver process specifically, reasoning that an in-process plugin would be a bypass of `EXT-020` — on reflection that conflated two different requirements: `EXT-020` governs how *core's own* INDI/Alpaca adapters connect to external drivers, while a plugin-registered device backend was always a legitimate, already-general extension point (`ARCH-070`/`PLUG-010`) for *any* device category, safety monitors included; singling safety out from that general rule was the actual inconsistency, not the fix. Whichever form a Tier 2 device backend takes, any debounce/hysteresis logic against a single borderline reading is that backend's own responsibility, not this module's — Galileo consumes only its already-settled state either way. An **internet API** with no device behind it (`SAFE-050` weather forecast, `SAFE-090` aurora, `SAFE-100` smoke) is a structurally different input — advisory-only, fetched directly by this module rather than through a device port, and structurally unable to publish an abort event, for the same reason `SAFE-050` is walled off. No Tier 2 device is implemented in this repository at present (Project Scope Document, Section 11, C8) — `SAFE-080` and this design note describe the pattern any future one must follow, not a specific product.
- **Libraries:** an Open-Meteo API client (weather forecast), a NOAA Kp-index/OVATION client (`SAFE-090`), a NOAA HMS smoke-polygon client (`SAFE-100`).
- **Current implementation:** `SafetyMonitorService.get_forecast_advisory(latitude=0.0, longitude=0.0)` forwards both straight to the configured forecast client's `get_forecast(latitude, longitude)` — added because its only caller (What's Up Tonight, `WUT-100`, Section 4.8b) was previously calling it with no coordinates at all, so every forecast request silently went to latitude/longitude 0,0 regardless of the Observatory actually configured; the default keeps the method callable with none, matching `OpenMeteoClient.get_forecast`'s own existing defaults.
- **Per-reading Weather-Station safety rules (`EQP-WX-020`, `EQP-SAFE-020`) — a fourth, distinct trust tier:** a Weather Station (`DeviceCategory.WEATHER_STATION`) is neither a Safety Monitor device nor an internet advisory — it is a connected sensor with no SAFE/NOT-SAFE state of its own in Galileo's device model, only readings. `WeatherSafetyRule` (`parameter`, `label`, `unit`, `safety_related`, `operator`, `threshold`) and `evaluate_weather_safety(readings, rules)` (returning a `WeatherSafetyStatus` of overall safe/unsafe plus which rules tripped) let the user mark any reading safety-related and define its unsafe condition (e.g. `rain > 0`, `wind_speed >= 20`), persisted per Pier/reading as `WeatherSafetyRuleRecord` (migration `024_add_weather_safety_rules.py`); `default_weather_safety_rules()` seeds a sensible starter set (Rain, Wind Speed pre-enabled) on a Pier's first visit to the Weather screen. This is deliberately walled off from the unsafe-state event path the same way `SAFE-050`'s forecast is (above) and for the identical reason: it is advisory/display-only and structurally cannot publish `SafetyUnsafeEvent` or drive `SAFE-010`'s automated abort — only a connected Safety Monitor device (Tier 1/2 above) is authoritative for that. The Equipment > Weather screen (`galileo.ui.app_window._weather_page`) is where the rules are configured and the full reading set is displayed; the Equipment > Safety Monitor screen (`galileo.ui.app_window._safety_monitor_page`, Section 4.4b) surfaces only the safety-related subset, read-only, alongside a trend graph and the connected Safety Monitor device's own (authoritative) SAFE/NOT-SAFE state — two displays of the identical `evaluate_weather_safety` computation so they can never disagree with each other.
- **Satisfies:** `SAFE-010`–`SAFE-100`, `EXT-130`, `EQP-WX-020`, `EQP-SAFE-020`.

### 4.17 `galileo.history` — Session History & Statistics

- **Responsibility:** Per-frame metric recording (HFR, star count, guide RMS), review UI, cross-restart retention, export.
- **Key design:** Append-only Peewee models keyed by session/sequence ID, in the same database as `galileo.library`'s repository catalog (ADR-002) rather than a separate SQLite file; chart rendering via Qt Charts against a query view.
- **Satisfies:** `HIST-010`–`HIST-040`.

### 4.18 `galileo.metadata` — Image Metadata (FITS)

- **Responsibility:** FITS header population, plate-solve result injection, tile-compressed FITS read/write, custom static keywords. FITS is the sole supported image format (Project Scope Document, Section 11, C3) — no XISF or other format support exists in this module.
- **Key design:** Compressed output uses `astropy.io.fits.CompImageHDU`, which wraps CFITSIO's tile-compression implementation directly — no separate compression library or format-specific writer is needed, since this is standard FITS, not an alternate container format. Default compression algorithm is Rice (lossless, low CPU cost, the common default for astronomical CCD/CMOS data); GZIP and HCOMPRESS are selectable per profile. `normalise_pixels` (Section 4.5) is this module's own — every writer here goes through it, so no path can silently regress to a 64-bit sample format.
- **Libraries:** `astropy.io.fits` (covers both plain and tile-compressed FITS read/write).
- **Satisfies:** `META-010`–`META-050`, `EXT-060`.

### 4.19 `galileo.notify` — Notifications

- **Responsibility:** In-app and external notification delivery for session/safety events, per-channel/per-event enablement. External channels are narrowed in this revision to **email and/or text message (SMS)** specifically (superseding the earlier "webhook or push service" example) — matching a single operator's overnight reachability rather than a generic integration surface.
- **Key design:** `NotificationChannel` adapter interface (in-app, email, SMS); event set sourced from the same event bus used internally, so no separate event-detection logic is needed. An SMS channel is implemented via a carrier email-to-SMS gateway or a third-party SMS API adapter behind the same `NotificationChannel` interface — the choice is an adapter-level decision, not a design constraint this module imposes. Delivery reads its target contact details (email address, phone/SMS number, enabled channel(s)) from the `Observatory` record (`galileo.observatory`, Section 4.4a, `OBS-090`) that owns the Pier/session raising the event, via a lookup rather than a separate per-notification contact store — `NOTIF-040`.
- **Satisfies:** `NOTIF-010`–`NOTIF-040`, `EXT-070`.

### 4.20 `galileo.plugins` — Plugin Framework

- **Responsibility:** Plugin discovery/load/unload, manifest/version compatibility checking, the **Options > Plugins screen** (installed-plugin list, Install from file, Plugin Marketplace, and Remove), fault isolation, per-plugin enable/disable, UI-panel insertion at primary or secondary navigation level, and the `PluginContext` service-access surface plugins use to call back into core (e.g. submitting a Scheduler job).

- **Plugin ZIP package format:** a plugin is distributed as a ZIP containing:
  - A Python package importable as `galileo.plugins.<name>` (the plugin's own code).
  - A top-level `plugin.toml` manifest with required fields: `name`, `version` (semver), `api_min`/`api_max` (Galileo plugin-API version range the plugin is compatible with), `author`, `description`, and `tier` (`first_party` or `third_party`). Optional fields: `nav_level` (`primary` or `secondary`, if the plugin registers a UI panel), `entry_point` (defaults to `galileo.plugins.<name>`).
  - Nothing else is required; optional `README.md`, `CHANGELOG.md`, and `LICENSE` are preserved but not required.

- **Distribution:** plugins are hosted on the galileo-imaging.com plugin page as direct download links. No plugin is bundled inside the Galileo installer itself — including first-party ones. VSTarget (`galileo.plugins.vstarget.planning` / `galileo.plugins.vstarget.analysis`) ships as two separately downloadable ZIPs, making them the first live proof that the full distribution pipeline (ZIP packaging → website hosting → in-app Marketplace → install → run) works end-to-end.

- **Options > Plugins screen (`PLUG-030`):**
  - **Installed** tab — table of installed plugins: name, version, tier, author, enabled toggle, Remove button. The enabled toggle immediately activates or deactivates the plugin's registered extension points and UI panels (or defers to restart if the runtime does not support hot-unload of the affected extension type). The Remove button triggers `PLUG-120`: marks the plugin for deletion, disables it immediately, completes file deletion and deregistration on next restart if live unload is not possible, and shows a banner prompting restart.
  - **Install from file** button — opens a file picker filtered to `*.zip`; on selection runs the install pipeline (`PLUG-090`).
  - **Marketplace** tab — on first open (or on a manual Refresh) fetches and parses the galileo-imaging.com plugin page (`PLUG-100`), populates a card grid (name, description, version, tier badge, Install button). Already-installed plugins show "Up to date" or "Update available" rather than a second Install button. Each Install triggers `PLUG-110` (download + install pipeline, same as `PLUG-090` after download).

- **Install pipeline (shared by `PLUG-090` and `PLUG-110`):**
  1. Validate the ZIP is well-formed and contains `plugin.toml`.
  2. Parse and validate the manifest (required fields, semver format).
  3. Version-check `api_min`/`api_max` against the running application's plugin-API version (`PLUG-050`); abort with a user-visible error if incompatible.
  4. Extract to `<plugins_dir>/<name>-<version>/` (platform path from `galileo.platform`).
  5. Register the package on `sys.path` and call `importlib.import_module(entry_point)` to load.
  6. If load raises, log the error, remove the extracted directory, and surface an error dialog — never leave a half-installed plugin on disk.

- **Key design:** Plugins are discovered at startup by scanning `<plugins_dir>` for valid `plugin.toml` manifests, not via `importlib.metadata` entry points (which require `pip install` and therefore wouldn't work for ZIP-dropped plugins). Every call from domain core into plugin-provided code is wrapped at the call boundary in an exception handler that logs and disables the offending plugin instance rather than propagating (`PLUG-040`). A UI-panel-registering plugin declares `nav_level` in its manifest; the shell's navigation container reads this the same way for every plugin, so there is no separate "built-in tab" code path. `PluginContext` (Section 6.3) exposes a narrow, explicitly-granted set of core service handles (e.g. `SchedulerJobSubmitter`) rather than the whole domain core (`PLUG-080`).

- **Marketplace scraping:** `galileo.plugins.marketplace.MarketplaceClient` issues an HTTP GET to the galileo-imaging.com plugins page. The website is expected to include a machine-readable JSON block (`<script type="application/json" id="galileo-plugins">…</script>`) listing available plugins; if absent, the client falls back to HTML scraping for `<a>` links in a designated `<section id="plugins">` element. Either way, the result is a list of `MarketplaceEntry(name, description, version, tier, download_url)` objects. The client caches the last-fetched result in memory for the session; a Refresh button forces a new fetch.

**Reference implementation:** `galileo.plugins.vstarget.planning`/`galileo.plugins.vstarget.analysis` are packaged as two separate first-party ZIP files and hosted on galileo-imaging.com — the concrete demonstration of Marketplace install (`PLUG-110`), per-plugin enable/disable (`PLUG-060`), primary-level UI-panel insertion (`PLUG-070`), the `PluginContext` Scheduler-submission callback (`PLUG-080`), and plugin removal (`PLUG-120`). Their own module design is in [`docs/plugins/vstarget/SDD.md`](../plugins/vstarget/SDD.md) Section 3.

**A second, smaller reference implementation — one `DeviceBackend` registration, no other extension point:** `kasa_switch` and `generic_relay` (source in the separate [Galileo-Plugins](https://github.com/gordtulloch/Galileo-Plugins) repository, not vendored under `galileo.plugins.*`) each call `PluginContext.register_device_backend(DeviceCategory.SWITCH, ...)` — `PLUG-010`/`ARCH-070` — and nothing else; their `build_page()` returns a secondary-level panel (`PLUG-070`) with no `PluginContext` service grant needed beyond that one registration. Where VSTarget demonstrates the full extension surface, these two demonstrate the minimum a plugin needs to add one new piece of hardware support. Their own module design is in [`docs/plugins/kasa_switch/SDD.md`](plugins/kasa_switch/SDD.md) and [`docs/plugins/generic_relay/SDD.md`](plugins/generic_relay/SDD.md) Section 3.

**Design note:** this provides fault isolation, not memory/security sandboxing — a plugin runs in-process with full application privileges; stronger sandboxing (e.g. subprocess-per-plugin) is out of scope for v1. In-process loading has a licensing consequence: under Galileo's GPL-3.0 license (ADR-002), plugins are very likely "combined works" and must themselves be GPL-compatible-licensed to distribute.
- **Satisfies:** `PLUG-010`–`PLUG-120`, `NFR-EXT-010`.

### 4.21 `galileo.ui.theme` — Customization & Theming

- **Responsibility:** Light/dark/red-night-vision theme, accent color, dockable panel layout persistence.
- **Key design:** Qt Style Sheets (QSS) driven by a small token set (background/surface/accent/text), so a theme is a token file, not per-widget styling. The red night-vision theme (`UI-011`) is that same token mechanism with every value constrained to `#RR0000` (green/blue channels always `0x00`), including its accent, which `ThemeManager.accent_color` forces to a fixed red rather than reading the user's saved preference (`UI-030`) — a user-picked accent is not guaranteed red, and any non-red pixel would defeat a night-vision theme's purpose. The sidebar theme-toggle button cycles Light → Dark → Red night-vision → Light rather than a binary switch.
- **Satisfies:** `UI-010`–`UI-030`.

### 4.22 `galileo.diagnostics` — Logging & Diagnostics

- **Responsibility:** Runtime logging service capturing all application log output, in-app log viewer (including a per-device-screen live tail), unhandled-exception capture, support-bundle export.
- **Key design:** `DiagnosticsService` sets the root `logging` logger to `DEBUG` and attaches a `logging.FileHandler` writing to a datestamped file under `logs/` in the application's own root directory (`default_log_dir()`, not a per-platform user directory — a deliberate departure from `NFR-INSTALL`-style per-OS conventions, made so the current run's log is always found next to the application itself) — opened in truncate mode (`LOG-050`) so each run starts a fresh file rather than appending to a prior run's. Because the root logger's level and handler are process-wide, every module's own `logging.getLogger(__name__)` calls are captured, not only ones routed through `DiagnosticsService`'s own `log_info`/`log_warning`/`log_error`/`log_exception` convenience methods (`LOG-010`'s "all runtime log output" clause) — this includes third-party library logging (e.g. Peewee's own SQL debug output) picked up along the way. A second handler (`_TailBufferHandler`) feeds a bounded, process-wide in-memory ring buffer exposed via `get_recent_log_lines(n)`, independent of any particular `DiagnosticsService` instance; `galileo.ui.app_window`'s Equipment device-category pages each embed a small read-only, auto-scrolling `QPlainTextEdit` (fixed to a 10-line viewport, scrollable back through a larger buffer) polling that function on a shared timer (`LOG-060`) — a lightweight, always-visible alternative to opening a dedicated Log Viewer for `LOG-020`.
- **Libraries:** standard library `logging` only (no `platformdirs` — the log directory is resolved directly, matching the application-root placement above).
- **Satisfies:** `LOG-010`–`LOG-060`.

### 4.23 `galileo.library` — Image Library & Repository Management (merged from AstroFiler)

- **Responsibility:** Repository scanning/ingestion (FITS and XISF), SHA-256 dedup, metadata-driven file organization, session linking (both heuristic, `LIB-040`, and sequence-authoritative, `LIB-160`), master calibration-frame creation and application, SEP-based quality metrics, repository statistics, smart-telescope ingestion (SMB/CIFS, FTP/FTPS, SFTP), Google Cloud Storage sync, live auto-registration during acquisition, and CLI entry points.
- **Key design:** This module is the vendored core of AstroFiler (ADR-002), restructured behind the same domain-core/adapter boundary as the rest of Galileo: scanning/dedup/organization/session-linking/master-frame logic is domain-core (no I/O dependency beyond the filesystem and the Peewee models it owns); SMB, FTP/FTPS, and GCS access are adapters (`SmbSourceAdapter`, `FtpSourceAdapter`, `GcsSyncAdapter`) implementing a common `RemoteSourceAdapter` interface, so adding a new smart-telescope source is an adapter, not a core change — consistent with how `PLT` treats solvers and `GUIDE` treats guiders elsewhere in this document.
  - **XISF import (`LIB-010`):** a best-effort `XisfToFitsConverter` runs at ingest time only — this module never reads or writes XISF anywhere else, preserving the FITS-only constraint (Project Scope Document, Section 11, C3) for everything downstream of ingestion. Metadata/pixel data that doesn't map cleanly to FITS keywords is logged, not silently dropped, and the frame is still ingested.
  - **Auto-registration (`LIB-150`):** rather than polling, `galileo.sequencer.basic`/`galileo.sequencer.advanced` (Sections 4.6–4.7) publish a "frame written" event on the domain-core event bus (Section 2.2) after each capture completes; this module subscribes and registers the frame immediately, the same fault-isolated event-bus pattern used for safety/dome coordination elsewhere in this document — `LIB-010`'s scan remains available as a reconciliation path for frames from outside a Galileo-run sequence (manual copies, other tools), not the primary ingestion route once a sequence is running.
  - **Session containers (`LIB-160`):** a `SessionContainer` is created per sequence-step execution and referenced by every frame the "frame written" event carries for that step — this is populated directly from the sequencer's own step boundaries, not inferred from FITS headers after the fact, which is what distinguishes it from `LIB-040`'s heuristic grouping of files already in the repository (the two coexist: a `LIB-160` container is authoritative when available, `LIB-040` grouping is the fallback for repository content that never went through a Galileo sequence).
  - **CLI (`LIB-130`/`EXT-140`):** all twelve of AstroFiler's command-line utilities live in `galileo.commands` (`load_repo`, `create_sessions`, `link_sessions`, `auto_calibration`, `cloud_sync`, `sync_repo`, `register_existing`, `download`, `stack`, `photometry`, `variable_star_photometry`, `reset_calibration_test_state`), each also installed as a `galileo-<name>` console script. They are thin entry points that call directly into `galileo.library.core` and `galileo.library.services`, bypassing the UI layer entirely (nothing under `galileo.commands` imports Qt) — matching AstroFiler's own `LoadRepo`/`AutoCalibration`/`CloudSync` pattern (Project Scope Document, Section 6.2). They share `galileo.commands._common` (the settings file and the log file), and none is a general-purpose scripting shell — consistent with `EXT-010`'s "selective exposure," not a backdoor into interactive equipment control.
  - **Layout and data:** `galileo.library.models` holds AstroFiler's catalog models (`fitsFile`, `fitsSession`, `Mapping`, `Masters`, `VariableStars`, under AstroFiler's table and column names so its databases open unchanged) beside Galileo's observatory/pier/device/optical-tube records, in the one shared database (ADR-002). The schema is owned by the numbered `peewee-migrate` files in `galileo/library/migrations` — AstroFiler's `001`–`012`, then Galileo's `013`/`014` — and `galileo.library.database.init_db` applies any pending at start-up. `galileo.library.core` is the domain logic (ingest, sessions, master frames, calibration, quality, duplicates); `galileo.library.services` the cloud and smart-telescope adapters; `galileo.library.registrar.LibraryRegistrar` is what the sequencer hands frames to (`LIB-150`/`LIB-160`); `galileo.library.config` reads and writes `library.ini`, the settings shared by the screens and the commands. `galileo.library.adapters` (SMB/FTP/SFTP) is the earlier, smaller set of source adapters that `EXT-080`/`EXT-120` tests and `galileo.plugins.vstarget.analysis` still use; AstroFiler's fuller implementations are in `galileo.library.services.telescope`.
  - **Screens (Library sidebar section, Options > Library):** the Library section opens onto Images, Sessions, Mappings, Dedup, Merge Objects and Cloud (one screen each, no tabs — the repository statistics dashboard once specified as `LIB-080` was removed on request and that requirement is now retired, see SRS Section 4.22; the Pier selector is hidden in this section because the catalog is not per-Pier), all in `galileo.ui.library`; Options > Library is `galileo.ui.library.config_widget`. They are adapters over `galileo.library` like every other screen, and are built together on first use because they read the whole catalog.
- **Libraries:** `astropy.io.fits` (metadata extraction, shared with `galileo.metadata`), `peewee`/`peewee-migrate` (catalog persistence, project-wide per ADR-002), `SEP` (quality metrics, unified per ADR-002), `pysmb` (SMB/CIFS), standard-library `ftplib` (FTP/FTPS), `paramiko` (SFTP, `galileo.library.adapters.sftp.SftpSession` — the only SFTP code in Galileo; plugins reuse the Library rather than carrying their own), `google-cloud-storage`/`google-auth` (cloud sync), `Pillow` (thumbnail/preview generation), `scipy`/`reproject` (master-frame stacking and alignment), `matplotlib` (statistics chart), `lz4` (lz4-compressed XISF blocks).
- **Satisfies:** `LIB-010`–`LIB-170`, `EXT-080`, `EXT-090`, `EXT-120`, `EXT-140`.

### 4.24 / 4.25 `galileo.plugins.vstarget.planning` / `galileo.plugins.vstarget.analysis` — Moved

Design for the VSTarget plugin's two modules is no longer here — see [`docs/plugins/vstarget/SDD.md`](../plugins/vstarget/SDD.md) Sections 3.1–3.2. These section numbers are kept as placeholders rather than renumbered away, so cross-references to Section 4.26 and beyond elsewhere in this document stay valid.

### 4.26 `galileo.derotation` — Rotator Field Derotation

- **Responsibility:** The domain logic behind the Rotator Equipment page's derotation section (layout reference: `assets/samples/rot.png`): converting a target's RA/Dec to Alt/Az for a site and time, the alt-az field rotation rate, and turning that rate into rotator move commands.
- **Key design:** Pure Python with no Qt, INDI or Alpaca dependency; the page drives a device adapter with it. The rate is `Ω·cos(lat)·cos(az)/cos(alt)` (Ω = 0.25068°/min, clamped near the zenith where it diverges). Sidereal time is computed directly from the Julian date rather than through `astropy`'s Alt/Az frames, which can try to download IERS data at runtime. `Derotator` integrates the rate into a virtual angle and only requests a move once it has drifted a minimum step (default 0.05°) from the last commanded angle, so a rotator isn't commanded for every tiny increment. A target comes from typed RA/Dec, or the newest FITS file in a folder (solved WCS, then `OBJCTRA`/`OBJCTDEC`, then `RA`/`DEC`). The rotator adapters (`galileo.adapters.indi` / `.alpaca`) gained `get_status`, `halt`, `set_reverse`, `sync_position` and `set_backlash`; backlash exists only on INDI drivers implementing it (ASCOM's `IRotatorV3` has none, and the INDI Rotator Simulator lacks it), and reports `DevicePropertyError` otherwise. The Reverse setting also flips the derotation direction. The derotation direction sign has not been validated against a real alt-az rig.
- **Libraries:** standard library plus `astropy.io.fits` for reading headers.
- **Satisfies:** `EQP-ROT-010` (position display and move commands). Derotation itself has no requirement ID yet — it should be added to the SRS/RTM.

All schema-validated formats (`pydantic` models) double as the machine-checkable contract for `EXT-060`, `META-010`–`META-030`, and the profile/session persistence requirements — schema validation failures surface as the "recoverable error" path required by `SES-080`/`PROF-060` rather than a crash.

## 6. Interface Design

### 6.1 Device Port Interfaces (internal)

Each device category exposes a minimal, transport-agnostic interface, e.g.:

```
CameraPort: connect(), disconnect(), capabilities() -> DeviceCapabilities,
            start_exposure(params), abort_exposure(), set_cooler_target(temp),
            on_frame_ready: Signal[FrameData], on_status_changed: Signal[DeviceStatus]
```

Both `galileo.adapters.indi` and `galileo.adapters.alpaca` implement every port; the domain core and UI never import either adapter module directly, only the port interfaces (enforced by module-boundary lint rules).

### 6.2 External Process Interfaces

- **Solvers:** subprocess invocation with a documented argument/exit-code/output-file contract per solver adapter (`galileo.platesolve`).
- **Guiders:** PHD2-compatible JSON-RPC-over-TCP event/command stream (`galileo.guiding`).
- **Smart-telescope/cloud sources:** SMB/CIFS session (`pysmb`), FTP/FTPS session (`ftplib`), and Google Cloud Storage API calls, each behind the `RemoteSourceAdapter` interface (`galileo.library`, Section 4.23).
- **Simbad:** object-name/coordinate/magnitude queries (`astroquery`), used by `galileo.planning.sky_atlas` (Section 4.8, `SKY-100`/`EXT-110`) and, independently, by the VSTarget plugin.
- **AAVSO (VSTarget plugin only, not core):** AAVSO Target Tool/VSP REST API calls (`requests`) — see [`docs/plugins/vstarget/SDD.md`](../plugins/vstarget/SDD.md) Section 5. SFTP image retrieval (`paramiko`) is core's, owned by the Library (`EXT-120`), not the plugin.
- **Open-Meteo:** geocoding (`galileo.planning.sky_atlas`, `SKY-090`) and weather-forecast (`galileo.safety`, `SAFE-050`) REST calls, adapted from AstroLlama (ADR-004, Section 2.7).

### 6.3 Plugin API Surface

A plugin depends only on: the device port interfaces (4.1), the `SequencerNode` interface (4.7), and a small `PluginContext` object (logging, config directory, event-bus handle) injected at load time. No plugin imports UI or adapter internals directly.

## 7. Deployment Design

Two supported topologies, both served by the same codebase (Section 2.1):

- **Topology A — Network split (primary, recommended default):** A Raspberry Pi 5 (or similar SBC) at the telescope runs only `indiserver` + device drivers (or an Alpaca device bridge) — not Galileo itself. Galileo's full GUI runs on a separate desktop/laptop, connecting to the SBC over the local network via the INDI/Alpaca adapters (`ARCH-020`, `EXT-030`). This keeps the SBC's resource constraints out of the GUI's performance budget entirely and is the deployment pattern the INDI ecosystem already assumes.
- **Topology B — Local/all-in-one:** Galileo's full GUI runs directly on the SBC (e.g. an all-in-one imaging box with a local touchscreen, or headless with VNC). PySide6's shared Qt rendering engine (ADR-001) makes this viable on Pi 5-class hardware, at a higher resource cost than Topology A.

The SDD does not mandate one topology for end users — both are supported by the architecture — but Topology A should be the documented recommended default for resource-constrained hardware.

## 7. Non-Functional Requirement Traceability

Functional requirements each trace to one primary module's `Satisfies` line (Section 4). | Requirement | Addressed by |
|---|---|
| `NFR-PERF-010` (full-frame render ≤3s) | `galileo.ui.imaging` (Section 4.5) rendering pipeline; verified by performance test, not a design-time guarantee any single module line can assert |
| `NFR-PERF-030` (stable memory over 8h) | Cross-cutting outcome of the `ProcessPoolExecutor` CPU-work isolation (Section 2.3) and per-sequence progress persistence (`galileo.sequencer.basic`, Section 4.6) not leaking state across long runs; verified by soak test |
